IIS Windows認証
初回パスワード設定ガイド

利用者のWindowsログオン情報で本人確認し、初回ログイン時に本人がパスワードを決められるようにするための導入手順です。

CONTENTS 1. 仕組み 2. 事前確認 3. 変更する場所 4. スクリプト実行 5. アプリ設定 6. 動作確認 7. トラブル対応 8. 元に戻す

1. 何を設定するのか

IISでは匿名認証とWindows認証を同時に有効にします。Windows認証を実際に要求するのはWatashi.Serverの認可ポリシーで、初回パスワード設定用の /api/auth/win/* だけです。通常API、ポータル、インストールページは匿名で到達できます。

IISのサイト／アプリ 匿名認証: 有効
Windows認証: 有効
Watashi.Serverの制御 /api/auth/win/*: Windows認証を要求
その他: 従来の匿名／JWT認証
重要: 匿名認証を無効にしないでください。また、IISに /api/auth/win の場所別Locationを作らないでください。場所別設定はASP.NET Coreのハンドラーを外し、APIを物理ファイルとして探す 404.0 の原因になります。

このIIS設定はサーバーの applicationHost.config に保存されます。一度設定すれば、Watashiを再発行しても再実行は不要です。

2. 実行前の確認

IISサーバーへ管理者権限でログインします。
deploy\configure-iis-windows-auth.ps1 をIISサーバー上の任意の作業フォルダーへ置きます。
IISマネージャーを開き、Watashiの「サイト名」と「アプリケーションプール名」を確認します。
利用者のWindowsユーザー名とWatashiユーザー名が一致することを確認します。例: JP\0020h28809 に対する登録名は 0020h28809 です。
サイト直下ではなく「Default Web Site」配下のWatashiアプリとして配置している場合、サイトパスは Default Web Site/Watashi です。

3. スクリプトのどこを変えるか

既定構成なら変更不要です。環境名が異なる場合は、スクリプト冒頭の param 内にある★印の2項目だけ変更します。

# ★ IIS マネージャーの「サイト」名
[string]$SitePath = "Watashi.Server",

# ★ IIS マネージャーの「アプリケーション プール」名
[string]$AppPoolName = "Watashi.Server",

ファイルを編集せず、実行時の引数で指定する方法を推奨します。

.\configure-iis-windows-auth.ps1 -SitePath "Default Web Site/Watashi" -AppPoolName "Watashi.Server.Production"
項目既定値変更が必要な場合
SitePathWatashi.ServerIISのサイト名が違う、またはサイト配下のアプリとして配置している
AppPoolNameWatashi.ServerWatashiを実行するアプリケーションプール名が違う
WindowsAuthPathapi/auth/win旧版が作成した場所別設定の移行と確認URLの表示に使用。通常は変更しない

4. スクリプトを実行する

4-1. 管理者PowerShellを開く

スタートメニューで「PowerShell」を検索し、「管理者として実行」を選びます。スクリプトのあるフォルダーへ移動してください。

4-2. 事前確認だけ行う

.\configure-iis-windows-auth.ps1 -WhatIf

4-3. 設定を適用する

Set-ExecutionPolicy -Scope Process Bypass
.\configure-iis-windows-auth.ps1
スクリプトはWindows認証機能の導入、IIS構成バックアップ、匿名認証とWindows認証の併用設定、旧版の場所別設定の削除、設定検証、アプリケーションプール再起動まで実施します。

主なオプション

オプション用途
-WhatIf変更内容を事前確認し、実際には変更しない
-SkipWindowsFeatureInstallWindows認証機能が導入済みで、役割サービス確認を省略したい
-SkipAppPoolRestart利用中のためアプリケーションプールを今すぐ再起動したくない

5. Watashi.Serverの設定

リポジトリの src\Watashi.Server\appsettings.json には、次の設定が既定で入っています。

"WindowsAuth": {
  "Mode": "IIS",
  "DomainMatch": "IgnoreDomain",
  "AllowedDomains": [],
  "EnableDiagnostics": true,
  "SetupPerMinutePerIp": 30
}
既存環境: 本番の appsettings.json にJWT秘密鍵などを設定済みの場合、ファイル全体を上書きしないでください。上記の WindowsAuth ブロックだけを本番設定の Auth 内へ追加します。

IgnoreDomain では、JP\0020h28809 のドメイン部を除いた 0020h28809 をWatashiユーザー名と照合します。大文字・小文字は区別しません。

6. 動作確認

Watashiを利用する本人のPCで、コマンドプロンプトから実行します。URLは実環境に置き換えてください。

whoami
curl.exe -s -i --negotiate -u : https://watashi.internal/api/auth/win/whoami
Negotiateの確認では、最初に 401 Unauthorized が表示され、その後に 200 OK とJSONが返ることがあります。最初の401は認証開始の合図で、最後のHTTPステータスが結果です。

次の値になれば、Windows認証とユーザー登録は正常です。

{
  "rawAccountName": "JP\\0020h28809",
  "normalizedName": "0020h28809",
  "domain": "JP",
  "domainAllowed": true,
  "watashiUserExists": true,
  "isPasswordSetupPending": true,
  "windowsAuthMode": "IIS"
}

その後Watashiを起動し、ユーザー名に 0020h28809 と入力します。「次へ」で初回パスワード設定画面へ進めば完了です。

7. うまくいかない場合

結果・症状確認すること
401 UnauthorizedIISのWindows認証機能、スクリプトの実行結果、利用者PCがドメイン参加しているかを確認
IIS詳細エラーが 404.0／ハンドラーが StaticFile旧版の Watashi.Server/api/auth/win Locationが残っている可能性があります。最新版のスクリプトを再実行し、場所別設定を削除します
JSON形式の 404 Not Found要求はWatashi.Serverに届いています。本番 appsettings.json の Mode と EnableDiagnostics を確認し、アプリケーションプールを再起動します
normalizedName が想定外rawAccountName を確認。Watashiにはドメインを除いた名前だけを登録
domainAllowed: falseDomainMatch を確認。IgnoreDomain なら通常は true
watashiUserExists: false管理画面の登録名を確認。例: JP\0020h28809 ではなく 0020h28809
isPasswordSetupPending: false管理画面で対象ユーザーを選び、「初回設定に戻す」を実行
パスワード入力画面へ進んでしまうWindows認証の判定に失敗すると通常ログインへフォールバックするため、上記の診断APIを確認

8. 元に戻す

スクリプト実行時に、Watashi-WindowsAuth-yyyyMMdd-HHmmss-fff という名前でIIS構成をバックアップします。

Import-Module WebAdministration
Get-WebConfigurationBackup
Restore-WebConfiguration -Name "Watashi-WindowsAuth-＜日時＞"

Windows認証による初回設定自体を止める場合は、本番 appsettings.json の WindowsAuth:Mode を None に変更し、アプリケーションプールを再起動します。

EnableDiagnostics は本人自身の情報だけを返しますが、導入確認が終わった後に診断APIが不要なら false に変更できます。
