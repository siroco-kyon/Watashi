Watashi certificate guide

.cer から .pfx を作る

社内 CA から受け取った .cer を、Kestrel や mTLS で使える .pfx (PKCS#12) にまとめる手順です。秘密鍵がどこにあるかで作り方が変わるため、まず所在を判定するところから始めます。

0. 先に結論

重要な前提

.cer 単体を .pfx に「変換」することはできません。.pfx には秘密鍵が入りますが、.cer には秘密鍵が含まれていないからです。

正しくは「.cer に秘密鍵を結合して .pfx を作る」という作業になります。したがって出発点は「秘密鍵がどこにあるか」の確認です。

Windows で運用するなら、そもそも .pfx を作らない選択肢もあります。Kestrel は Windows 証明書ストアから直接読めるので、ストア参照方式のほうが運用は楽です（パスワードを設定ファイルに書かずに済み、更新時も設定変更が不要）。方式の比較は CERTIFICATE.md にまとめてあります。

それでも .pfx が必要になるのは、別マシンへ証明書を持ち込む場合（証明書を取得できないマシンへの配布）や、mTLS のクライアント証明書としてファイル指定する場合です。

1. .cer / 秘密鍵 / .pfx の関係

3 つのファイルが何を含んでいるかを押さえると、以降の判断がすべて自明になります。

2. サーバ証明書を用意するまでの流れ

ケース A（サーバで CSR を作る）では、PFX を作る前段としてこの 4 ステップが必要です。順序が重要で、③ を飛ばすと ④ が失敗します。

① サーバで CSR を作成する

証明書を使うマシン自身で作ります。秘密鍵はこの操作でマシン内に生成され、以降そのマシンから出ません。別のマシンで作ると、そちらに秘密鍵が残ってしまいます。

; request.inf
[NewRequest]
Subject = "CN=watashi.internal"
KeyLength = 2048
KeyAlgorithm = RSA
HashAlgorithm = SHA256
MachineKeySet = True
; PFX にして別マシンへ持ち出す予定があるなら True にする
Exportable = True
KeyUsage = 0xa0
ProviderName = "Microsoft RSA SChannel Cryptographic Provider"
RequestType = PKCS10

[Extensions]
2.5.29.17 = "{text}"
_continue_ = "dns=watashi.internal&"
_continue_ = "dns=watashi&"

[EnhancedKeyUsageExtension]
OID = 1.3.6.1.5.5.7.3.1
certreq -new request.inf request.req

Exportable の値はここで決まります。PFX にして別マシンへ持ち込む予定があるなら True にしてください。False で発行してしまうと、後から変更する手段はなく、5 章の手順が使えません。同じマシンで使うだけなら False（秘密鍵が外に出せない）のほうが安全です。

SAN には、クライアントが実際にアクセスに使う名前をすべて入れてください。FQDN・短縮名・必要なら IP。最近の .NET やブラウザは CN を見ずに SAN だけで判定するため、SAN に無い名前で接続すると証明書エラーになります。

② 社内 CA へ申請してサーバ証明書を受け取る

生成された request.req を社内 CA へ提出します。AD CS なら Web 登録ページから申請できます。

http://<CAサーバ名>/certsrv

「証明書を要求する」→「証明書の要求の詳細設定」→「Base 64 エンコード ... を使用して要求を送信する」で request.req の中身を貼り付けます。証明書テンプレートは Web サーバー（サーバー認証用）を選びます。Web 登録ページが無い環境では、CA 担当者に .req を渡して発行を依頼してください。

発行された .cer をダウンロードします。この時点ではまだ使えません。秘密鍵と結合されていないうえ、チェーンも繋がっていないためです。

③ ルート CA / 中間 CA 証明書を登録する

ここが最も抜けやすいステップです。「サーバ証明書を申請する」作業とは別に、その証明書を発行した CA を自分のマシンが信頼できる状態にする必要があります。申請フローの案内に含まれていないことが多く、飛ばしたまま ④ に進んで 0x800B010A（証明書チェーンを信頼されたルート機関に構築できませんでした）で止まる、というのが典型的な詰まり方です。

同じ certsrv のトップページから入手できます。

http://<CAサーバ名>/certsrv を開き、「CA 証明書、証明書チェーン、または CRL のダウンロード」を選ぶ

「CA 証明書チェーンのダウンロード」を選ぶと、ルートと中間がまとめて .p7b で取得できる（個別の .cer でも可）

サーバへ持ち込み、ルートは Root、中間は CA ストアへ登録する

:: ルート CA →「信頼されたルート証明機関」
certutil -addstore Root C:\temp\rootCA.cer

:: 中間 CA →「中間証明機関」(2 階層構成の場合)
certutil -addstore CA C:\temp\intermediateCA.cer

入れるストアを取り違えるとチェーンは繋がりません。ルートを CA に、中間を Root に入れても、見た目は成功しますが ④ で同じエラーになります。

サーバから CA サーバへ到達できない閉じたネットワークの場合は、ドメイン参加 PC から Export-Certificate で取り出して持ち込みます。手順は INTERNAL-CA-HTTPS.html の 3 章にまとめてあります。

④ サーバ証明書を取り込んで秘密鍵と結合する

チェーンが繋がったことを先に確認してから取り込みます。

:: チェーンが構築できるか確認 (-urlfetch は付けない)
certutil -verify C:\temp\server.cer

:: 秘密鍵と結合する
certreq -accept -machine C:\temp\server.cer

:: 結合できたか確認 →「秘密キーがあります」が出れば成功
certutil -store My

「秘密キーがあります」が表示されれば、この証明書は TLS で使える状態です。ここまで来て初めて 5 章の PFX 書き出しが可能になります。

③ を飛ばしたまま certutil -repairstore で無理に紐付けた場合、④ 自体は通ることがあります。しかしその状態で PFX を作ると -ChainOption BuildChain がチェーンを構築できず、中間 CA の入っていない PFX ができあがります。配布先で証明書エラーになるため、結局 ③ からやり直しになります。

3. どのケースかを判定する

秘密鍵の所在は CSR をどこで、何で作ったかで決まります。次のコマンドで確認します。

:: Windows 証明書ストアに秘密鍵付きで入っているか
certutil -store My

対象証明書のブロックに「秘密キーがあります」の行があるかどうかが分岐点です。

ケース C に該当した場合、PFX を作る手段はありません。秘密鍵はどこにも残っていないため、復元も再構成もできません。CA へ CSR を出し直して再発行を依頼してください。証明書自体は公開情報なので、再発行しても実害はありません。

ただし判定を誤っている可能性もあるので、先に以下を確認してください。

  • 保留中の要求が残っていないか — certutil -store REQUEST / certutil -user -store REQUEST
  • 証明書だけ取り込まれて紐付けが切れていないか — certutil -repairstore My "<拇印>" で修復できる場合がある
  • CSR を別のマシンで作っていないか — 秘密鍵はそのマシンにある

4. 手順の全体像

5. ケース A — Windows 証明書ストアから書き出す

そのマシンで CSR を作り、certreq -accept で証明書を取り込み済みの状態が前提です。

Step 1: 拇印を調べる

Get-ChildItem Cert:\LocalMachine\My |
    Where-Object { $_.HasPrivateKey } |
    Select-Object Subject, DnsNameList, Thumbprint, NotAfter | Format-List

HasPrivateKey が True の証明書だけが PFX にできます。目的の証明書の Thumbprint を控えてください。

IIS の証明書要求機能や Win-ACME で取得した証明書は My ではなく WebHosting ストアに入ります。My に見当たらない場合は Cert:\LocalMachine\WebHosting も確認してください。

Step 2: エクスポート可否を確認する

社内 PKI から配布される証明書は、秘密鍵をエクスポート不可にして配られるのが普通です。その場合 PFX は作れません。先に確認してください。

$thumb = "1A2B3C4D5E6F7890ABCDEF1234567890ABCDEF12"
$cert = Get-ChildItem "Cert:\LocalMachine\My\$thumb"
$rsa = [System.Security.Cryptography.X509Certificates.RSACertificateExtensions]::GetRSAPrivateKey($cert)
if ($rsa -is [System.Security.Cryptography.RSACng]) {
    "CNG / ExportPolicy = " + $rsa.Key.ExportPolicy
} else {
    "CAPI / Exportable = " + $cert.PrivateKey.CspKeyContainerInfo.Exportable
}
出力意味対処
AllowExport を含む / Exportable = Trueエクスポート可Step 3 へ
ExportPolicy = None / Exportable = Falseエクスポート不可PFX は作れない。下の対処を参照

GUI でも判定できます。certlm.msc → 対象を右クリック →「すべてのタスク」→「エクスポート」で、「はい、秘密キーをエクスポートします」がグレーアウトしていればエクスポート不可です。

エクスポート不可だった場合の選択肢は 2 つです。

  • PFX を諦めてストア参照方式にする — 同じマシンで使うだけなら、これで解決します（CERTIFICATE.md の方式 A）
  • CA に「秘密鍵エクスポート可能」で再発行を依頼する — 別マシンへ持ち込む必要がある場合。ただし運用ポリシー上断られることが多い

後からエクスポート可能に変更する手段はありません。

Step 3: PFX として書き出す

$thumb = "1A2B3C4D5E6F7890ABCDEF1234567890ABCDEF12"
$pw = Read-Host -AsSecureString -Prompt "PFX のパスワード"

Export-PfxCertificate -Cert "Cert:\LocalMachine\My\$thumb" `
    -FilePath "C:\temp\server.pfx" `
    -Password $pw `
    -ChainOption BuildChain

パスワードは Read-Host -AsSecureString で入力してください。ConvertTo-SecureString -AsPlainText でスクリプトに直書きすると、PowerShell の履歴ファイルに平文で残ります。

-ChainOptionPFX に入るもの使いどころ
BuildChainサーバ証明書 + 構築できた中間/ルート CA通常はこれ。配布先でチェーンを別途入れずに済む
EndEntityCertOnlyサーバ証明書のみ配布先に既にチェーンがある場合
PfxDataOnly元の PFX の構成をそのままPFX を読み直して再出力する場合

BuildChain はそのマシンでチェーンを構築できることが前提です。中間 CA がマシンに入っていないと、サーバ証明書だけの PFX ができてしまいます。書き出したあと 7 章で必ず中身を確認してください。

GUI で行う場合

certlm.msc を開き、「個人」→「証明書」→ 対象を右クリック →「すべてのタスク」→「エクスポート」

「はい、秘密キーをエクスポートします」を選択（グレーアウトしていたらエクスポート不可）

形式は「Personal Information Exchange - PKCS #12 (.PFX)」を選び、「証明書のパスにある証明書を可能であればすべて含める」にチェック（= BuildChain 相当）

パスワードを設定し、出力先を指定して完了

6. ケース B — OpenSSL で結合する

OpenSSL で CSR を作った場合、対になる .key が手元にあるはずです。Windows の証明書ストアは一切関係ありません。

Step 1: .cer の形式を確認する

OpenSSL は PEM 形式（-----BEGIN CERTIFICATE----- で始まるテキスト）を前提にします。CA から DER 形式（バイナリ）で渡されることもあるため、先に確認します。

# PEM ならそのまま読める
openssl x509 -in server.cer -noout -subject

# 上が失敗したら DER。PEM へ変換する
openssl x509 -inform der -in server.cer -out server.pem

Step 2 & 3: 秘密鍵と結合し、チェーンを同梱する

openssl pkcs12 -export \
    -out server.pfx \
    # 秘密鍵
    -inkey server.key \
    # サーバ証明書 (PEM)
    -in server.cer \
    # 中間 CA (+ ルート)。複数ある場合は 1 ファイルに連結しておく
    -certfile chain.crt

実行するとエクスポート用のパスワードを聞かれます。.key にパスフレーズが掛かっている場合は、そちらも先に聞かれます。

中間 CA が複数ある場合は、1 つのファイルに連結してから -certfile に渡します。順序は「下位 → 上位」です。

cat intermediate.crt rootCA.crt > chain.crt

コマンドラインにパスワードを書かないでください。-passout pass:xxxx はシェル履歴とプロセス一覧に平文で残ります。対話入力か、どうしても自動化が必要なら -passout file:<path> を使い、そのファイルは直後に削除してください。

Windows で読めない PFX ができたら

OpenSSL 3.x が既定で使う暗号化方式（AES-256-CBC + PBKDF2）は、古い Windows の証明書インポート機能が読めないことがあります。「パスワードが正しくありません」と言われるのに合っている、という症状が出たらこれです。

# 旧来の方式で書き出す (OpenSSL 3.x)
openssl pkcs12 -export -out server.pfx \
    -inkey server.key -in server.cer -certfile chain.crt \
    -legacy

.NET 8 以降で読む分には既定のままで問題ありません。-legacy が必要になるのは、古い Windows の GUI や旧バージョンのツールに読ませる場合です。

7. 作った PFX を検証する

配布する前に必ず中身を確認してください。特に「中間 CA が入っているか」は見落としやすく、入っていないと配布先で証明書エラーになります。

$pw = Read-Host -AsSecureString -Prompt "PFX のパスワード"
$data = Get-PfxData -FilePath "C:\temp\server.pfx" -Password $pw

# サーバ証明書 (1 枚のはず)
$data.EndEntityCertificates | Select-Object Subject, DnsNameList, NotAfter, HasPrivateKey

# 同梱されたチェーン。ここが空なら中間 CA が入っていない
$data.OtherCertificates | Select-Object Subject
確認項目期待する値違ったときは
HasPrivateKeyTrue秘密鍵が入っていない。手順をやり直す
DnsNameList (SAN)接続に使うホスト名を含む証明書自体が用途に合っていない。再発行が必要
NotAfter十分先の日付期限切れ間近。更新を検討
OtherCertificates中間 CA が並ぶ空なら配布先でチェーンエラー。5 章の -ChainOption BuildChain / 6 章の -certfile を確認

OpenSSL で確認する場合はこちらです。

# 秘密鍵を出力せずに中身だけ見る (-nokeys が重要)
openssl pkcs12 -in server.pfx -nokeys -info

openssl pkcs12 -in server.pfx -nodes は秘密鍵を平文で画面に出力します。確認目的なら必ず -nokeys を付けてください。うっかり実行すると、ターミナルのスクロールバッファやログに秘密鍵が残ります。

8. 取り扱いの注意

.pfx は秘密鍵入りのファイルです。これ 1 つが漏れると、そのホスト名を騙る通信が可能になります。.cer とは扱いのレベルが根本的に違います。

項目やること
パスワード強い値にし、PFX 本体とは別経路で渡す。設定ファイルに平文で書かない
置き場所共有フォルダ・OneDrive 同期フォルダ・チャットへの添付は避ける
ファイル権限サービスアカウントと Administrators のみ読み取りに絞る
作業後中継用にコピーした PFX は使い終わったら削除する
バックアップ取る場合もパスワード保護のまま。復号して保管しない
 
:: 継承を切って SYSTEM と Administrators だけに読み取りを許可
icacls "C:\Apps\Watashi\server.pfx" /inheritance:r /grant "SYSTEM:R" /grant "Administrators:R"

9. Watashi での設定

作った PFX を使う場所は 2 つあります。どちらもパスワードは環境変数で渡すのが安全です。

Agent の HTTPS 待受 (Kestrel)

"Kestrel": {
  "Endpoints": {
    "Https": {
      "Url": "https://0.0.0.0:8443",
      "Certificate": {
        "Path": "C:\\Apps\\Watashi\\server.pfx",
        "Password": ""
      }
    }
  }
}

mTLS のクライアント証明書

中央サーバが Agent へ接続する際に提示する証明書です。

"Routing": {
  "UseMtls": true,
  "ClientCertificatePath": "C:\\Apps\\Watashi\\client.pfx",
  "ClientCertificatePassword": ""
}

Agent 側が中央へ提示する証明書は Certificate:Path / Certificate:Password です。

パスワードを設定ファイルに書かない

setx Kestrel__Endpoints__Https__Certificate__Password "<password>" /M

環境変数は設定ファイルより優先されます。反映にはサービスの再起動が必要です。

同じマシンで使うだけなら、PFX ではなくストア参照方式を検討してください。パスワード管理が不要になり、証明書更新時も appsettings.json の変更が要りません。比較表は CERTIFICATE.md にあります。

10. トラブル対応

「はい、秘密キーをエクスポートします」がグレーアウトする

エクスポート不可で発行された証明書です。後から可能にする手段はありません。ストア参照方式に切り替えるか、CA へエクスポート可能での再発行を依頼してください（5 章 Step 2）。

Export-PfxCertificate がアクセス拒否になる

管理者権限で実行しているか確認してください。LocalMachine ストアの秘密鍵は管理者権限が必要です。専用サービスアカウントで運用している場合は、秘密鍵への読み取り権限も確認してください。

PFX のインポートで「パスワードが正しくありません」と言われる

パスワードが合っているのにこれが出る場合、OpenSSL 3.x の既定の暗号化方式を読めていない可能性があります。-legacy を付けて作り直してください（6 章）。

配布先でチェーンエラーになる

PFX に中間 CA が入っていません。7 章の OtherCertificates が空になっているはずです。-ChainOption BuildChain / -certfile を付けて作り直すか、配布先のマシンに中間 CA を直接インポートしてください。

certutil -addstore CA C:\temp\intermediateCA.cer

Kestrel が PFX を読めずに起動しない

  • Path のバックスラッシュを \\ でエスケープしているか
  • ファイルが存在し、サービス起動アカウントに読み取り権限があるか
  • パスワードが環境変数と設定ファイルで食い違っていないか（環境変数が優先されます）

certutil -store My に証明書はあるが「秘密キーがあります」が無い

証明書だけ取り込まれて鍵との紐付けが切れています。修復できる場合があります。

certutil -repairstore My "拇印をスペース無しで"
