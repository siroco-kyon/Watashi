Win-ACME 証明書取得ガイド

どのスクリプトを、どのマシンで、どの順番で実行するのかだけに絞った手順書です。ACME サーバへ到達できない Agent に対して、別マシンで PFX を代理取得して届ける方法を中心に説明します。

0. 先に結論

おおむね その理解で合っています

「普通に PFX を取得して、対象サーバに持っていくだけ」で正しいです。Watashi の Agent 側の設定 (appsettings.json) は、自分で取ろうが代理で取ろうがまったく同じです。PFX はただのファイルなので、置いてサービスを再起動すれば動きます。

ただし ハマるポイントが 2 つだけあります。ここを知らずに始めると必ず止まります。

落とし穴 ①: 検証方式を HTTP-01 のままにすると代理取得できません。
HTTP-01 は「CA が http://agent-b.internal/.well-known/... に取りに来る」方式なので、そのホスト名で外から到達できるマシン自身で wacs.exe を動かす必要があります。代理マシン (Agent A) で実行しても、CA は A ではなく B を見に行くため必ず失敗します。代理取得では DNS-01 検証 (TXT レコード) に変更が必須です。

落とし穴 ②: 「持っていく」のは初回だけでは済みません。
証明書は 60〜90 日で失効し、win-acme が自動更新します。更新されるのは代理マシン側の PFXなので、更新のたびに B へコピーし直さないと B は古い証明書のまま期限切れになります。この「更新 → コピー → B のサービス再起動」を無人化するのが deploy-pfx-to-remote-agent.ps1 です。

代理取得で変わるのはこの 5 行だけ

2. どのパターンに当てはまるか

判定基準はひとつだけ、「その Agent 自身が社内 ACME CA と通信できるか」です。

証明書を入れたい Agent は… ┌─ その Agent 自身から CA (ACME URL) に HTTPS で到達できる？ │ ├── YES ──┬─ CA → Agent の TCP 80 も通る？ │ │ │ ├── YES → 【パターン1】その Agent で register-agent-acme.ps1 │ │ （HTTP-01 検証・いちばん簡単） │ │ │ └── NO → 【パターン2】DNS-01 検証にする │ （その Agent 自身で取ってもよいし、代理でもよい） │ └── NO ───┬─ DNS の TXT レコードを自動登録できる？ │ ├── YES → 【パターン2】代理マシンで取得 → PFX を配布 ★本命 │ └── NO → 【パターン3】CA から通常発行 (手動更新運用)
パターン1
自分で取得		パターン2
代理取得 + 配布		パターン3
ACME を使わない
前提Agent ⇔ CA が疎通
CA → Agent:80 が疎通		代理マシンが CA と疎通
DNS-01 が使える		社内 CA に CSR / GUI 発行の窓口がある

区間ごとに別パターンでも構いません。Server → Agent A はパターン1、Agent A → Agent B はパターン2、という混在が実際いちばん多い構成です。http / https も区間ごとに独立して選べるので段階移行できます。

3. パターン1: Agent 自身で取得する (基本形)

まずこちらを理解しておくと、パターン2 は「実行場所と後処理が違うだけ」として読めます。

実行マシン: 証明書をもらう Agent 自身
スクリプトを配置: after-renew.ps1 と register-agent-acme.ps1 を C:\ProgramData\WatashiAgent\scripts\ へコピー。
PFX パスワードを決める: 自分で決める任意の値です (CA から与えられるものではありません)。長いランダム文字列にし、後で appsettings.json に同じ値を書きます。
ラッパーを実行して win-acme に登録。
appsettings.json を Https に変更してサービス再起動 → 6章。
中央サーバのノード Endpoint を https://… に変更 → 疎通確認。

3-1. 取得コマンド

cd C:\ProgramData\WatashiAgent\scripts

.\register-agent-acme.ps1 `
    -WacsPath  "C:\tools\win-acme\wacs.exe" `
    -AcmeUrl   "https://ca.internal/acme/directory" `
    -HostName  "agent-a.internal" `
    -PfxPassword (Read-Host -AsSecureString "PFX パスワード")

スクリプトが内部で叩いているのは次のコマンドです。手動で実行したい場合やオプションを足したい場合の参考に:

wacs.exe --source manual --host agent-a.internal `
    --baseuri https://ca.internal/acme/directory `
    --store pfxfile `
    --pfxfilepath C:\ProgramData\WatashiAgent\certs\ `
    --pfxpassword "<決めたパスワード>" `
    --installation script `
    --script "C:\ProgramData\WatashiAgent\scripts\after-renew.ps1" `
    --accepttos
オプション意味
--source manual --hostIIS のサイトからではなく、ホスト名を直接指定して証明書を要求する。Agent には IIS が無いのでこれを使う
--baseuri社内 ACME CA のディレクトリ URL
--store pfxfileWindows 証明書ストアではなく PFX ファイルとして出力する。Kestrel はファイルを直接読めるのでこれが最短
--pfxfilepath / --pfxpassword出力先フォルダと、自分で決めるパスワード
--installation script --script更新に成功した直後に実行するフック。ここでサービスを再起動しないと Kestrel は古い証明書を掴んだまま
--accepttos利用規約への同意 (無人実行に必要)
成功すると C:\ProgramData\WatashiAgent\certs\agent-a.internal.pfx が生成され、タスクスケジューラに win-acme renew タスクが登録されます。以後の更新は無人です。

PFX のファイル名は win-acme のバージョンで変わります。dir C:\ProgramData\WatashiAgent\certs\ で実際の名前を必ず確認してから appsettings.json に書いてください。バージョンによっては --pfxfilename でファイル名を固定できます。

既定の検証は HTTP-01 (selfhosting) で、win-acme が検証中だけ TCP 80 に一時リスナーを立てます。Agent の 8081 とはぶつかりません。CA → Agent の 80 番が閉じている場合は、パターン2 と同じ DNS-01 検証に切り替えれば、取得マシンは Agent 自身のままで構いません。

4. パターン2: 代理で取得して PFX を届ける ★本題

チェーン構成 (Server → Agent A → Agent B → CIFS) の Agent B のように、隔離セグメントにいて CA と通信できない Agent が対象です。

① DNS-01 で B の証明書を要求 ② PFX をコピー ┌──────────────┐ ┌──────────────┐ ┌──────────────┐ │ 社内 ACME CA │ ◄────────── │ Agent A │ ───► │ Agent B │ └──────┬───────┘ │ (代理取得) │ │ (隔離) │ │ └──────┬───────┘ └──────┬───────┘ │ TXT を確認 │ │ ▼ │ ③ サービス再起動 │ ┌──────────────┐ └─────────────────────►┘ │ 社内 DNS │ ◄── TXT 登録 ───────┘ │ _acme-challenge.agent-b.internal └──────────────┘ ※ B は CA とも DNS 登録とも一切通信しない。B が受け取るのは「PFX ファイル」だけ。

なぜ DNS-01 なのか。ACME の所有確認には「そのホスト名を本当に持っているか」を示す必要があります。HTTP-01 は そのホスト名の 80 番に置いたファイルで示すので、実行マシン = 検証対象マシンでなければなりません。DNS-01 は DNS の TXT レコードで示すため、どのマシンから要求しても構いません。これが代理取得が成立する唯一の理由です。

4-0. 事前に用意するもの

項目内容
代理マシンCA (ACME URL) に到達でき、かつ B の管理共有に書き込めるマシン。通常は Agent A
DNS-01 の手段_acme-challenge.agent-b.internal の TXT レコードを自動で登録・削除できること (Windows DNS + RSAT、または CA/DNS ベンダのプラグイン)
B への書き込み\\agent-b\C$ (管理共有) への書き込み権限
B のサービス再起動WinRM (推奨) または RPC (sc.exe \\agent-b)。配布スクリプトは WinRM を試して失敗したら sc.exe にフォールバックします
ルート CA の信頼B の証明書を検証するのは Agent A です。社内 CA のルート証明書が A の「信頼されたルート証明機関 (LocalMachine)」に入っていること
ホスト名--host に書く名前 = ノード Endpoint に書く名前 = A から名前解決できる名前。中央サーバから解決できる必要はありません

いちばん多い詰まり方: 更新タスクの実行アカウント。
win-acme の更新タスクは既定で SYSTEM として動きます。SYSTEM がネットワーク越しに \\agent-b\C$ を触るときの資格情報はコンピュータアカウント (DOMAIN\AGENT-A$) であり、これは普通 B の管理者ではありません。手で実行したときは通ったのに自動更新時だけ配布が失敗する、という形で表面化します。対処は次のどちらか:

  • タスクスケジューラで win-acme renew タスクの実行ユーザーを、B の管理者権限を持つドメインサービスアカウントに変更する (推奨)
  • DOMAIN\AGENT-A$ を B のローカル Administrators に追加する

4-1. まず配布スクリプトを単体で試す

ACME を絡める前に、「PFX を置いて再起動する」部分だけが通ることを確認します。ここが通れば残りは自動化するだけです。

実行マシン: Agent A (代理取得側) 
# 動作確認用にダミーでも実物でもよいので PFX を用意して実行
.\deploy-pfx-to-remote-agent.ps1 `
    -PfxPath      "C:\ProgramData\WatashiAgent\certs\agent-b.internal.pfx" `
    -ComputerName "agent-b" `
    -HealthUrl    "https://agent-b.internal:8081/health"

このスクリプトが行うのは次の 3 つだけです。中身が分かっていれば手作業でも同じことができます。

#処理手作業でやるなら
1PFX を管理共有経由でコピーCopy-Item C:\...\agent-b.internal.pfx \\agent-b\C$\ProgramData\WatashiAgent\certs\
2リモートのサービス再起動
(WinRM → だめなら sc.exe)		Invoke-Command -ComputerName agent-b { Restart-Service Watashi.Agent -Force }
3/health の応答確認 (任意)curl.exe -k https://agent-b.internal:8081/health
パラメータ既定値説明
-PfxPath(必須)配布元 PFX のローカルパス
-ComputerName(必須)配布先の Agent サーバ名
-RemotePfxDirC:\ProgramData\WatashiAgent\certs配布先フォルダ (リモート上のローカルパス表記)。内部で \\<名前>\C$\… に変換される
-ServiceNameWatashi.Agent再起動するリモートのサービス名
-HealthUrl(空)指定すると配布後に応答確認。ホスト名検証はスキップし、応答の有無だけ見る
-LogPathC:\ProgramData\WatashiAgent\logs\cert-deploy.log実行ログ。自動化後の調査はここを見る
PFX には秘密鍵が入っています。メール・チャット・共有フォルダ経由で運ばないでください。管理共有 (SMB) 経由が使えない環境で手渡しする場合も、置いた先の ACL を絞り、作業用の一時コピーは必ず削除します。
icacls "C:\ProgramData\WatashiAgent\certs\agent-b.internal.pfx" /inheritance:r /grant "SYSTEM:R" /grant "Administrators:R"

4-2. DNS-01 検証の準備

win-acme が TXT レコードを自動で登録・削除できるようにします。社内 DNS が Windows DNS サーバなら、スクリプト検証プラグイン + RSAT の DnsServer モジュールが最短です。

実行マシン: Agent A (代理取得側)

登録用スクリプト C:\ProgramData\WatashiAgent\scripts\dns-create.ps1

param([string]$Identifier, [string]$RecordName, [string]$Token)

$ErrorActionPreference = "Stop"
$zone = "internal"                       # ★ 自社の DNS ゾーン名
$dns  = "dns01.internal"                 # ★ DNS サーバ名
$name = $RecordName -replace "\.$zone$", ""   # _acme-challenge.agent-b

Add-DnsServerResourceRecord -ComputerName $dns -ZoneName $zone `
    -Name $name -Txt -DescriptiveText $Token

Start-Sleep -Seconds 30   # 伝播待ち。環境に合わせて調整

削除用スクリプト C:\ProgramData\WatashiAgent\scripts\dns-delete.ps1

param([string]$Identifier, [string]$RecordName, [string]$Token)

$ErrorActionPreference = "SilentlyContinue"
$zone = "internal"
$dns  = "dns01.internal"
$name = $RecordName -replace "\.$zone$", ""

Remove-DnsServerResourceRecord -ComputerName $dns -ZoneName $zone `
    -Name $name -RRType Txt -Force

Windows DNS 以外 (BIND、外部 DNS ベンダ、CA 側が TXT を代理登録する仕組みなど) の場合は、この 2 本の中身を各環境の登録手段に差し替えてください。win-acme から見れば「TXT を登録する / 消す」外部コマンドでしかありません。Route53・Azure DNS・Cloudflare などは win-acme に専用プラグインがあるのでそちらを使えます。

4-3. 更新後フック (B 向けラッパー) を作る

win-acme から呼ばれるフックは引数を取れないため、配布スクリプトを B 向けの引数で呼ぶだけの 1 行ラッパーを用意します。代理する Agent が複数ある場合は、この 1 行ラッパーを Agent ごとに作ります (どの証明書の更新かを取り違えないための、いちばん確実な方法です)。

C:\ProgramData\WatashiAgent\scripts\deploy-agent-b.ps1

& C:\ProgramData\WatashiAgent\scripts\deploy-pfx-to-remote-agent.ps1 `
    -PfxPath      "C:\ProgramData\WatashiAgent\certs\agent-b.internal.pfx" `
    -ComputerName "agent-b" `
    -HealthUrl    "https://agent-b.internal:8081/health"

4-4. win-acme に登録する

実行マシン: Agent A (代理取得側) 
wacs.exe --source manual --host agent-b.internal `
    --baseuri https://ca.internal/acme/directory `
    --validationmode dns-01 --validation script `
    --dnscreatescript "C:\ProgramData\WatashiAgent\scripts\dns-create.ps1" `
    --dnsdeletescript "C:\ProgramData\WatashiAgent\scripts\dns-delete.ps1" `
    --dnscreatescriptarguments "{Identifier} {RecordName} {Token}" `
    --dnsdeletescriptarguments "{Identifier} {RecordName} {Token}" `
    --store pfxfile `
    --pfxfilepath C:\ProgramData\WatashiAgent\certs\ `
    --pfxpassword "<B の appsettings.json に書くパスワード>" `
    --installation script `
    --script "powershell.exe" `
    --scriptparameters "-NoProfile -ExecutionPolicy Bypass -File C:\ProgramData\WatashiAgent\scripts\deploy-agent-b.ps1" `
    --accepttos

パターン1 と比べて変わったのは黄色の 5 行 (DNS-01 への切り替え) と、最後のフックの向き先だけです。--host は B の名前のまま、--store pfxfile も同じです。

オプション名はバージョン差があります。DNS 検証プラグインの引数名やプレースホルダ ({Identifier} {RecordName} {Token}) は win-acme のバージョンで異なることがあります。手元の実行ファイルで wacs.exe --help を確認するか、対話モード (wacs.exe をそのまま起動 → メニューから選択) で 1 度登録し、生成された %ProgramData%\win-acme\…\Renewals\<id>.renewal.json を見るのが確実です。--script "powershell.exe" --scriptparameters "-File …" の形にしているのは、実行ポリシーの影響を受けずに .ps1 を確実に起動するためです。

4-5. B 側の設定 (ここは普通の取得とまったく同じ)

実行マシン: Agent B (証明書を受け取る側)

配布された PFX を指すように appsettings.json を変更してサービスを再起動します → 6章。パスワードは 4-4 の --pfxpassword と同じ値です。B 側では win-acme も DNS も一切触りません。

4-6. 通しで確認する

強制更新: A で wacs.exe --renew --force を実行。
配布ログ: A の C:\ProgramData\WatashiAgent\logs\cert-deploy.log に「コピー完了」「サービス再起動完了」が出ているか。
B の PFX: \\agent-b\C$\ProgramData\WatashiAgent\certs\ のタイムスタンプが更新されているか。
A から疎通: .\test-agent-https.ps1 -AgentUrl https://agent-b.internal:8081 をAgent A 上で実行 (B を検証するのは A なので、中央サーバではなく A で実行するのがポイント)。
ノード Endpoint を https://agent-b.internal:8081 に変更し、クライアントツールから B 経由のホストに接続テスト。
順序に注意: ノード Endpoint の https:// 化は、必ず Agent 側の HTTPS 設定を済ませた後に行ってください。逆順にすると HTTP で待ち受けている Agent に HTTPS で繋ぎに行き、ノードが Unhealthy になります。

5. パターン3: ACME を使わずに手動配置する

DNS-01 が使えない、社内 CA が ACME 未対応、といった場合。社内 CA の通常の発行フロー (CSR 提出 / 管理 GUI) で 秘密鍵込みの PFX を受け取り、B に置くだけです。

社内 CA に agent-b.internal のサーバ証明書を PFX (秘密鍵込み) で発行依頼する。
PFX を C:\ProgramData\WatashiAgent\certs\agent-b.internal.pfx に配置 (配置と再起動は deploy-pfx-to-remote-agent.ps1 をそのまま使えます)。
appsettings.json を設定 (パスワードは発行時に指定したもの) → Restart-Service Watashi.Agent。
有効期限を台帳に記録し、期限前の再発行 → 再配置 → 再起動を運用手順に組み込む。
Watashi 側の設定は ACME で取った場合と完全に同一です。違いは更新が自動化されないことだけ。逆に言えば、ACME 化はいつでも後から差し替えられます (PFX の出どころが変わるだけで、B は何も変わらないため)。

参考: どうしても HTTPS 化が難しい区間

Server → Agent A だけ HTTPS 化し、Agent A → Agent B は http:// のまま運用することもできます。A/B 間が物理的・論理的に隔離された専用セグメントで、セキュリティポリシー上許容できる場合の選択肢です。認証は全区間とも共有秘密 (X-Watashi-Secret) のままなので、暗号化の有無だけの差になります。

6. Agent の appsettings.json (全パターン共通)

ファイル位置: C:\Program Files\Watashi\Agent\appsettings.json

変更前 (HTTP)

"Kestrel": {
  "Limits": { "MaxRequestBodySize": 10737418240 },
  "Endpoints": {
    "Http": { "Url": "http://0.0.0.0:8081" }
  }
}

変更後 (HTTPS)

"Kestrel": {
  "Limits": { "MaxRequestBodySize": 10737418240 },
  "Endpoints": {
    "Https": {
      "Url": "https://0.0.0.0:8081",
      "Certificate": {
        "Path": "C:\\ProgramData\\WatashiAgent\\certs\\agent-b.internal.pfx",
        "Password": "<--pfxpassword と同じ値>"
      }
    }
  }
}
  • Http ではなく Https というキー名ごと変える (キー名で待ち受け方式が決まります)
  • パスの区切りは JSON なので \\ と二重に書く
  • PFX のファイル名は dir で実際の名前を確認してから貼る
  • パスワードをファイルに書きたくない場合は環境変数で上書き可:
    setx Kestrel__Endpoints__Https__Certificate__Password "<password>" /M

変更したらサービスを再起動し、ローカルで待ち受けを確認します。

Restart-Service Watashi.Agent

curl.exe -k https://localhost:8081/health
# {"status":"ok","at":"..."} が返れば Kestrel の HTTPS 化は完了
# -k は localhost とのホスト名不一致を無視するため。ローカル確認時のみ使用

変更しないもの

設定そのままにする理由
Routing:UseMtls両側とも false のまま。ここで行うのは TLS 暗号化だけで、mTLS は使いません
Auth:SharedSecret / Routing:SharedSecret認証は引き続き共有秘密が担当します。証明書は暗号化のみの担当
Agent の Certificate:Pathこれは Agent が外向きに提示するクライアント証明書欄です。サーバ証明書とは別物なので空のまま

7. 自動更新が回る仕組み

パターン1 (自分で取得) タスクスケジューラ win-acme renew (毎日)
→ ① CA に更新要求 (HTTP-01)
→ ② PFX を上書き
→ ③ after-renew.ps1 でローカル再起動
パターン2 (代理取得) タスクスケジューラ win-acme renew (A 上, 毎日)
→ ① CA に更新要求 (DNS-01)
→ ② A の PFX を上書き
→ ③ deploy-agent-b.ps1 → B へコピー + B を再起動
  • appsettings.json は固定パス + 固定パスワードを指しているため、更新のたびの設定変更は不要です
  • ③ の再起動で数秒のサービス断が起きます。実行中のファイル転送がその瞬間に当たると失敗するため、更新タスクの実行時刻は業務時間外に設定してください (タスクスケジューラで win-acme renew のトリガー時刻を変更)
  • Kestrel は起動時にしか PFX を読みません。フックを外すと、証明書は新しくなっているのに Agent は期限切れの古い証明書を出し続ける、という一番厄介な壊れ方をします
  • 動作確認は wacs.exe --renew --force。PFX のタイムスタンプ更新と、ログ (cert-renew.log / cert-deploy.log) を確認します
期限切れは静かに来ます。代理取得はフックの経路が長い (A の更新 → コピー → B の再起動) ぶん、どこか 1 箇所が黙って失敗すると気づけません。四半期に一度でよいので test-agent-https.ps1 を回して、有効期限が伸びているかを目視確認する運用をおすすめします。

8. 動作確認

接続する側のマシンで test-agent-https.ps1 を実行します。どちらから繋ぐ区間かで実行マシンが変わる点に注意してください。

確認したい区間実行するマシンコマンド
Server → Agent A中央サーバ.\test-agent-https.ps1 -AgentUrl https://agent-a.internal:8081
Agent A → Agent BAgent A.\test-agent-https.ps1 -AgentUrl https://agent-b.internal:8081

スクリプトは 4 段階で切り分けます。どこで NG になったかがそのまま原因の切り分けになります。

段階NG のときに疑うところ
1/4 TCP 接続Agent サービスが起動していない / ファイアウォールで 8081 が閉じている
2/4 TLS + 証明書検証NameMismatch → 証明書のホスト名と接続先名の不一致。ChainErrors → 実行マシンでルート CA が未信頼
3/4 証明書の内容Subject / SAN / 有効期限 / 発行者を目視確認。更新が回っているかもここで分かる
4/4 GET /healthTLS は張れているがアプリが応答しない。Agent のログを確認
すべて OK になったら、中央サーバの管理画面 → ノード管理で Endpoint を http://…:8081 から https://…:8081 に変更し、最後にクライアントツールからそのノード経由のホストに「接続テスト」を実行してファイル一覧が取得できることを確認してください。

9. トラブル対応

代理取得まわり

症状原因と対処
代理マシンで実行したら検証が失敗するHTTP-01 のままになっています。CA は代理マシンではなく B の 80 番を見に行くため、原理的に通りません。--validationmode dns-01 に変更してください
TXT レコードが見つからない / 検証がタイムアウトDNS の伝播待ちが足りない (dns-create.ps1 の Start-Sleep を延ばす)。Resolve-DnsName -Type TXT _acme-challenge.agent-b.internal で実際に引けるか確認
手動実行では配布できるのに、自動更新時だけ失敗する更新タスクの実行アカウントです。SYSTEM 実行だとネットワーク先へはコンピュータアカウントで行くため、B の管理共有に弾かれます → 4章の警告
\\agent-b\C$ にアクセスできない管理共有の無効化、ファイアウォール (SMB 445)、ワークグループ環境での UAC リモート制限などを確認
コピーはできたが B のサービスが再起動されないWinRM が無効で sc.exe にもフォールバックできていない。cert-deploy.log にどちらで失敗したか出ています。Enable-PSRemoting -Force を B で実行するのが早道
B が更新後も古い証明書で応答するコピー先パスと appsettings.json の Path がずれている (別ファイルを更新している)。B 上で PFX のタイムスタンプを確認
