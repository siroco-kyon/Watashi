Watashi troubleshooting guide

初回パスワード設定が
動かないときの切り分け

Windows 統合認証にならず、パスワードを設定していないのにパスワード入力画面が出る — この症状は原因が 8 通りあり、画面には何も表示されません。ランタイム更新や IIS 構成変更のあとに再発しやすい落とし穴を、切り分け手順つきでまとめます。

0. 症状と結論

これは異常動作ではありません

パスワード画面が出るのは「Windows 認証による判定に失敗したとき」の既定動作です。クライアントは失敗理由を一切表示せず、黙って通常のパスワードログインへ切り替えます。

したがって画面を見ても原因は分かりません。切り分けは必ず HTTP ステータスを取るところから始めてください。

ランタイム更新 (.NET のバージョン上げ) や IIS 構成変更の直後に再発したなら、まず 4 章の場所別 Location 問題を疑ってください。「昨日まで動いていたのに突然」というパターンはほぼこれです。復旧は configure-iis-windows-auth.ps1 の再実行だけで済みます。

このページは動かなくなったときの切り分け専用です。初回導入の手順は IIS-WINDOWS-AUTH-SETUP.html を参照してください。

1. なぜ画面から原因が分からないのか

クライアントの PrepareLoginAsync は、あらゆる失敗を握りつぶして「パスワードモード」を返します。ドメイン非参加 PC や旧サーバーでも画面が進むようにするための意図的な実装ですが、副作用として障害時の原因が完全に隠れます。

// Watashi.Client/Services/ApiClient.cs
var fallback = new PrepareLoginResponse { Mode = LoginModes.Password };
try
{
    using var res = await http.PostAsJsonAsync("api/auth/win/prepare-login", ...);
    if (!res.IsSuccessStatusCode) return fallback;   // 404 / 401 / 403 を全部握りつぶす
    return await res.Content.ReadFromJsonAsync<PrepareLoginResponse>(...) ?? fallback;
}
catch
{
    return fallback;                                // 通信例外も握りつぶす
}

2. 初回設定画面が出るために必要な条件

以下のすべてを満たす必要があります。1 つでも欠けるとパスワード画面になります。

#条件外れたときの応答確認方法
1Auth:WindowsAuth:Mode が None でない404 (エンドポイント未登録)配置済み appsettings.json
2Mode がホスティング方式と一致
(IIS ホスト→IIS / Kestrel 直受け→Negotiate)		401同上
3IIS で /api/auth/win に Windows 認証が届く401 または 4043 章
4接続が HTTPS (または AllowHttp=true)403接続先 URL
5OS アカウント名 == Watashi ユーザー名200 だが Mode=Passwordwhoami
6ドメイン部が許可されている200 だが Mode=Passwordwhoami
7DB 上で IsPasswordSetupPending = true200 だが Mode=Password管理画面のパスワード状態
8設定受付期限内・ロック/無効でない200 だが Mode=Password管理画面

1〜4 は「サーバーに届いていない」系、5〜8 は「届いたが本人と認められない」系です。境目は HTTP ステータスが 200 かどうかで、切り分けの分岐点もそこになります。

3. 切り分けフロー

画面を見ても分からない以上、HTTP ステータスを取るのが唯一の入口です。2 つのリクエストで原因がほぼ確定します。

Step 1: 前提確認

curl.exe -i https://watashi.internal/health

{"status":"ok",...} が返れば、ベース URL・web.config・aspNetCore ハンドラー・アプリ起動はすべて正常です。ここが 404 ならサイト構成側の問題で、Windows 認証の話ではありません。サブアプリ配置ならパス接頭辞 (/Watashi/...) が必要な点も確認してください。

Step 2: 症状が出ているクライアント PC から prepare-login を叩く

try {
    (Invoke-WebRequest -Uri "https://watashi.internal/api/auth/win/prepare-login" `
        -Method POST -UseDefaultCredentials -UseBasicParsing `
        -ContentType "application/json" -Body '{"username":"自分のGID"}').StatusCode
} catch {
    $_.Exception.Response.StatusCode.value__
}

必ず症状が出ている本人の PC・本人のログオンセッションで実行してください。Windows 統合認証はログオン中の OS アカウントを使うため、管理者が自分の PC から叩くと別人として判定され、結果が変わります。

4. 最頻出の原因 — 場所別 Location 設定

旧版の設定スクリプトが <サイト名>/api/auth/win という場所別 Location を作っていました。これが残っていると、環境によっては IIS がそのパスを ASP.NET Core アプリに渡さず、静的ファイルとして探しにいきます。

なぜ「今まで動いていたのに突然」起きるのか

この場所別 Location は、作られた時点では必ずしも問題を起こしません。ハンドラーの解決結果が環境依存だからです。以下が引き金になります。

旧版スクリプトが <location path="Watashi.Server/api/auth/win"> を作成する。この時点では aspNetCore ハンドラーが選ばれていて正常に動作している。

.NET ランタイム / ASP.NET Core Hosting Bundle を更新する。インストーラーが AspNetCoreModuleV2 を再登録し、applicationHost.config のモジュール・ハンドラー登録を書き換える。

その場所別 Location 配下で aspNetCore が継承されなくなり、StaticFile が選ばれるようになる。

/api/auth/win/* だけが 404.0 になる。クライアントは握りつぶしてパスワード画面へ。利用者からは「突然 Windows 認証が効かなくなった」ように見える。

引き金はランタイム更新に限りません。IIS のサイト再作成、Hosting Bundle の修復インストール、Windows Update による IIS コンポーネント更新でも同じことが起こり得ます。「IIS 構成を触ったあとに Windows 認証が効かない」と感じたら、まずこれを疑ってください。

確認コマンド

Import-Module WebAdministration
(Get-WebConfigurationLocation -PSPath "IIS:\").Path

出力に Watashi.Server/api/auth/win（実際のサイト名/api/auth/win）が含まれていれば原因確定です。5 章へ進んでください。

5. 復旧手順

最新版の configure-iis-windows-auth.ps1 は、旧版が作った場所別 Location の撤去に対応しています。再実行するだけで復旧します。

Step 1: 空振り確認

powershell -ExecutionPolicy Bypass -File .\deploy\configure-iis-windows-auth.ps1 `
    -SitePath "Watashi.Server" -AppPoolName "Watashi.Server" -WhatIf

サイト名・アプリプール名は IIS マネージャーの実際の表示名に合わせてください。サイト配下のアプリとして配置している場合は -SitePath "Default Web Site/Watashi" のように書きます。

Step 2: 本実行

powershell -ExecutionPolicy Bypass -File .\deploy\configure-iis-windows-auth.ps1 `
    -SitePath "Watashi.Server" -AppPoolName "Watashi.Server"

Step 3: 確認

:: 場所別 Location が消えたか
powershell -Command "Import-Module WebAdministration; (Get-WebConfigurationLocation -PSPath 'IIS:\').Path"

:: クライアント PC から疎通確認 (200 か 401 が返れば経路は復旧)
curl.exe -i --negotiate -u : https://watashi.internal/api/auth/win/whoami

実行前に自動でバックアップが取られます（Watashi-WindowsAuth-<日時>）。問題があれば Restore-WebConfiguration -Name "<バックアップ名>" で戻せます。

スクリプトが「認証以外の設定が残っているため自動削除できません」で停止した場合、それは安全装置です。旧 Location に誰かが別の設定（リダイレクト規則、MIME、圧縮設定など）を書いています。バックアップを保持したまま、IIS マネージャーでその Location の中身を確認し、必要な設定をアプリの Location 側へ移してから再実行してください。

最後にアプリケーションプールが再起動されます。瞬断が困る時間帯なら -SkipAppPoolRestart を付けて実行し、あとで手動で再起動してください。再起動しないと設定が反映されません。

6. スクリプトは何をしているのか

誤解されやすい設計なので、中身を明示しておきます。

#やること実体
1IIS 役割サービス Web-Windows-Auth の確認・導入Install-WindowsFeature
2IIS 構成のバックアップBackup-WebConfiguration
3サイト単位で匿名認証と Windows 認証を両方有効化Set-WebConfigurationProperty -PSPath "IIS:\" -Location <サイト名>
4旧版が作った場所別 Location を撤去Clear-WebConfiguration → 空なら Remove-WebConfigurationLocation
5検証してアプリプール再起動両方 enabled か / 旧 Location が消えたか

なぜサイト全体に Windows 認証を有効化するのか

手順 3 は一見おかしく見えます。「初回設定 API だけに効かせたいのに、なぜサイト全体？」— これが正解です。

  • 匿名認証も有効のまま残す → 通常 API・ClickOnce 配布ページは匿名で到達できる
  • Windows 認証も有効にする → クライアントが Negotiate を要求されたときに応答できる状態を作る
  • 「どのパスで Windows 認証を必須にするか」はアプリが決める → WindowsSetup 認可ポリシーが /api/auth/win/* にだけ適用される

つまり IIS は「使える状態にする」だけで、範囲の限定はアプリの責務という分担です。IIS 側でパスを絞ろうとしたのが旧版のミスであり、4 章の 404 の根本原因です。

なぜ web.config ではなく applicationHost.config に書くのか

system.webServer/security/authentication は既定でサーバーレベルにロックされているため、web.config に書くと 500.19 になります。スクリプトが -PSPath "IIS:\" -Location <サイト名> の形で applicationHost.config 側へ書いているのはこのためで、ロック解除は不要になります。

この設定は applicationHost.config に保存されるため、Watashi を再発行（publish）しても維持されます。publish のたびに実行し直す必要はありません。

7. 200 が返ったあと — whoami の読み方

経路が正常なのにパスワード画面が出る場合、原因は本人確認の中身です。診断エンドポイントで一発で分かります。

whoami は Auth:WindowsAuth:EnableDiagnostics が true のときだけ有効です。これが false だと whoami だけが 404 になります（prepare-login は生きている）。切り分けの際はこの違いに注意してください。

症状が出ているクライアント PC のブラウザで開きます。

https://watashi.internal/api/auth/win/whoami
{
  "rawAccountName": "CORP\\G012345",
  "normalizedName": "G012345",
  "domain": "CORP",
  "domainAllowed": true,
  "watashiUserExists": true,
  "isPasswordSetupPending": false,
  "windowsAuthMode": "IIS"
}
フィールド異常値意味と対処
rawAccountNamenull / 空ハンドシェイクは通ったが ID が取れていない。IIS の Windows 認証設定を確認
normalizedName入力する ID と違うOS アカウント名と Watashi ユーザー名の不一致。ログイン画面にはこの値と同じものを入力する必要がある（大文字小文字とドメイン部は無視される）
domainAllowedfalseDomainMatch=AllowList なのに AllowedDomains が空か不一致。空のままだと全て拒否される
watashiUserExistsfalseその名前のユーザーが DB に無い。管理画面で作成する
isPasswordSetupPendingfalseDB 上は「設定済み」扱い。パスワード画面が正しい動作。管理画面のパスワードリセットで「設定待ち」に戻せる
windowsAuthModeNoneそもそも機能が無効。appsettings.json を修正

初期管理者アカウントは isPasswordSetupPending = false で作られます。ブートストラップで作成した管理者でログインしようとしている場合、パスワード画面が出るのは正しい動作です。既知の初期パスワードでログインしてください。

8. 更新作業のチェックリスト

この症状は「更新作業のあと」に出ます。以下を作業手順に組み込んでおくと再発に気づけます。

.NET ランタイム / Hosting Bundle を更新したとき

curl.exe -i https://watashi.internal/health で 200 を確認

curl.exe -i https://watashi.internal/api/auth/win/whoami で 404 でないことを確認（401 なら経路は生きている）

404 なら 4 章 → 5 章。configure-iis-windows-auth.ps1 を再実行

アプリが動作するランタイムバージョンが引き続き導入されているか確認（新しい Hosting Bundle を入れても、アプリのターゲットに合うランタイムは別途必要）

publish で入れ替えたとき

dotnet publish -o <本番フォルダ> は本番の appsettings.json を上書きします。必ず publish 前にバックアップし、publish 後に本番用設定を戻してください。より安全にするなら、一度別フォルダへ publish してから必要なファイルだけを配備します。Auth:WindowsAuth セクションが巻き戻っていないか、入れ替え後に必ず確認してください。

IIS のサイトを作り直した / 物理パスを移動したとき

やったこと再実行が必要か
物理パスだけ移動（サイト名は同じ）Windows 認証設定は不要（サイト単位のため）。ただし移動先への ACL 付与は必要
サイトを作り直した / サイト名を変えたconfigure-iis-windows-auth.ps1 の再実行が必要
サイト直下からサブアプリ配置に変えた再実行に加えて、クライアントの接続先 URL にパス接頭辞が必要
 
:: 物理パス移動後の ACL 付与（パスは実際の値に合わせる）
icacls "C:\Sites\Watashi.Server" /grant "IIS AppPool\Watashi.Server:(OI)(CI)RX"

現在の IIS 構成を確認する

Import-Module WebAdministration
Get-Website | Select-Object Name, State, PhysicalPath,
    @{n='Binding';e={($_.bindings.Collection.bindingInformation) -join ', '}} | Format-List
Get-WebApplication | Select-Object Path, PhysicalPath

Get-WebApplication に何か出力されればサブアプリ配置です。その場合 API の URL にはパス接頭辞が必要になります。
