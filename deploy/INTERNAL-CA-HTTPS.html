Watashi deployment guide

社内 CA 証明書で
Watashi を HTTPS 化する

社内 CA に CSR を出して .cer ファイルを受け取ったところから、Server (IIS) と Agent (Kestrel) の両方を HTTPS で動かすまでの手順書です。CA サーバへ直接通信できない閉じたネットワークを前提にしています。

CONTENTS 0. 先に結論 1. 証明書は 3 枚ある ★ 2. 今どこで止まっているか 3. ルート CA の入手 ★ 4. サーバへ取り込む 5. 通信経路と証明書の配置 ★ 6. Server (IIS) の設定 7. Agent (Kestrel) の設定 8. 接続先 URL の切り替え 9. クライアント PC への配布 10. 失効チェックについて 11. エラー別トラブル対応

0. 先に結論

3 行でいうと

① .cer 単体では HTTPS は張れません。秘密鍵が入っていないためです。ただし CSR をそのサーバで作っているなら、秘密鍵はマシン内に残っているので certreq -accept で結合できます。

② ルート CA 証明書を .cer から取り出すことはできません。これが今いちばん詰まっている点です。ルート / 中間 CA は別のファイルとして別途入手するしかありません。

③ Agent 用の証明書がもう 1 枚必要かもしれません。Server → Agent も HTTPS なので、Agent 自身のホスト名の証明書が要ります。

0x800B010A (証明書チェーンを信頼されたルート機関に構築できませんでした) が出ている状態は、秘密鍵の問題ではありません。
秘密鍵の紐付けはできているのに、その手前のチェーン検証で止まっています。つまり「この証明書を発行した CA の証明書が、このサーバに入っていない」というだけです。3 章でルート / 中間 CA を入れれば解消します。

同時に出ている 0x80092013 (失効サーバーがオフライン) は無視して構いません。
CA サーバに到達できない環境なので当然の結果ですが、Watashi の運用には影響しません。理由は 10 章にコードの実装根拠つきでまとめています。

1. 証明書は 3 枚ある — .cer はそのうちの 1 枚

ここが最大の誤解ポイントです。証明書は階層構造をもつ別々のファイルとして存在します。手元にあるのは一番下の 1 枚だけです。

例外: もらったファイルが実はチェーン入りかもしれません。
拡張子が .cer でも中身が PKCS#7 (証明書の束) なら、その中にルート / 中間が同梱されています。次章の certutil -dump で「PKCS7」「証明書の数: 2」等と表示されたら、そのファイル 1 つで 3 章はスキップできます。

2. 今どこで止まっているか確認する

まず受け取った証明書の中身を見ます。対象サーバ で管理者権限のコマンドプロンプトから:

certutil -dump C:\path\to\server.cer

この出力から 3 つを読み取ってメモします。

見る項目何が分かるか後でどう使うか
発行者 (Issuer) の CNどの社内 CA が発行したか3 章でルート CA を探すときの検索キーワードになる
サブジェクト代替名 (SAN)この証明書が名乗れるホスト名の一覧Agent 用の証明書を追加発行してもらう必要があるかの判断材料 (5 章)
冒頭が X509 証明書: か PKCS7 か単体 1 枚か、チェーン入りの束かPKCS7 ならチェーン同梱。3 章をスキップできる

チェーン検証の状態を見る

certutil -verify C:\path\to\server.cer

-urlfetch は付けないでください。
-urlfetch は「不足している CA 証明書と CRL をネットワーク経由で取りに行く」オプションです。CA サーバに到達できない環境では必ず失敗し、本質と関係ない 0x80092013 (失効サーバーがオフライン) が大量に出てノイズになります。ローカルに入れた証明書だけでチェーンが繋がるかを見るのが、この環境での正しい検証です。

エラーコード意味対処
0x800B010Aチェーンを構築できない。発行元 CA の証明書がこのサーバに存在しない3〜4 章。今回のケースはこれ
0x800B0109チェーンは繋がったがルートが信頼されていないルート CA を Root ストアへ (4 章)
0x80092013失効サーバーがオフラインで CRL を確認できない無視してよい (10 章)
0x80092009対応する保留中の要求が見つからない秘密鍵の紐付けが切れている → 4 章の repairstore

3. ルート / 中間 CA 証明書を入手する

対象サーバから CA サーバへ通信できないので、CA 証明書を別経路で持ち込みます。一番現実的なのは、あなたが普段使っているドメイン参加 PC から取り出す方法です。ドメイン参加 PC には GPO で社内ルート CA が既に配布されているので、そこに必ずあります。

手順

手元の管理 PC

管理者 PowerShell で社内 CA 証明書を探します。検索キーワードには 2 章でメモした 発行者の CN を使います。

手元の管理 PC

出てきた PSParentPath を見て、末尾が Root ならルート CA、CA なら中間 CA です。それぞれの Thumbprint を控えます。

手元の管理 PC

Export-Certificate でファイルに書き出し、共有フォルダや USB で対象サーバへコピーします。

# 1) 社内 CA 証明書を Root / 中間 の両ストアから探す
Get-ChildItem Cert:\LocalMachine\Root, Cert:\LocalMachine\CA |
    Where-Object { $_.Subject -like "*社内CA名の一部*" } |
    Select-Object Subject, Thumbprint, NotAfter, PSParentPath | Format-List

# 2) ルート CA を書き出す (Thumbprint は 1) の出力から)
Export-Certificate -Cert Cert:\LocalMachine\Root\<ルートのThumbprint> -FilePath C:\temp\rootCA.cer -Type CERT

# 3) 中間 CA を書き出す (2 階層構成の場合のみ。無ければ不要)
Export-Certificate -Cert Cert:\LocalMachine\CA\<中間のThumbprint> -FilePath C:\temp\intermediateCA.cer -Type CERT

手元 PC にも無い / ドメイン非参加の場合は、CA 担当者に「ルート CA 証明書と中間 CA 証明書 (.cer または .p7b)」と依頼してください。CSR を出した窓口に頼めば通常すぐ出てきます。certsrv に到達できる端末があるなら、http://<CAサーバ名>/certsrv →「CA 証明書、証明書チェーン、または CRL のダウンロード」→「CA 証明書チェーンのダウンロード」で .p7b として一括取得するのが最短です。

4. 対象サーバへ取り込んで秘密鍵と結合する

対象サーバ で管理者権限で実行します。入れるストアを間違えるとチェーンが繋がりません。

:: 1) ルート CA →「信頼されたルート証明機関」ストア
certutil -addstore Root C:\temp\rootCA.cer

:: 2) 中間 CA →「中間証明機関」ストア (2 階層構成の場合のみ)
certutil -addstore CA C:\temp\intermediateCA.cer

:: 3) チェーンが繋がったか確認 (-urlfetch は付けない)
certutil -verify C:\path\to\server.cer

:: 4) サーバ証明書を秘密鍵と結合する
certreq -accept -machine C:\path\to\server.cer

:: 5) 結合できたか確認 → 「秘密キーがあります」が出れば成功
certutil -store My

3) で 0x800B010A が消えれば目的達成です。0x80092013 (失効サーバーがオフライン) は残っていて構いません。5) で「秘密キーがあります」が表示されれば、この証明書は TLS で使える状態になっています。

4) でまだ弾かれる場合は、チェーン検証を行わない経路で紐付けだけ済ませられます。-repairstore は検証をしないため、この状況の回避策として有効です。

:: 個人ストアに証明書だけ入れてから、鍵コンテナと紐付け直す
certutil -addstore My C:\path\to\server.cer
certutil -repairstore My "拇印をスペース無しで"

repairstore はサーバ側の紐付けを直すだけです。中間 CA がサーバに入っていないと、TLS ハンドシェイクでサーバが中間証明書を提示できず、クライアント側 (Watashi.Client / Agent) でチェーン検証に失敗します。1) 2) は結局必須なので、順序を入れ替えているだけと考えてください。

5. 通信経路と証明書の配置 — 何枚必要か

Watashi は通信経路が 3 本あり、それぞれで「証明書を提示する側」と「ルート CA を信頼する側」が違います。ここを整理しないと、証明書を入れたのに繋がらない状態になります。

経路証明書を提示する側ルート CA を信頼させる側設定場所
(1) Client → ServerServer (IIS バインド)全クライアント PC6 章 / 9 章
(2) Server → AgentAgent (Kestrel)Server マシン7 章
(3) Agent → ServerServer (同上)Agent マシン8 章

先に確認してください: 証明書は何枚必要ですか。
今回もらった server.cer が中央サーバのホスト名 (例 watashi.internal) だけのものなら、Agent 用にもう 1 枚 CA に発行してもらう必要があります。2 章で確認した SAN (サブジェクト代替名) に Agent のホスト名が入っているかを見てください。

  • Agent が複数台 → 台数分、または SAN に全ホスト名を入れた 1 枚
  • Agent を中央サーバと同居させている → 1 枚で足りる
  • SAN に入っていない → Agent 機で CSR を作って追加発行を依頼する

Agent 用 CSR の作成例

Agent 機で以下の INF を用意し、certreq -new で CSR を生成して CA へ提出します。

; agent-request.inf
[NewRequest]
Subject = "CN=agent01.internal"
KeyLength = 2048
KeyAlgorithm = RSA
HashAlgorithm = SHA256
MachineKeySet = True
Exportable = False
KeyUsage = 0xa0
ProviderName = "Microsoft RSA SChannel Cryptographic Provider"
RequestType = PKCS10

[Extensions]
2.5.29.17 = "{text}"
_continue_ = "dns=agent01.internal&"
_continue_ = "dns=agent01&"

[EnhancedKeyUsageExtension]
OID = 1.3.6.1.5.5.7.3.1
certreq -new agent-request.inf agent-request.req

SAN には、クライアントが実際にアクセスに使う名前をすべて入れてもらってください。FQDN・短縮名・必要なら IP。8 章で設定する接続先 URL のホスト名が SAN に無いと、証明書は正しくても検証に失敗します。

6. Server 側 (IIS ホスト) の設定

本番の Server は IIS ホストなので、Kestrel の HTTPS 設定は使いません。
In-process ホスティングでは TLS 終端を IIS が行うため、appsettings.json の Kestrel:Endpoints:Https を書いても無視されます。証明書はIIS のサイトバインドに割り当てます。

Server 機

4 章まで完了させ、証明書が LocalMachine\My に秘密鍵付きで入っている状態にする。

Server 機

IIS マネージャ → 対象サイト → バインド → 追加 → 種類 https / ポート 443 → 証明書を選択。ホスト名を指定するなら SNI にチェック。

Server 機

appsettings.json の Kestrel:Endpoints は Http のままで OK。Auth:AllowHttpForAutoLogin も本番既定の false のままにする。

IIS 側の詳細な構成 (アプリプール、Windows 認証、アップロード上限など) は IIS-HOSTING.md を参照してください。

Kestrel 直受け構成 (IIS を挟まない) にする場合のみ、appsettings.json にストア参照を書きます。書き方は次章の Agent と同じです。証明書ストア参照 / PFX ファイル指定の使い分けは CERTIFICATE.md に詳しくまとめてあります。

7. Agent 側 (Kestrel 直受け) の設定

Agent は UseWindowsService で動く独立した Windows サービスで、IIS を挟みません。したがってこちらは Kestrel に直接証明書を設定します。

Agent 機

3〜4 章と同じ手順で、ルート / 中間 CA の導入と Agent 用証明書の certreq -accept を実施する。

Agent 機

appsettings.json に Https エンドポイントと証明書ストア参照を追加する (下記)。

Agent 機

サービス起動アカウントに秘密鍵の読み取り権限を付与する。

Agent 機

サービスを再起動し、curl で HTTPS 応答を確認する。

appsettings.json

"Kestrel": {
  "Limits": { "MaxRequestBodySize": 10737418240 },
  "Endpoints": {
    "Https": {
      "Url": "https://0.0.0.0:8443",
      "Certificate": {
        "Subject": "agent01.internal",
        "Store": "My",
        "Location": "LocalMachine",
        "AllowInvalid": false
      }
    }
  }
}

Subject に CN= を付けないでください。
Kestrel は内部で X509FindType.FindBySubjectName を使い、CN 値 (Simple Name) に対する部分一致を行います。"CN=agent01.internal" と書くと「Simple Name に CN= という文字列が含まれるか」を探してしまい、必ずマッチしません。値だけを書きます。

  • 正: "Subject": "agent01.internal"
  • 誤: "Subject": "CN=agent01.internal"
  • 誤: "Subject": "CN = agent01.internal" (PowerShell の出力をそのまま貼ると陥りやすい)

秘密鍵へのアクセス権付与

Agent サービスは既定で LocalSystem 起動です。LocalSystem は大抵そのまま読めますが、社内 PKI 配布の証明書では明示的な権限付与が必要な場合があります。CNG / CAPI を自動判定して ACL を付与するコピペ用スクリプトを CERTIFICATE.md の「Step 3」に用意してあるので、そちらを使ってください。

certlm.msc の「秘密キーの管理」メニューがグレーアウトして操作できないことがあります (CNG キーで生成された証明書に多い)。その場合は GUI を諦めて PowerShell 手順で行ってください。

反映と確認

Restart-Service Watashi.Agent
curl.exe https://agent01.internal:8443/health

-k を付けずに成功すれば、証明書チェーンも含めて正しく組めています。-k が必要な状態はチェーンが繋がっていないので、4 章に戻ってください。

8. 接続先 URL の切り替え (見落としやすい)

証明書を入れただけでは通信は HTTPS になりません。接続先 URL の設定が 3 箇所あり、格納場所がそれぞれ違います。

経路設定の格納場所変更内容変更方法
(2) Server → Agent DB (Node.Endpoint) http://agent01:8081 → https://agent01.internal:8443 管理画面のノード管理から変更 (appsettings ではない)
(3) Agent → Server Agent の appsettings.json Agent:CentralUrl を実サーバの FQDN に合わせる ファイル編集 → サービス再起動
(1) Client → Server deployment.json serverUrl を実サーバの FQDN に合わせる 配布パッケージの作り直しが必要

URL のホスト名は、証明書の SAN に入っている名前と完全一致させてください。
IP アドレスや短縮名で接続すると、それが SAN に含まれていない限り証明書の検証に失敗します。「証明書は正しいのに繋がらない」の原因の大半がこれです。

deployment.json は配布時に管理者が固定する値で、利用者側からは変更できません。URL を変えるときは再配布パッケージを作り直す必要があるため、Server の FQDN は最初に確定させておくのが安全です。

9. クライアント PC へのルート CA 配布

経路 (1) のために、Watashi.Client が動く全 PC が社内ルート CA を信頼している必要があります。サーバ側が完璧でも、ここが抜けていると利用者側で接続エラーになります。

ドメイン参加 PC 通常は GPO で配布済みです。念のため 1 台で certutil -store Root を実行し、社内 CA が入っているか確認してください。
ドメイン非参加 PC 手動インポートが必須です。配布対象にこうした端末が含まれていないか、展開前に必ず洗い出してください。 
:: クライアント PC でルート CA が信頼されているか確認
certutil -store Root | findstr /i "社内CA名の一部"

:: 入っていなければ管理者権限でインポート
certutil -addstore Root C:\temp\rootCA.cer

ドメイン参加 PC で GPO 配布が反映されていない場合は、gpupdate /force または certutil -pulse で強制的に取り込めます。

10. 失効チェック (0x80092013) を放置してよい理由

CRL 配布ポイントに到達できないまま本番運用して問題ないか、Watashi のコードを確認した結果をまとめます。結論として影響ありません。

コンポーネント失効チェックの挙動根拠
IIS (Server) 自分自身のサーバ証明書の失効確認はしない 提示するだけ。TLS の仕様上そもそも行わない
Watashi.Client CRL を取りに行かない 既定の HttpClientHandler を使用。CheckCertificateRevocationList は既定値 false
Watashi.Agent CRL を取りに行かない サーバ証明書の検証は HttpClientHandler の標準検証に委譲。独自の失効チェックは実装していない
mTLS のクライアント証明書認証 明示的に X509RevocationMode.NoCheck Server / Agent 双方の AddCertificate 設定。今回のサーバ証明書とは別系統

つまり必要なのはルート CA が信頼されていることだけで、CRL 到達性は不要です。certutil -verify に 0x80092013 が残っていても、そのまま先へ進んで構いません。

長期的な改善として、証明書の CDP / AIA に書かれた URL が Server・Agent・クライアントの各セグメントから到達できるかを CA 担当者に確認してもらうのが望ましい状態です。ただし今回の HTTPS 化には必須ではないため、後回しで問題ありません。

11. エラー別トラブル対応

0x800B010A — チェーンを構築できない

発行元 CA の証明書がマシンに存在しません。3 章で入手し、4 章で Root / CA ストアへ導入してください。ルートを CA ストアに入れる、中間を Root に入れる、といった取り違えでも同じエラーになります。

0x800B0109 — ルートが信頼されていない

チェーンは繋がっているが、ルート CA が「信頼されたルート証明機関」に無い状態です。certutil -addstore Root でルート CA を導入してください。

0x80092009 — 対応する保留中の要求が見つからない

秘密鍵との紐付けが切れています。誰かが .cer をダブルクリックして個人ストアに取り込み済みだと発生しやすいです。4 章の certutil -repairstore で修復します。保留中の要求が残っているかは以下で確認できます。

certutil -store REQUEST
certutil -user -store REQUEST

マシン側に出るなら certreq -accept -machine、ユーザ側にしか出ないなら CSR をユーザコンテキストで作っています。その場合は certreq -accept -user で受け入れてから PFX 経由でマシンストアへ入れ直してください (IIS / サービスはユーザストアを見ません)。どちらにも無ければ repairstore を試し、それも駄目なら CSR の作り直しと再発行が必要です。

Kestrel 起動時 The requested certificate ... could not be found

最頻出は Subject に CN= を含めているケースです (7 章参照)。次に多いのが Store の指定違いで、IIS の証明書要求機能や Win-ACME で取得したものは My ではなく WebHosting ストアに入ります。全ストアを横断検索するには:

@("My","WebHosting","Root","CA") | ForEach-Object {
    Write-Host "=== $_ ==="
    Get-ChildItem "Cert:\LocalMachine\$_" -ErrorAction SilentlyContinue |
        Where-Object { $_.HasPrivateKey } | Select-Object Subject, Thumbprint
}

Kestrel 起動時 Access denied

秘密鍵へのアクセス権限不足です。サービス起動アカウントを確認し、そのアカウントに読み取り権限を付与してください。

sc.exe qc Watashi.Agent | findstr SERVICE_START_NAME

クライアントで証明書エラーが出る

  • クライアント PC にルート CA が入っていない → 9 章
  • 接続先 URL のホスト名が証明書の SAN に無い → 8 章
  • サーバが中間証明書を提示できていない → Server / Agent 機の CA ストアに中間 CA を導入 (4 章)

証明書の更新時

ストア参照方式なら、新しい証明書を同じ Subject でインポートし、秘密鍵の ACL を付与してサービスを再起動するだけです。appsettings.json の変更は不要です。Kestrel は Subject 一致かつ有効期限が最も遠い証明書を自動選択します。詳細な更新手順は CERTIFICATE.md にあります。
