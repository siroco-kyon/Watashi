⛩ Watashi 管理者マニュアル

管理者向け。ユーザー・ホスト・権限・ノードの管理から、監査ログ・緊急復旧まで、運用に必要な操作を網羅的に説明します。

0このガイドについて

この文書は、Watashi の管理コンソール（管理画面）を操作する管理者向けのマニュアルです。利用者（エンドユーザー）向けの操作は 利用者マニュアル を参照してください。

管理者ができること（全体像） Watashi の管理コンソールは 10個のタブで構成され、次のことを管理します。
  • 誰が使えるか：ユーザーの作成・パスワード・ロック・自動ログイン端末
  • どこに繋ぐか：CIFSファイルサーバー（ホスト）・共有・接続経路（実行ノード）
  • 誰が何をできるか：権限テンプレート × ユーザー権限（共有 × パス単位）
  • 何が起きたか：全操作の監査ログ・システム設定
すべての管理操作は監査ログに残ります ユーザー追加・削除・権限変更・設定変更など、管理者の操作はすべて ADMIN_* プレフィックスで操作ログに記録されます（→第14章）。「誰が・いつ・何を変えたか」を後から追跡できます。

1管理画面の開き方

  1. 管理者ユーザー（IsAdmin = true）でログインします。
  2. メイン画面の右上にある朱色の 管理 ボタンをクリックします。
  3. 別ウィンドウで 管理コンソール（タブ表示）が開きます。
一般ユーザーには「管理」ボタンは表示されません 非管理者には管理ボタン自体が出ないため、管理画面には入れません。管理コンソールは別ウィンドウなので、×（閉じる）でメイン画面に戻ります（Esc／戻るボタンはありません）。閉じると、権限変更の結果がメイン画面のリモート場所一覧に反映されます。

2初期セットアップの流れ

新しいCIFS共有を利用者に使わせるまでの典型的な順番です。上から順に進めると迷いません。

③の接続テストは必ず実施 ホストを登録したら、共有を1つ登録してから接続テストを行います。ここで失敗を早期に発見できれば、ユーザーに権限を渡したあとで「繋がらない」と言われずに済みます。

3ユーザー（タブ）

ユーザーアカウントの作成・削除・管理者フラグ・ロック解除・パスワードリセット・CSV一括取込／出力を行います。任意の「名前」を登録すると、管理画面では 山田 太郎（G012345） のように表示されます。名前は表示・検索用で、ログインには引き続きユーザー名（GID）を使います。

Windows 統合認証を有効にした環境では、初期パスワードの配布は不要です ユーザーを作成すると「初回設定待ち」になり、本人が初回ログイン時に自分でパスワードを決めます。本人確認は Windows のログオン情報（ログオン名＝GID＝Watashiのユーザー名）で自動的に行われます。無効な環境では「初期PW発行」を使います。

3-1. 新規ユーザーの作成

  1. 右パネル「新規ユーザー」で ユーザー名（GID） を入力。Windows のログオン名と同じ GID にします。
  2. 必要なら任意の名前（最大100文字）を入力します。空欄でも構いません。
  3. 管理者にするなら「管理者として作成」にチェック。
  4. ＋ 作成 を押す。
パスワード欄はありません 作成されたユーザーは 初回設定待ち になります。DBには誰も知り得ないランダム値が入るため、この状態ではどんなパスワードでもログインできません。本人が初回ログイン時に決めたパスワードが、そのまま本パスワードになります（直後にもう一度変更させることはしません）。有効期限は本人が設定した時点で「今 ＋ PasswordExpiryDays（既定90日）」で計算されます。

3-2. 初回パスワード設定の流れ

利用者の環境流れ
ドメイン参加端末 利用者が Watashi を起動し GID を入力して「次へ」→ Windows のログオン情報で本人確認（自動）→「初回パスワードの設定」画面 → 本人がパスワードを決めて完了。管理者の作業はありません。
ドメイン非参加端末
（Windows認証が使えない）		 「次へ」を押すと通常のパスワード入力欄が出るが、まだパスワードが無いのでログインできない → 利用者から管理者へ連絡 → 管理者が 🔑 初期PW発行 でパスワードを決めて本人に伝える → 従来どおり初回ログインで強制変更。
サーバー側の設定が必要です Windows 統合認証は既定で無効です。有効にする手順は deploy/IIS-HOSTING.md の「Windows 統合認証を有効にする」を参照してください。未設定の場合、全ユーザーが下段（管理者が初期PWを発行）の流れになります。
複数ドメインとユーザー名の注意 AllowList は許可ドメインを絞るだけで、ユーザーごとにドメインを結び付けません。複数の独立ドメインを許可する場合、GID は全許可ドメインを通して一意である必要があります。同名 GID が存在し得る場合は管理者発行の初期PW経路を使ってください。Watashi のユーザー名は英字の大文字・小文字を区別しないため、alice と ALICE は同じユーザーです。

3-3. 管理者フラグの変更・ロック解除・パスワード関連・削除

  • 管理者フラグ：一覧でユーザーを選び、右パネルの「管理者」チェックを変更して 保存。昇格前／降格前の access・refresh token は即時失効するため、対象ユーザーは再ログインが必要です。
  • ロック解除：連続ログイン失敗（既定15回）でロックされたユーザーを選び 🔓 ロック解除。
  • 初期PW発行：ユーザーを選び 🔑 初期PW発行 → ダイアログ（目玉アイコン付き）で新パスワードを入力。Windows認証が使えない端末向けの代替手段です。
  • 初回設定に戻す：ユーザーを選び ↩ 初回設定に戻す。パスワードを忘れた利用者に、自分で決め直してもらう場合に使います（パスワードを伝える必要がありません）。ログイン中のセッションと「このPCを記憶」も同時に失効します——端末の記憶を残すと自動ログインでパスワード無しに入れてしまうためです。
  • 削除：ユーザーを選び 🗑 削除。確認ダイアログ：
    ユーザー "G012345" を削除しますか？　このユーザーの権限・信頼デバイス・セッションも削除されます。
管理者ロックアウト防止（サーバが強制） 次の操作は、サーバが 400 Bad Request で拒否します。締め出しを防ぐための仕様です。
  • 自分自身を削除する／自分自身の管理者フラグを外す／自分自身を初回設定待ちに戻す
  • 他にアクティブな管理者がいない状況で、最後の管理者を削除／降格／初回設定待ちに戻す
※「アクティブな管理者」はロック中のユーザーと初回設定待ちのユーザーを除外して数えます。どちらもログインできないため、数えてしまうと実際に使える最後の管理者を消せてしまいます。ロック中の管理者しかいない場合は、先にその管理者をロック解除してから操作してください。万一全管理者が締め出された場合は第16章へ。

3-4. CSV一括登録（インポート）

📥 CSV取込 → ファイル選択 → モード選択ダイアログが出ます。

モード動作用途
新規追加のみ
（[はい]）		既存ユーザー名と衝突する行はスキップ「追加する人だけ取り込みたい」
上書き
（[いいえ]）		既存ユーザーの IsAdmin のみ更新。パスワードには一切触れません管理者フラグの一括見直し
「上書き」の動作が変わりました 以前は既存ユーザーのパスワードも再設定していましたが、現在はしません。CSVを再取り込みしただけで全員が締め出される事故を防ぐためです。パスワードの再設定が必要な場合は 🔑 初期PW発行 か ↩ 初回設定に戻す を明示的に使ってください。

CSVフォーマット

UTF-8（BOM推奨）、1行目はヘッダー必須。必須列 Username ／ 任意列 IsAdmin（新規作成時は省略すると false）と DisplayName（最大100文字）。列順は問いません。パスワードはCSVに書きません。

Username,IsAdmin,DisplayName
G012345,false,山田 太郎
G012346,true,佐藤 花子
G012347,false,
  • 取り込まれた新規ユーザーは初回設定待ちになります。
  • 上書きモードで DisplayName のセルを空にすると名前を消去します。列やその行の末尾セル自体が無い場合は、既存の名前を維持します。
  • 旧形式（Username,Password,IsAdmin）もそのまま取り込めます。Password 列は無視され、完了ダイアログにその旨が出ます。手元の古いCSVを作り直す必要はありません（CSVに書かれたパスワードではログインできません）。
  • 値にカンマ・改行・ダブルクォートを含む場合は "..." で囲む（RFC4180風）。
  • 全行を1件ずつ処理します。途中で失敗しても他の行は処理されます。
  • 完了ダイアログに 追加 N / 更新 N / スキップ N / 失敗 N と、失敗行の理由（行番号＋ユーザー名＋メッセージ、先頭10件）が表示されます。

3-5. CSVエクスポート（棚卸し用）

📤 CSV出力 → 保存先を指定。ファイル名は watashi-users-YYYYMMDD-HHmmss.csv。
既存の列順を維持し、末尾に DisplayName が追加されます。パスワード列は含まれません（DBに平文がないため）。PasswordStatus は PendingSetup ／ Active ／ MustChange ／ Expired のいずれかです。BOM付きUTF-8でExcelでそのまま開けます（数式インジェクション対策済み）。

退職者の扱い 削除でも構いませんが、監査ログとの紐付けが切れます。証跡を残すなら「全デバイス失効（第9章）＋↩ 初回設定に戻す」で無効化する運用がおすすめです（パスワードが無効化され、端末とセッションも同時に失効します）。

名前ReadWriteDeleteRename

一覧は権限の強さスコア（Read+Write+Delete+Rename の合計）の降順でクライアント側ソートされるため、フルアクセスが先頭に来ます。ユーザー権限タブの「権限テンプレート」ドロップダウンもデフォルトはフルアクセスです。

6-1. 各権限でできること（重要）

権限テンプレートのチェックは、Watashiクライアントの操作に次のように対応します。利用者に「なぜできない/できる」を説明するときの根拠になります。

権限できること注意・できないこと
Readリモート一覧表示・フォルダ移動・ダウンロードReadが無いと一覧取得もダウンロードも拒否
Writeアップロード・新規フォルダ作成Writeだけでは削除もリネームもできない
Deleteファイル/フォルダ削除許可パスのルート自体はDeleteがあっても削除不可
Rename同じ親フォルダ内でのリネーム実行にはRenameに加え新名パスへのWriteも必要。フォルダ間移動は不可

よく使う組み合わせと利用者の体験

テンプレート例利用者ができること
読取のみ一覧・移動・ダウンロードのみ。アップロード/新規フォルダ/削除/リネームは権限エラー
読取+書込＋アップロード・新規フォルダ作成。削除とリネームは不可
読取+書込+Rename＋ファイル名変更。削除は不可
フルアクセス許可パス配下の読み・書き・削除・リネームすべて可（ルート自体の削除/リネームは禁止）
使用中のテンプレートは削除できません どこかのユーザー権限で使われているテンプレートは、FK制約で守られており削除するとサーバーエラーになります。先に該当する権限割当を外してください。監査ログ：ADMIN_TEMPLATE_CREATE / _UPDATE / _DELETE。

7ユーザー権限（核心機能）

Watashi の中心となる機能。ユーザー × 共有 × サブパス × テンプレートの粒度で「誰がどこで何をできるか」を割り当てます。

画面は 左：ユーザー一覧（検索＋件数バッジ）／右：選択ユーザーの付与済みパス＋追加カードの構成です。ユーザーは 名前（Username） で表示され、名前と Username のどちらでも検索できます。

7-1. パスを追加する手順

  1. 左でユーザーをクリック（検索で絞り込み可）。件数バッジ（例 tanaka 4件）で付与状況がわかります。
  2. 下の「＋ パスを追加」で サーバー を選ぶ。
  3. 共有が自動でそのサーバー配下に絞られるので選ぶ。
  4. 権限テンプレートを選ぶ（デフォルトはフルアクセス）。
  5. 許可パスを入力（共有全体なら /、サブフォルダなら /dept-A）。任意で表示名。
  6. （任意）「ブラウズ」で実在ディレクトリを開き、サブフォルダをクリックすると許可パスに自動反映。
  7. ＋ このパスを追加 を押す → パスを追加しました。
1ユーザー × 1共有に複数のパス権限を持たせられる 例：watashitest 共有で /dept-A はフルアクセス、/shared/templates は読取のみ — のように、共有の中のフォルダごとに別の権限を与えられます。

特殊な制約

  • 許可パスのルート（例 /dept-A 自体）は削除/リネーム不可（誤削除防止）。中身は操作可。
  • リネームは同じ親ディレクトリ内のみ（隠れた移動を防止）。

削除

付与済みパスを選び 🗑 選択を削除。確認ダイアログ：
この権限を削除しますか？（対象のホスト/共有/パスが示されます）。監査ログ：ADMIN_PERMISSION_CREATE / ADMIN_PERMISSION_DELETE。

7-2. 📦 セットから一括適用 ／ 📋 他ユーザーから全件コピー

「付与済みのパス」上のクイック追加カードから、複数行をまとめて付与できます。

  • 📦 セットから一括適用：権限セット（第8章）を選び 適用。確認で [はい] 既存重複も上書き／[いいえ] 重複はスキップ（推奨）／[キャンセル]。結果：セット適用: 追加 N / 更新 N / スキップ N（監査：ADMIN_BUNDLE_APPLY）。
  • 📋 他ユーザーから全件コピー：コピー元ユーザーを選び コピー。同じ確認ダイアログ。結果：権限コピー: 追加 N / 更新 N / スキップ N（監査：ADMIN_PERMISSION_COPY）。

8権限セット（PermissionBundle）

「経理部標準」「営業部標準」のように、複数の権限行をひとまとめにした再利用可能セットです。同じパス群を毎回手入力する手間を解消します。

ワークフロー

  1. + 新規セット で名前を入力 → 空のセットが作成される。
  2. 左でセットを選択して右に詳細表示。
  3. 「＋ セットに行を追加」で 共有／テンプレート／許可パス／表示名 を入力して 追加。
    行を追加しました。「保存」で確定してください。
  4. すべての行を入れたら 💾 保存 で確定。
  5. ユーザー権限タブに移動し、各ユーザーへ「セットから一括適用」。
セットはスナップショット展開 セットの編集は「全件置換」（差分編集ではない）です。セット自体を削除しても、すでに適用済みのユーザー権限は残ります（リンクではなく、適用時に展開される方式）。監査ログ：ADMIN_BUNDLE_CREATE / _UPDATE / _DELETE / _APPLY。

9信頼デバイス

ユーザーの「このPCを記憶する（自動ログイン）」を管理します。

一覧の列

ID ／ ユーザー（名前＋Username） ／ マシン ／ Windowsユーザー ／ 登録 ／ 最終使用 ／ 失効。名前、Username、端末、Windowsユーザーで絞り込めます。

11操作ログ

全ファイル操作と管理者操作の監査ログを閲覧・出力します。

フィルタ

  • User：名前・ユーザー名の部分一致、またはユーザーID
  • Operation：READ / WRITE / DELETE / RENAME または ADMIN_*
  • From / To (UTC)：期間指定
  • 🔍 検索 でクエリ実行

カラム

ID ／ 時刻 ／ User（名前＋Username） ／ 端末 ／ Op ／ Result（success/failure）／ ホスト / 共有 ／ Path ／ Bytes ／ Dur(ms) ／ Err。User列は保存済みのUsernameを証跡として維持し、現在も存在するユーザーだけ現在の名前を補助表示します。削除済みユーザーはUsernameのみです。
「ホスト / 共有」列はホスト名（1行目）と共有表示名（2行目）の2行表示。Path列にホバーすると「ホスト / 共有 :: パス」のフル表記がツールチップで出ます（例 経理部FS / share-keiri :: /dept-A/file.txt）。ログ取得後にホスト/共有が削除された場合は (削除済 host#42) のように表示されます（ログ自体は保全）。

CSVエクスポート

📤 CSV出力で、現在のフィルタ条件のまま全件CSVをダウンロード。BOM付きUTF-8でExcelでそのまま開けます（数式インジェクション対策済み）。列に Location（「ホスト / 共有 :: パス」）・HostName・ShareName を含み、既存列の位置と HostId/ShareId を後方互換で維持したまま、末尾へ現在の DisplayName を追加します。

保管期間 デフォルト365日（AuditLogRetentionDays で変更可。0以下で永久保管）。日次バッチ AuditLogPurgeService が古いログを自動削除し、月次VACUUMでDBを圧縮します。

12システム設定

左の一覧でKeyを選び、右の「値を編集」で値を変更して 💾 保存。監査ログ：ADMIN_SETTING_UPDATE。

キー用途既定
PasswordExpiryDaysパスワード有効期限（日）90
PasswordWarningDays期限警告を出し始める日数14
AgentMaxConcurrencyAgent新規登録時のデフォルト同時接続上限20
SessionIdleMinutesクライアントのアイドルタイムアウト（分）30
AuditLogRetentionDays監査ログ保管日数（0以下で永久保管）365
MaxFailedLoginAttempts連続ログイン失敗で自動ロックするまでの回数15
反映タイミングに注意
  • PasswordExpiryDays を変えても既存ユーザーの期限は再計算されません。次回パスワード変更時から新しい期限が適用されます。
  • SessionIdleMinutes はログイン中のクライアントには次回ログインまで反映されません（ログイン応答で配信されるため）。
  • AuditLogRetentionDays は次の日次パージ実行時に反映（起動30秒後＋以降24時間毎）。即時反映したいならサーバ再起動＋30秒待ち。
  • MaxFailedLoginAttempts は小さくするほど総当たり耐性が上がりますが、誤入力ロックも起きやすくなります。

13認証のしくみ（運用上の挙動）

13-1. リフレッシュトークンのローテーション＋盗難検知

  • リフレッシュ成功のたびに新トークンを発行し、旧トークンは即失効します。
  • 失効済みトークンが再提示された場合は再利用とみなし、当該ユーザーのアクティブな全リフレッシュトークンを失効（token_reuse_detected）。盗難検知機構です。
  • この場合、該当ユーザーは強制再ログインになります。
あるユーザーが頻繁に「再ログインしてください」になる場合 画面の理由を確認してください。token_reuse_detected は複数端末や古い Credential Manager の token、password_changed はパスワード・管理者権限・初回設定状態の変更、account_locked はアカウントロック、device_revoked は端末失効です。盗難検知が疑われる場合は「全デバイス失効」→再度信頼デバイス登録を案内してください。

13-2. ログインのレート制限

/api/auth/login と /api/auth/auto-login に IP単位の固定ウィンドウ制限（デフォルト 10回/分、Auth:LoginPerMinutePerIp）。超過すると 429 Too Many Requests。内部NAT等で同一IPに多数ユーザーがいる環境では値を上げてください（例 50）。

13-3. その他

  • パスワードは bcrypt（ソルト自動付与）。アクセストークンはJWT(HS256)15分。リフレッシュは30日。
  • 連続ログイン失敗が MaxFailedLoginAttempts（既定15）に達すると自動ロック。
  • access token の認証時にDB状態を確認し、資格情報世代・初回設定状態・アカウントロックを即時反映。管理者フラグ変更でも資格情報世代が進みます。
  • リフレッシュのたびにもDB状態を確認：ユーザーがロック／信頼デバイスが失効なら 401、MustChangePassword ならフラグ付与。
  • クライアントは各リクエストを session generation に結び付け、古い401やrefresh応答が新しいログインを失効・上書きしないようにします。

14監査ログコード一覧

操作ログの Op 列に出るコードの早見表です。フィルタは完全一致なので、まとめて見たいときはCSV出力→Excelで ADMIN_ 絞り込みが便利です。

コード意味

15トラブル対応

症状対処
あるユーザーだけ全画面でエラー操作ログでそのユーザーを絞り込み、denied（権限不足）/not_found（ホスト・共有削除済）/parent_changed（リネーム禁止違反）を確認
ログインの 429 が頻発同一IPが1分10回超。NAT等なら Auth:LoginPerMinutePerIp を上げる。攻撃の可能性もあるのでまずIP確認
頻繁に「再ログイン」になるリフレッシュトークン再利用検知の可能性。対象に「全デバイス失効」→再登録を案内（→13章）
Agentが突然 UnhealthyAgentサービス稼働確認 → Agentログ確認 → 中央への疎通 → 中央DBの ExecutionNodes.Name とAgent側 Agent:AgentId 一致 →（mTLS）証明書の期限・サムプリント
Agentが 503 頻発MaxConcurrency 超過 → ノードタブで値を上げる。同時転送数・Health状態も確認
操作が遅い／SMB操作毎にハンドシェイク中央 appsettings.json の Cifs:SessionIdleSeconds（60→120等）/Cifs:MaxSessionsPerKey（4→8等）を増やす（要再起動）
ストレージ逼迫AuditLogs肥大の可能性。AuditLogRetentionDays を短縮、または日次パージ稼働を確認。即時は古いログをDELETE＋VACUUM
全ユーザーにPW変更を強制したいSQL：UPDATE Users SET MustChangePassword=1, PasswordExpiresAt=datetime('now');

Encryption MasterKey を変更したくなった

既存の暗号化済みCIFSパスワードはすべて復号不能になります マスターキーを変えると、全ホストのCIFSパスワードを再設定する必要があります。手順：①新キー生成（旧キーは捨てない）②旧キーで全ホストの平文を運用記録から取得 ③appsettings.json のMasterKeyを差し替え ④サーバ再起動 ⑤全ホストの編集画面でパスワード再入力（新キーで再暗号化）。

16管理者の緊急復旧（最悪のケース）

別の管理者がいれば、その人がユーザータブ → 🔓ロック解除／🔑PWリセットで復旧できます。他に管理者がいない場合のみ、DBを直接更新します。

16-1. ロック解除だけ（パスワードは覚えている）

sqlite3.exe があれば：

sqlite3.exe C:\ProgramData\Watashi\watashi.db
sqlite> UPDATE Users SET IsLocked=0, FailedLoginCount=0 WHERE Username='admin';
sqlite> .quit

16-2. ロック＋パスワード忘れの両方（完全復旧）

サーバ publish フォルダの BCrypt.Net-Next.dll で新ハッシュを生成し、Microsoft.Data.Sqlite.dll でDBに直接UPDATEします（sqlite3.exe 不要）。

# === 環境に合わせて書き換え ===
$publishDir  = "C:\Program Files\Watashi\Server"   # Watashi.Server.exe のフォルダ
$dbPath      = "C:\ProgramData\Watashi\watashi.db"
$newPassword = "RecoverMe2026!@#"                  # 12字＋大小数記号

# 0. サーバ停止 (SQLite 排他ロック解放)
Stop-Service Watashi.Server -ErrorAction SilentlyContinue

Push-Location $publishDir
try {
    # 1. BCrypt ハッシュ生成
    Add-Type -Path ".\BCrypt.Net-Next.dll"
    $hash = [BCrypt.Net.BCrypt]::HashPassword($newPassword)

    # 2. SQLite に UPDATE
    Add-Type -Path ".\SQLitePCLRaw.batteries_v2.dll"
    [SQLitePCL.Batteries_V2]::Init()
    Add-Type -Path ".\Microsoft.Data.Sqlite.dll"
    $conn = New-Object Microsoft.Data.Sqlite.SqliteConnection("Data Source=$dbPath")
    $conn.Open()
    $cmd = $conn.CreateCommand()
    $cmd.CommandText = @"
UPDATE Users SET PasswordHash=@h, IsLocked=0, FailedLoginCount=0,
  MustChangePassword=1, PasswordChangedAt=@now, PasswordExpiresAt=@exp
WHERE Username='admin'
"@
    $p1=$cmd.CreateParameter();$p1.ParameterName="@h";$p1.Value=$hash
    $p2=$cmd.CreateParameter();$p2.ParameterName="@now";$p2.Value=[DateTime]::UtcNow.ToString("o")
    $p3=$cmd.CreateParameter();$p3.ParameterName="@exp";$p3.Value=[DateTime]::UtcNow.AddDays(90).ToString("o")
    $cmd.Parameters.Add($p1)|Out-Null;$cmd.Parameters.Add($p2)|Out-Null;$cmd.Parameters.Add($p3)|Out-Null
    $cmd.ExecuteNonQuery()
    $conn.Close()
}
finally { Pop-Location }

# 3. サーバ再起動
Start-Service Watashi.Server

実行後は admin ＋仮パスワードでログイン → 強制変更画面で本番用パスワードに置き換え → パスワードマネージャ等に保管して二度と忘れないようにしてください。このスクリプトは PasswordChangedAt も更新するため、既存リフレッシュトークンは自動失効します（横取り防止）。

17用語集

ホスト
接続先のCIFS（SMB）ファイルサーバー。IP＋資格情報＋実行ノードで登録。
共有 (Share)
ホスト上のSMB共有。表示名と実際の共有名を持つ。
権限テンプレート
Read/Write/Delete/Rename の組み合わせに名前を付けたひな型。
ユーザー権限
ユーザー×共有×サブパス×テンプレートの割当。Watashiの核心。
権限セット (Bundle)
複数の権限行をまとめた再利用セット。スナップショット展開。
実行ノード
CIFSへの接続経路。Direct（中央自身）/Agent（踏み台）。
信頼デバイス
自動ログインに使う端末登録。既定3台（管理設定で1〜20台）。利用者自身による個別失効にも対応。
監査ログ
全ファイル操作・全管理操作の記録。ADMIN_* プレフィックス。
mTLS
Server↔Agent間の双方向証明書認証。サムプリントで照合。
MustChangePassword
次回ログインで強制的にパスワード変更させるフラグ。
