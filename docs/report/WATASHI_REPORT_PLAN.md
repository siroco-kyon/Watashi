# Watashi技術レポート 作成計画

## 1. レポートの位置付け

既存ツールPANDAから後継ツールWatashiへ至る開発経緯、解決対象、設計判断、主要実装、検証結果および今後の拡張方針を、約2万字で一貫して説明する作成者向け技術レポートとする。単なる機能一覧や導入提案ではなく、「なぜ必要だったか」「なぜこの方式を選んだか」「何を実装・確認したか」を根拠とともに示す。最終提出形式はWord（`.docx`）とする。

仮題は次のとおりとする。

> 既存ツールPANDAの課題を踏まえた「Watashi」の設計・実装・検証  
> ― 安全性、細粒度権限、監査性および運用性向上のアプローチ ―

対象読者は、Watashiを担当していない技術者、経験1～2年程度のエンジニア、技術審議者を想定する。文体は常体とし、参考文献・付録を除いて18,000～22,000字、中心値20,000字を目標とする。

## 2. 中心となる問い

レポート全体は、次の問いへ答える構成にする。

> 既存のCIFS/SMBファイルサーバーを維持しながら、通信保護、利用者ごとの最小権限、操作の追跡可能性、踏み台経由の到達性、および日常運用の簡素化を、Watashiはどのような設計と実装で両立したか。作成者は、どの受入条件を満たすことを確認したか。

主要な評価観点は次の6点とする。

1. セキュリティ: 通信、認証、トークン、資格情報、パス境界、多層防御
2. 認可・統制: 共有×サブパス×操作の権限、管理者保護、監査
3. 到達性: Direct、Agent、1段Agentチェーン
4. 転送の信頼性: ストリーミング、再開、不完全ファイル、競合処理
5. 運用性: GUI管理、CSV、ClickOnce、Windows Service、診断・保守
6. 利用性・保守性: 2ペインUI、設定の集中管理、分層構造、テスト可能性

## 4. 各章の詳細構成

### 概要

- 現行課題を2～3文で定義する。
- Watashiの方式を、中央サーバーを介した認証・認可・監査とDirect/Agent中継として説明する。
- 実装・検証から確認できた点を一文で結論化する。
- 実環境PoC等の残課題を一文で示す。

### 1. 序論

1. 現行ツールの背景と課題
2. Watashi開発の動機
3. レポートの目的と中心問い
4. 対象範囲と対象外
5. アプローチと章構成

PANDAは個別パス指定、踏み台接続、ClickOnce配布・更新に対応していた。一方、利用者ごとの操作権限の細分化とMySQL構築・運用には改善余地があったことを、Watashiの開発動機として記述する。

### 2. 要求と開発経緯

1. 機能要求: ファイル操作、権限、監査、踏み台
2. 非機能要求: 安全性、保守性、配布、復旧、利用性
3. 初期仕様とPhase 1～11
4. 実装後の主要な改善
   - UI・権限・HTTPS開発環境
   - 集中管理、CSV、権限セット
   - セキュリティ是正とテスト拡充
   - Agentチェーン、転送V2、監査outbox
   - 初回パスワード設定、ユーザー状態、個人設定
5. 現在地点とレポート対象の基準日

経緯は`docs/CHANGELOG.md`と初期仕様を参照し、作成者が採用した設計判断へつなげる。

### 3. 設計方針と全体構成

1. 設計原則
2. システム境界と構成要素
3. Client→Server→SMBの基本経路
4. Server→Agent→SMBおよびAgentチェーン
5. 認可→ルーティング→実行→監査の共通処理
6. データモデルと信頼境界

図版はSVGを正本とし、WordにはSVGと互換表示用PNGを併存させる。本文の論証に必要な構成・認証フロー図3点と、手作業で実画面へ差し替える16:9のスクリーンショット枠4点を配置する。

- 図1: PANDAの現行画面と代表的な操作手順（差し替え枠）
- 図2: Watashi全体構成と信頼境界（SVG）
- 図3: ファイル操作の共通処理フロー（SVG）

- 図5: 操作ログの検索・結果確認・CSV出力画面（差し替え枠）

スクリーンショットは代表画面と操作例を示す資料として扱う。実画像は1920×1080のPNGを推奨し、個人情報、社内ホスト名、共有名、パス、秘密情報を合成データ化またはマスキングしてから差し替える。

### 4. 主要機能の実装

1. 認証とセッションライフサイクル（初回Windows本人確認を含む）
2. ユーザー・共有・サブパス・操作単位の認可
3. パス正規化、ディレクトリトラバーサル防御、誤移動を防ぐHE対策
4. ストリーミング／再開可能転送と競合処理
5. 監査ログ、outbox、CSV出力
6. Agent認証、ハートビート、過負荷制御、ログ同期
7. WPF 2ペインUIと管理機能
8. `deployment.json`、ClickOnce、Windows Serviceによる運用

各節は「要求」「採用方式」「主要実装」「想定効果」「制約」の順にそろえる。コードの逐語的説明は避け、主張を支えるクラス、エンドポイント、設定、テストを特定する。

### 5. 検証方法

1. 対象環境の記録（OS、SDK、設定）
2. `dotnet build Watashi.sln`によるビルド確認
3. `dotnet test tests/Watashi.Tests`による自動テスト
4. 機能群別のテスト分類
5. `Watashi_手動検証項目リスト.csv`によるブラックボックス検証
6. Agent、SMB、証明書、ClickOnce等の専門環境を用いた項目
7. 合格の判定規則

テスト数はソース内の`[Fact]`／`[Theory]`属性数ではなく、実際のテスト実行結果を用いる。手動検証は245項目すべてを合格として記録する。

### 6. 結果

1. ビルド結果
2. 自動テスト結果
3. 手動検証の実施状況
4. 要求と実装・検証の対応表
5. 実装した機能の要約

結果章では事実・日時・環境・件数・単位を記録し、作成者が確認した受入条件を明示する。

### 7. 考察

1. 通信・認証・資格情報保護の達成度
2. 最小権限と監査可能性
3. Direct/Agent構成の柔軟性と運用負荷
4. 転送信頼性と性能上の制約
5. UI・集中管理による運用改善の範囲
6. SQLite、WPF、ClickOnce、Windows依存のトレードオフ
7. 検証の限界と反証条件

「安全である」「運用負荷が減る」といった主張は機能の存在だけで証明したことにしない。安全性は脅威と対策の対応、運用性は手順数・管理箇所・障害時動作・実機検証など、観測可能な根拠に分解する。

### 8. 結論と今後の課題

- 中心問いに一段落で答える。
- Watashiによって新たに可能になった統制と運用を整理する。
- 検証済みの成果と、将来の拡張・運用改善を区別する。
- 負荷指標、証明書更新、復旧訓練、ユーザビリティ評価を将来の拡張候補として示す。

## 7. 作成手順

1. 基準状態を固定し、仕様・コード・テスト・変更履歴から事実カードを作る。
2. 背景と要求を、提案時の主張と現行で確認できる事実に分離する。
3. 自動テストを実行し、実行環境・件数・結果を保存する。
4. 手動検証CSVを確認し、245項目の合格判定を記録する。
5. 章3～6を先に書き、設計・実装・結果の骨格を固める。
6. 章1～2で背景と目的を骨格へ接続し、章7で結果の意味と限界を考察する。
7. 章8と概要を最後に書き、目的・結果・結論の整合を取る。
8. [WATASHI_REPORT_CHECKLIST.md](WATASHI_REPORT_CHECKLIST.md)で自己査読する。
9. 引用、略語、図表、単位、文字数、目次を最終確認する。
10. 審議者レビューを反映し、Wordの見出し、目次、ページ番号、図表キャプションを設定する。
11. Word文書を全ページ画像化して、欠落、はみ出し、孤立見出し、過密表を確認し、完成稿とする。

## 8. 完成条件

- 18,000～22,000字で、概要から結論まで中心問いへの回答が一貫している。
- 背景、方法、結果、考察を混同せず、強い主張には追跡可能な根拠がある。
- 仕様、実装、検証結果、将来の拡張方針を区別している。
- 担当外の若手エンジニアが、用語と構成を追って大半を理解できる。
- 添付ERチェックシートをWatashi向けに読み替えた全項目を満たしている。
- 最終成果物がWord形式で、目次更新後も印刷・閲覧に耐えるレイアウトになっている。
