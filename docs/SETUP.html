Watashi setup guide

Watashi 環境構築ガイド

開発機での 5 分動作確認から本番デプロイまで。「どのマシンで何をするのか」を各章の先頭に示し、通信構成の選択・設定ファイルの書き方・投入前チェックまでを通しでまとめています。

1. 全体像と前提条件

Watashi は 4 つの登場人物からなります。まず何がどこと通信するのかを押さえてください。設定でつまずく箇所のほとんどは、この図のどの線の話なのかが分かれば解決します。

登場人物実体置く場所役割
クライアントWatashi.Client (WPF)利用者の Windows PC画面。ClickOnce で配布・自動更新される
配布サーバーIIS社内 Web サーバーClickOnce の発行物を置く。中央サーバーと同居可
中央サーバーWatashi.ServerWindows Server認証・権限・監査ログ・DB (SQLite)。ファイル操作の司令塔
エージェントWatashi.Agent踏み台サーバーCIFS へ実際に SMB 接続する実行役。不要なら省略可
エージェントは必須ではありません。中央サーバーから CIFS に直接 SMB 接続できる構成なら、seed 済みの Direct (Local) ノードだけで動きます。ネットワークセグメントが分かれていて中央から直接届かない場合にエージェントを置きます。

前提条件

項目要件
OS (Server / Agent)Windows Server 2019 以降 (Windows Service として常駐)
OS (Client)Windows 10 / 11
.NET ランタイム8.0 (いずれも net8.0。self-contained 発行ならランタイム導入不要)
ネットワーク閉域網 (社内 LAN / VPN 内) を想定
同時接続50 ユーザー程度を想定
権限サービス登録には管理者権限の PowerShell が必要

本番構築は次の順で進めます。3 章 (通信モードの決定) を先に済ませておくと、4〜6 章の設定ファイルで迷いません。

2. 5 分で動かす (開発機での動作確認)

作業マシン: 開発機

CIFS サーバーが無くても、ログイン・認証・DB 自動生成までは確認できます。本番構築の前に一度通しておくと、後の切り分けが楽になります。

2-1. 中央サーバーを起動

cd src\Watashi.Server
dotnet run -- --bootstrap-admin
# → Username とランダムな One-time password をこの端末にだけ表示して終了
# → 表示値を安全に控えたら通常起動する
dotnet run
# → http://127.0.0.1:18080 で起動
# ASPNETCORE_ENVIRONMENT=Development は launchSettings.json で自動設定されるため、環境変数の手動指定は不要

2-2. 疎通とログインを確認

別ウィンドウで実行します。

# 疎通確認 (ブラウザで http://127.0.0.1:18080/ を開くとエンドポイント一覧が見える)
Invoke-RestMethod http://127.0.0.1:18080/health
# → {"status":"ok","at":"..."}

# ログイン (bootstrap で表示された資格情報)
$secure = Read-Host '表示された One-time password' -AsSecureString
$password = [Net.NetworkCredential]::new('', $secure).Password
$body = @{ username = 'admin'; password = $password } | ConvertTo-Json
$login = Invoke-RestMethod -Method Post -Uri http://127.0.0.1:18080/api/auth/login `
    -ContentType 'application/json' -Body $body
$login.mustChangePassword   # → True (初回はパスワード変更が必要)
$login.accessToken          # → JWT

PowerShell の curl に注意。curl は Invoke-WebRequest のエイリアスです。上記の PowerShell ネイティブ例を使うか、Unix 構文を使う場合は curl.exe と明示してください。一時パスワードをコマンド履歴へ直接書かないでください。

2-3. WPF クライアントを起動

cd ..\Watashi.Client
# 接続先と更新確認先は同梱の deployment.json で固定される。
# 開発機では serverUrl を http://127.0.0.1:18080 に書き換えてから起動する。
dotnet run
# → bootstrap の資格情報でログイン → パスワード変更画面 → メイン画面

ホストが未登録ならリモートペインは空です。ホストの登録手順は ADMIN-GUIDE.md を参照してください (実 CIFS サーバーが必要)。

開発時のポートsrc\Watashi.Server\appsettings.Development.json の Kestrel:Endpoints:Http:Url で設定。HTTPS (https://localhost:18443) も併設済みで、dev-cert を信頼すれば HTTPS でも検証できます (手順: DEVELOPMENT.md)。
DB ファイルの場所開発: src\Watashi.Server\watashi-dev.db
本番: C:\ProgramData\Watashi\watashi.db

3. 通信モードを決める

通信経路は 区間 A (Client ↔ Server) と 区間 B (Server ↔ Agent) の 2 つがあり、それぞれ独立に HTTP / HTTPS を選べます。組み合わせで 3 つの標準モードを用意しています。

CIFS 資格情報とファイル内容がネットワークを流れるため、区間 A (Client ↔ Server) は HTTPS 必須です。区間 B が社内 LAN 内で完結するなら HTTP でも実用上問題ありませんが、PCI / 個人情報など規制対象を扱う場合は mTLS にしてください。

3-1. モード A: 全 HTTPS + mTLS

Server appsettings.json

{
  "Kestrel": {
    "Endpoints": {
      "Https": {
        "Url": "https://0.0.0.0:8443",
        "Certificate": { "Path": "server.pfx", "Password": "..." }
      }
    }
  },
  "Routing": {
    "UseMtls": true,
    "ClientCertificatePath": "central-client.pfx",
    "ClientCertificatePassword": "..."
  }
}
UseMtls=true のとき、サーバー Kestrel は ClientCertificateMode.AllowCertificate で起動し、/api/internal/* は Agent ポリシーで証明書サムプリント検証が必須になります。サムプリントは ExecutionNode.ClientCertificateThumbprint と照合されます。

Agent appsettings.json

{
  "Agent": {
    "AgentId": "bastion-a",
    "CentralUrl": "https://central.internal:8443",
    "MaxConcurrency": 20
  },
  "Certificate": {
    "Path": "agent.pfx",
    "Password": "..."
  },
  "Auth": {
    "CentralCertificateThumbprint": "<中央サーバが Agent へ提示するクライアント証明書 Thumbprint>",
    "SharedSecret": ""
  },
  "Routing": { "UseMtls": true },
  "Kestrel": {
    "Endpoints": {
      "Https": {
        "Url": "https://0.0.0.0:8443",
        "Certificate": { "Path": "agent.pfx", "Password": "..." }
      }
    }
  }
}

中央 DB の ExecutionNodes

Endpoint = https://bastion-a:8443
ClientCertificateThumbprint = <Agent が提示するクライアント証明書 Thumbprint>

Client の接続先 (同梱 deployment.json、発行前に編集)

// exe と同じ場所に置かれる。利用者は変更不可
{
  "serverUrl": "https://watashi.internal:8443",
  "updateManifestUrl": "https://watashi.internal/install/Watashi.Client.application",
  "enableDragDrop": true
}

3-2. モード B: 混在 (区間 A は HTTPS、区間 B は HTTP + 共有秘密)

現実的な落としどころです。中央と踏み台が同一データセンタ / 同一信頼ゾーンにあり、クライアント PC は事務 LAN や VPN 越しという構成に向きます。

Server appsettings.json (mTLS 無効)

{
  "Kestrel": {
    "Endpoints": {
      "Https": {
        "Url": "https://0.0.0.0:8443",
        "Certificate": { "Path": "server.pfx", "Password": "..." }
      }
    }
  },
  "Routing": {
    "UseMtls": false,
    "SharedSecret": "<32 バイト以上のランダム値。Agent と同じ値>"
  }
}

Agent appsettings.json

{
  "Agent": {
    "AgentId": "bastion-a",
    "CentralUrl": "https://central.internal:8443",
    "MaxConcurrency": 20
  },
  "Auth": {
    "CentralCertificateThumbprint": "",
    "SharedSecret": "<Server と同じ値>"
  },
  "Routing": { "UseMtls": false },
  "Kestrel": {
    "Endpoints": { "Http": { "Url": "http://0.0.0.0:8081" } }
  }
}
SharedSecret を両側に設定すると、Agent は X-Watashi-Secret ヘッダで中央サーバーを認証します。中央サーバーも Agent からの heartbeat / ログ同期を同じ共有秘密で認証します。mTLS が使えない場合の最低限の保護です。ExecutionNodes の Endpoint は http://bastion-a:8081、ClientCertificateThumbprint は空で構いません。

3-3. モード C: 全 HTTP

検証・ラボでのみ使います。Server の appsettings.json から Https セクションを削除して Http のみ残し、Agent もすべて HTTP、Client も HTTP で接続します。

HTTP モードでも「このPCを記憶する」(信頼デバイス) は利用できますが、デバイストークン交換が平文で流れます。Production の appsettings.json で Auth:AllowHttpForAutoLogin を true にしない限り、サーバーは HTTP の auto-login を 401 で拒否します (Dev は既に true)。

3-4. ファイアウォールは片方向でよい

中央サーバーは Agent への接続を発信側として行います。踏み台のファイアウォールで Agent のポート (8081 / 8443) を中央サーバーの IP からのみ許可すれば足ります。Agent → 中央は heartbeat とログ送信に限定されます。

3-5. ポート番号の変更

Server / Agent とも Kestrel:Endpoints の URL の :port を変えるだけで変更できます。

// Server (appsettings.json / appsettings.Development.json)
"Kestrel": {
  "Endpoints": {
    "Http":  { "Url": "http://0.0.0.0:8080" },
    "Https": { "Url": "https://0.0.0.0:8443" }
  }
}

// Agent (appsettings.json)
"Kestrel": {
  "Endpoints": {
    "Http": { "Url": "http://0.0.0.0:8081" }
  }
}
よくあるケース対処
80 / 443 が IIS や Skype 等で使用中8080 / 8443 / 18080 / 18443 など空きポートに変更
同一マシンで複数インスタンスを起動各 appsettings.json で別ポートを割り当て
社内ファイアウォールが特定範囲のみ許可その範囲内のポートに合わせる
 
# 起動前に、そのポートが空いているか確認
netstat -ano | findstr :8080
Get-NetTCPConnection -LocalPort 8080 -ErrorAction SilentlyContinue

ポートが埋まっていると起動時に次のエラーになります。別ポートに変更してください。

System.IO.IOException: Failed to bind to address http://0.0.0.0:80: address already in use.

ポートを変えたら ExecutionNode.Endpoint も忘れず更新してください。中央 DB の Agent ノードの Endpoint に反映されていないと繋がりません。

4. 中央サーバーを立てる

作業マシン: CI / 開発機 → 中央サーバー

4-1. ビルド (CI / 開発機で実施)

dotnet publish src\Watashi.Server\Watashi.Server.csproj `
    -c Release -r win-x64 --self-contained `
    -o D:\publish\WatashiServer

4-2. appsettings.json を設定

{
  "ConnectionStrings": {
    // ローカル SSD 必須。ネットワーク共有は不可
    "Default": "Data Source=C:\\ProgramData\\Watashi\\watashi.db;Cache=Shared;Foreign Keys=True;"
  },
  "Jwt": {
    // 32 バイト以上のランダム値に必ず変更。Production で "CHANGE-ME" のままだと起動拒否
    "Secret": "<4-3 の方法で生成。48 バイトの Base64 推奨>",
    "Issuer": "Watashi",
    "Audience": "Watashi",
    "AccessTokenMinutes": 15,
    "RefreshTokenDays": 30
  },
  "Encryption": {
    // 32 バイトの Base64 (= 44 文字)。CIFS パスワード暗号化に使用
    // 紛失すると全 CIFS 資格情報が復号不能になるので厳重管理
    "MasterKey": "<4-3 の方法で生成>"
  },
  "Auth": {
    "AllowHttpForAutoLogin": false,
    "LoginPerMinutePerIp": 10,
    "WindowsAuth": {
      "Mode": "IIS",
      "AllowHttp": false,
      "DomainMatch": "IgnoreDomain",
      "AllowedDomains": [],
      "EnableDiagnostics": true,
      "SetupPerMinutePerIp": 30
    }
  },
  "Cifs": {
    "SessionIdleSeconds": 60,
    "MaxSessionsPerKey": 4
  },
  "Kestrel": {
    "Endpoints": {
      "Https": {
        "Url": "https://0.0.0.0:8443",
        "Certificate": { "Path": "C:\\Apps\\Watashi\\server.pfx", "Password": "..." }
      }
    }
  },
  // モード A の場合のみ
  "Routing": {
    "UseMtls": true,
    "ClientCertificatePath": "C:\\Apps\\Watashi\\central-client.pfx",
    "ClientCertificatePassword": "...",
    "SharedSecret": ""
  }
}

HTTPS 証明書の指定方法は 2 通りあります。上記は PFX ファイル指定ですが、社内 PKI から配布された証明書 (= IIS のバインドで選んでいる証明書) をファイル化せずそのまま使うこともでき、Windows 上では一般にこちらの方が運用が楽です。証明書ストア参照モードへの書き換え、秘密キーへのアクセス権付与、エクスポート可否の判定、更新時の流れは deploy/CERTIFICATE.md を参照してください。

起動時に検証される項目。Jwt:Secret が CHANGE-ME で始まり ASPNETCORE_ENVIRONMENT=Production の場合は例外で起動拒否されます。Encryption:MasterKey も REPLACE-WITH プレフィックスを検出します (Dev / Stg では警告のみ)。

Encryption:MasterKey は Base64 でデコードして 32 バイトになる値が必須です。プレースホルダ以外でも、Base64 として無効な文字列や長さ不足だと、起動時ではなく CIFS ホスト登録時に Encryption:MasterKey は Base64 でエンコードされた値である必要があります で 500 エラーになります。

4-3. Jwt:Secret / Encryption:MasterKey を生成する

# Windows PowerShell 5.1 / 7 どちらでも動く
$rng = [System.Security.Cryptography.RandomNumberGenerator]::Create()

# Jwt:Secret 用 (48 バイト推奨)
$bytes = New-Object byte[] 48
$rng.GetBytes($bytes)
[Convert]::ToBase64String($bytes)

# Encryption:MasterKey 用 (32 バイト固定)
$bytes = New-Object byte[] 32
$rng.GetBytes($bytes)
[Convert]::ToBase64String($bytes)

PowerShell 7+ (pwsh.exe) なら 1 行で書けます。Git for Windows が入っていれば openssl も使えます。

[Convert]::ToBase64String([System.Security.Cryptography.RandomNumberGenerator]::GetBytes(32))

& "C:\Program Files\Git\usr\bin\openssl.exe" rand -base64 32

★ MasterKey の保管が最重要です。32 バイト Base64 (44 文字、末尾 = 1 個) を生成したら、パスワードマネージャや金庫に、DB バックアップとは別の場所へバックアップしてください。鍵を紛失すると DB 内の CIFS 接続パスワードが全部復号不能になり、ホスト登録のやり直しになります。運用開始後の鍵変更も既存暗号データが読めなくなるため、要計画です。

ファイル流出リスクを下げるなら、appsettings.json に書かず環境変数で渡せます:
setx WATASHI_MASTER_KEY "<生成した値>" /M

4-4. Windows サービスとして登録

# 管理者 PowerShell で実行
.\deploy\install-server-service.ps1 -PublishDir D:\publish\WatashiServer

# 既定の動作:
#   - C:\Program Files\Watashi\Server に配置
#   - サービス名 Watashi.Server、自動起動、LocalSystem アカウント
#   - 異常終了時の自動再起動 (5s → 30s → 60s)
# 専用サービスアカウントを使う場合
.\deploy\install-server-service.ps1 `
    -PublishDir D:\publish\WatashiServer `
    -ServiceAccount "DOMAIN\svc-watashi"
# パスワードプロンプトは sc.exe の制約上未対応。設定後 services.msc で資格情報を入れる

# アンインストール
.\deploy\uninstall-service.ps1 -ServiceName Watashi.Server
固定の初期管理者パスワードはありません。サービスを停止し、サーバー端末で Watashi.Server.exe --bootstrap-admin を一度だけ明示実行してください。表示された一時パスワードは DB やログに平文保存されず、初回ログインで変更を強制されます。表示を失った場合は未ログインの間だけ再発行でき、初回ログイン後または有効な管理者が存在する場合は拒否されます。
旧版の固定パスワードで作られた admin が未使用なら、サービス停止中に同じコマンドを実行するとランダムな一時パスワードへ置換され、旧値が無効になります。ログイン履歴のある運用中の管理者は変更されません。
Stop-Service Watashi.Server
Push-Location "C:\Program Files\Watashi\Server"
.\Watashi.Server.exe --bootstrap-admin
# Username / One-time password を安全に控える
Pop-Location
Start-Service Watashi.Server

4-5. Server appsettings.json キー一覧

キー必須設定する値補足
ConnectionStrings:Default必須SQLite DB の保存先例: C:\ProgramData\Watashi\watashi.db。サービスアカウントが親フォルダを作成・読み書きできること
Jwt:Secret必須32 バイト以上のランダム文字列Production で CHANGE-ME のままだと起動拒否
Jwt:Issuer / Jwt:Audience推奨通常は WatashiJWT 検証用。通常変更不要
Jwt:AccessTokenMinutes推奨アクセストークン分数短いほど漏えい時の影響が小さい。既定 15
Jwt:RefreshTokenDays推奨再ログイン不要期間既定 30
Encryption:MasterKey必須32 バイト Base64CIFS パスワード暗号化用。紛失すると既存ホスト資格情報を復号できない
Auth:AllowHttpForAutoLogin任意false 推奨HTTP 接続で「このPCを記憶する」を許可するか。Production は false
Auth:LoginPerMinutePerIp任意1 分あたり試行数同一 NAT で誤検知する場合だけ増やす。既定 10
Auth:WindowsAuth:*IIS 構成で必須初回設定の Windows 本人確認同梱設定は Mode=IIS。設定手順は HTML ガイド と IIS-HOSTING.md
Routing:UseMtls構成依存true / false区間 B を mTLS で相互認証するなら true
Routing:ClientCertificatePathmTLS 時必須中央が Agent へ提示する PFXServer → Agent の呼び出しに使うクライアント証明書
Routing:ClientCertificatePasswordmTLS 時必須上記 PFX のパスワード環境変数での上書きも可
Routing:SharedSecret共有秘密時必須32 バイト以上のランダム値Server と Agent の両方に同じ値。mTLS 本番では空推奨
Cifs:SessionIdleSeconds任意SMB セッション再利用秒数長くすると再接続は減るが、セッション保持時間が伸びる
Cifs:MaxSessionsPerKey任意接続キーごとの最大セッション数同時転送が多い環境で増やす
Kestrel:Endpoints必須Listen URL と証明書HTTP / HTTPS ポート、HTTPS 証明書を定義
Serilog:WriteTo推奨Console / File既定で C:\ProgramData\Watashi\logs\server-.log に日次ローテーション

5. 配布サーバー (ClickOnce)

作業マシン: CI / 開発機 → 配布サーバー (IIS)

クライアントは ClickOnce で配布します。

src\Watashi.Client\Properties\PublishProfiles\ClickOnceProfile.pubxml を編集します。
<PublishUrl> = 発行先 (例: \\fileserver\share\Watashi\)、 <InstallUrl> = 利用者が開く URL (例: https://watashi.internal/install/)、 <ManifestCertificateThumbprint> = Code Signing 証明書のサムプリント。
接続先・更新確認先・機能を src\Watashi.Client\deployment.json に設定します (発行前に必ず編集)。
発行します。
IIS 側で MIME 設定を行います → deploy/IIS-MIME.md
クライアント PC で https://watashi.internal/install/Watashi.Client.application を開くとインストールが始まります。
初回起動でそのままログイン画面が表示されます。接続先は deployment.json で確定済みのため、利用者が入力する項目はありません (ログイン画面下の「接続テスト」で疎通確認のみ可能)。
以降、起動時に ClickOnce とアプリ本体の両方でバージョンチェックが走り、更新があれば自動でダウンロードされます。

deployment.json

{
  "serverUrl": "https://watashi.internal:8443",                                    // 接続する中央サーバ
  "updateManifestUrl": "https://watashi.internal/install/Watashi.Client.application", // 起動時に確認する ClickOnce マニフェスト
  "enableDragDrop": true                                                           // ドラッグ＆ドロップ転送の可否
}
  • このファイルは発行物に同梱され、起動時にこの値で接続先・更新確認先・機能が固定されます。利用者からは変更できません
  • %LocalAppData%\Watashi\settings.json より優先されます

発行コマンド

dotnet publish src\Watashi.Client\Watashi.Client.csproj `
    -c Release -p:PublishProfile=ClickOnceProfile

6-3. Agent appsettings.json キー一覧

キー必須設定する値補足
Agent:AgentId必須Agent の一意名中央の ExecutionNodes.Name と完全一致。例: bastion-a

Auth:CentralCertificateThumbprintmTLS 時必須中央が Agent へ提示する証明書の ThumbprintServer → Agent の /agent/* 呼び出しを Agent 側で検証する

HTTP + 共有秘密モードでは Certificate:Path / Certificate:Password は空で構いません。Agent の待受も Kestrel:Endpoints:Http を使うため、Agent 側に HTTPS サーバー証明書は不要です。証明書が必要になるのは、区間 A を HTTPS にする中央サーバー側と、Routing:UseMtls=true で mTLS を使う場合だけです。UseMtls=false かつ Auth:SharedSecret が空だと、Agent は起動時に設定エラーで停止します。
複数 Agent でも同じ共有秘密を利用できます。heartbeat は各 Agent の Agent:AgentId と中央の ExecutionNodes.Name を照合します。現行 Agent は X-Watashi-Agent-Id も送信するため、監査ログも AgentId 別に記録されます。旧 Agent の監査ログは互換性のため (agent:shared-secret) として受理されます。

6-6. 「Agent の証明書」は 3 種類ある

Watashi で「Agent の証明書」と呼ぶものには 3 種類あり、守る通信も設定先も違います。混同しやすいので、下図で「どの線を守るものか」を確認してください。

用途設定先何を守るか
① Agent の HTTPS サーバ証明書Agent Kestrel:Endpoints:Https:CertificateServer が Agent の HTTPS endpoint に接続するときの TLS
② Agent クライアント証明書Agent Certificate:Path / Server ExecutionNode.ClientCertificateThumbprintAgent が中央の /api/internal/* に接続するとき、どの Agent かを証明する
③ 中央クライアント証明書Server Routing:ClientCertificatePath / Agent Auth:CentralCertificateThumbprintServer が Agent の /agent/* に接続するとき、中央からの呼び出しかを Agent が検証する

検証環境では同じ PFX を複数用途に流用しても動きますが、本番では「HTTPS サーバ証明書」と「クライアント認証証明書」を分ける方が更新・失効・監査が楽です。

HTTP + 共有秘密モードでは、上記 3 つはいずれも使いません。ただし「共有秘密のまま通信だけ TLS 化する」(Agent の待受を https:// にする) ことはでき、その場合は ① だけを使います (手順: AGENT-HTTPS-ACME.html)。

6-7. 複数 Agent / 複数踏み台

複数の踏み台サーバーに Agent を配置できます。各 Agent で Agent:AgentId を一意にし、中央の管理画面で同じ名前の ExecutionNode を登録してください。CIFS ホスト登録時にどの ExecutionNode から接続するかを選ぶため、ネットワークセグメントごとに Agent を分けられます。

複数 Agent でも中央 Server と共通の共有秘密を使用できます。各 Agent の Agent:AgentId は一意にし、中央の ExecutionNodes.Name と完全一致させてください。すべての Agent は同じ管理・信頼境界として扱います。

9-2. 監査ログの保管期間

監査ログ (AuditLogs) の削除はサーバー内蔵の AuditLogPurgeService が自動で行います (起動 30 秒後 + 以降 24 時間ごと)。保管日数は appsettings.json ではなく管理画面の「システム設定」で変更する DB 格納の設定値です。

# 例: 管理者トークン取得後、保管日数を 180 日に変更 (サーバー再起動は不要)
Invoke-RestMethod -Method Put -Uri "$u/api/admin/settings/AuditLogRetentionDays" `
    -ContentType 'application/json' -Body (@{Value='180'} | ConvertTo-Json) -Headers $adminHeaders

0 を設定すると自動削除が止まり永久保管になります。

外部の schtasks / sqlite3.exe で DELETE FROM AuditLogs ... を別途スケジュールしないでください。内蔵パージと二重に動作し、特に AuditLogRetentionDays=0 (永久保管) を設定していても外部タスクが古いログを消してしまい、保管ポリシーの保証が崩れます。

月次で VACUUM を回す場合:

schtasks.exe /Create /SC MONTHLY /TN "Watashi VACUUM" `
    /TR "sqlite3.exe C:\ProgramData\Watashi\watashi.db \"VACUUM;\"" /ST 04:00

10. トラブルシューティング

起動できない

症状原因と対処
「Jwt:Secret がデフォルトのプレースホルダ値のままです」Production では実値必須。Dev / Stg なら警告だけで起動継続
「Jwt:Secret が設定されていません」appsettings.json または環境変数を確認
「Encryption:MasterKey は 32 バイト...」Base64 文字列が正しく 32 バイトにデコードされるか確認 (下の確認コマンド参照)
DB ファイルパスの親フォルダが作れない起動ユーザー (サービスアカウント) の権限を確認
Windows Service が起動しないイベントビューアの Application ログ、または直接実行してエラーを確認
 
Get-EventLog -LogName Application -Source "Watashi.Server" -Newest 20
& "C:\Program Files\Watashi\Server\Watashi.Server.exe"

ホスト登録 (CIFS 登録) で HTTP 500

例外が Encryption:MasterKey は Base64 でエンコードされた値である必要があります の場合、MasterKey がプレースホルダのままか、Base64 ではない値です。

EncryptionService は Singleton + 初回利用時解決のため、サーバーの起動自体は通り、CIFS パスワード暗号化が初めて走るホスト登録時に失敗します。4-3 で 32 バイト Base64 を生成して差し替え、サーバーを再起動してください。
$key = "<appsettings.json に入れている値>"
try { $b = [Convert]::FromBase64String($key); "OK: $($b.Length) bytes" } catch { "NG: $($_.Exception.Message)" }
# → "OK: 32 bytes" でないと受理されない

ログインできない

症状原因と対処
ロックされている連続失敗 (既定 15 回) でロック。管理画面で解除、または DB を直接更新:
UPDATE Users SET IsLocked=0, FailedLoginCount=0 WHERE Username='alice';
パスワード期限切れMustChangePassword=true になりレスポンスにフラグが付く。クライアントは強制変更画面へ遷移する
429 Too Many Requestsログイン試行が 1 分あたり 10 回を超えた。Auth:LoginPerMinutePerIp を緩めるか時間を空ける
初回設定待ちなのにパスワード入力へ進むWindows 統合認証が無効・不成立のときの安全なフォールバック。IIS で匿名認証と Windows 認証が両方有効か確認し、/api/auth/win の場所別 Location は作成しない
大文字小文字違いのユーザー名同一ユーザーとして扱う。アップグレード migration が重複を検出して停止した場合は、該当ユーザーを統合してから再実行

自動ログイン / トークン関連

症状原因と対処
自動ログインが効かない① 接続が HTTP で Auth:AllowHttpForAutoLogin=false → HTTPS に切り替える。② Credential Manager から消えている → 再度「このPCを記憶する」をチェック。③ 管理者がデバイスを失効済み → 管理画面 → 信頼デバイスで確認
token_reuse_detected でリフレッシュ失敗失効済みリフレッシュトークンが提示された。ファミリー全体が失効するため再ログインが必要。同じトークンを別端末から使った / ログアウト後に再生された等が原因。該当ユーザーの全 active セッションが切断されるので、頻発する場合は配布ログを確認
操作中に「再ログインしてください」パスワード変更・初回設定への差し戻し・管理者権限変更・アカウントロックは、発行済み access token にも次の API 呼び出しで反映される。理由 (password_changed / account_locked / device_revoked / token_reuse_detected) を確認

Agent 関連

症状原因と対処
Agent が Unhealthy のまま① サービス起動確認 (Get-Service Watashi.Agent)。② Agent 側ログで heartbeat 送信を確認。③ Agent → 中央の送信がファイアウォールで許可されているか。④ ExecutionNodes.Name と Agent:AgentId が大文字小文字含めて一致しているか。⑤ (mTLS) サムプリントの一致
Agent から 401 / 403 が返る(mTLS) Auth:CentralCertificateThumbprint が中央の提示する証明書と一致しているか。(HTTP) SharedSecret を両側で同じ値にしたか。いずれも未設定だと匿名アクセスは拒否されます

ファイル操作

症状原因と対処
ファイル一覧が空 / 403① ユーザー権限が登録されているか (管理画面 → ユーザー権限)。② AllowedPath とリクエストパスの関係。③ CIFS 資格情報 (管理画面 → ホスト → 接続テスト)
操作が遅い / SMB ハンドシェイクが頻発Cifs:SessionIdleSeconds を伸ばす (60 → 120)。Cifs:MaxSessionsPerKey を増やす (4 → 8)
「リネームでは親ディレクトリを変更できません」仕様。同一フォルダ内でのリネームのみ許可し、フォルダ間の移動は禁止 (DELETE 権限の抜け穴対策)
転送中にキャンセルしたい転送センターから個別/全体キャンセル、一時停止、失敗項目の再試行が可能。キューは再起動後も復元される
