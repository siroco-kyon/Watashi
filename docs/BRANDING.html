01 / Choose a path

最初に、目的を選びます

「1つのアプリの名前を変える」のか、「A版とB版を同じPCで同時利用する」のかで 必要な変更範囲が違います。

通常の改名

1種類だけ配布する

画面表示名、ClickOnceの製品名、アイコンを変更します。exe名の変更は任意です。

読む章: 2・4・5

A/B共存

2種類を同じPCへ入れる

見た目だけでなく、ClickOnce ID、配布URL、資格情報なども分離します。

読む章: 2〜5に加えて7が必須

変えたいもの主な対象A/B共存
画面・ホバーに出る名前XAMLのWindow.Title別名必須
exeファイル名Watashi.Client.csproj別名推奨
インストール名ClickOnceProfile.pubxml別名必須
タスクバーのグループClickOnceマニフェストID別ID必須
接続先と更新先deployment.json・配布URL完全分離
人が見分けるアイコンWatashi.icoなど色分け推奨

02 / Display name

画面とタスクバーのホバー表示

WPFのWindow.Titleが、各ウィンドウのタイトルとタスクバーのホバー表示に使われます。 A版ならWatashi-a、B版ならWatashi-bへ変更します。

ファイル表示される場所現在値
Views/SplashWindow.xaml起動中Title="Watashi - 起動中"
Views/LoginWindow.xamlログインTitle="Watashi - ログイン"
Views/MainWindow.xamlメイン・通常時のホバーTitle="Watashi"
Views/Admin/AdminWindow.xaml管理画面Title="Watashi - 管理"
Views/InitialPasswordWindow.xaml初回パスワード設定Title="Watashi - 初回パスワード設定"
Views/MaintenanceWindow.xamlメンテナンス案内のタイトル・見出しTitle="Watashi - メンテナンスのご案内" / Text="Watashi"
Views/AboutWindow.xamlバージョン情報のアプリ名・コピー内容Text="Watashi"
Themes/Icons.xaml画面内のロゴ文字Text="Watashi"
App.xaml.csダイアログ"Watashi - …"

バージョン情報のコピー内容は、AboutWindow.xamlのアプリ名を参照します。名前変更スクリプトで見出しを変更するとコピー内容にも反映されます。補足文字「CIFS ファイル管理」は自動置換の対象外です。必要に応じてMainWindow.xaml、LoginWindow.xaml、SplashWindow.xaml、AboutWindow.xamlを変更してください。

鳥居以外のブランドにする場合は、AboutWindow.xamlの初期メッセージとボタンの読み上げ名、AboutWindow.xaml.csのひとことも確認してください。「鳥居をくぐって、信頼できる場所へ。」などの文言は名前変更スクリプトでは変更されません。画像はThemes/Icons.xamlのToriiIconを参照します。

一括置換スクリプト

# 変更内容だけ確認
powershell -NoProfile -File scripts/Rename-Brand.ps1 `
  -NewName "Watashi-a" -WhatIf

# 問題なければ適用
powershell -NoProfile -File scripts/Rename-Brand.ps1 `
  -NewName "Watashi-a"
タイトル変更だけではグループは分かれません。 ホバー文字はA/Bになっても、ClickOnceの内部IDが同じなら Watashi (2)のようにまとめられます。A/B共存では7章も実施します。

03 / Executable identity

exe名と製品プロパティ

現在はAssemblyNameが未設定なので、出力名は Watashi.Client.exeです。通常の改名では任意ですが、 A/B共存ではClickOnceのアプリケーションマニフェストIDを分けるため、別名を推奨します。

発行プロファイルをA/Bで分ける運用では、AssemblyNameは各.pubxmlに書きます。 csprojに書くと発行のたびに手で書き換えることになります。

A版のプロファイル

<AssemblyName>WatashiA.Client</AssemblyName>
<BrandId>Watashi-a</BrandId>
<Product>Watashi-a</Product>
<AssemblyTitle>Watashi-a</AssemblyTitle>

B版のプロファイル

<AssemblyName>WatashiB.Client</AssemblyName>
<BrandId>Watashi-b</BrandId>
<Product>Watashi-b</Product>
<AssemblyTitle>Watashi-b</AssemblyTitle>
csprojで$(BrandId)を条件にAssemblyNameを切り替えることはできません。 MSBuildはプロパティを記述順に評価し、.pubxmlはcsproj本文より後に importされます。そのためcsprojのプロパティは.pubxmlの値を参照できず、条件が常に偽になります。 一方項目 (ItemGroup) は全プロパティの評価後に処理されるため、 <AssemblyMetadata Include="BrandId" Value="$(BrandId)" />は.pubxmlの値を拾えます。 これが「BrandIdは.pubxmlで効くのにAssemblyNameの条件分岐は効かない」理由です。
他プロジェクトをプロパティ汚染から守る（対応済み）。 VSの「発行」は、発行するプロジェクトの値をソリューション全体のビルド/復元へグローバルに波及させます。 無防備だと他プロジェクトが巻き込まれ、AssemblyName汚染で Ambiguous project name、それを直すと次はOutputType汚染で CS5001（エントリポイントのMainが無い）と、順に失敗します。 コマンドラインからプロジェクトを指定して発行した場合はビルド範囲が狭いため再現しません。 「VSの発行だけ失敗し、コマンドラインなら通る」という切り分けになったらこれを疑ってください。 対策としてWatashi.Client以外の4プロジェクトに TreatAsLocalProperty="AssemblyName;OutputType"と、各プロジェクト本来の値を入れてあります。 新しいプロジェクトを追加する場合も同じ指定が必要です。
プロジェクト本来のOutputType
Watashi.SharedLibrary
Watashi.Server / Watashi.Agent / Watashi.TestsExe
Watashi.Client（ブランドを受け取る側）WinExe — 防御しない
内部IDはASCIIで。 表示名には任意の文字を使えますが、AssemblyNameやURL、マニフェスト名には 全角のｂではなくASCIIのBを使います。

05 / Icon & color

アイコンとブランドカラー

アイコンは「exe・タスクバー・ClickOnce用の.ico」と 「画面内で描画するXAML」の2系統です。外側だけでなく画面内も揃える場合は両方変更します。 色はライト用（Colors.Light.xaml）とダーク用（Colors.Dark.xaml）に分かれています。 両パレットを同じブランド色相で調整し、固定画像の.ico生成スクリプトも合わせます。

5-1. どこを変えると何が変わるか

変えたいもの編集するファイル具体的な場所反映先
exe・タスクバー・インストーラのアイコン src/Watashi.Client/Watashi.ico 同名で上書き。別名にするならWatashi.Client.csprojとClickOnceProfile.pubxmlの<ApplicationIcon>2箇所も更新 exe、ショートカット、タスクバー、インストーラ、スタートメニュー
画面内ロゴの形 src/Watashi.Client/Themes/Icons.xaml ToriiIcon（通常）とToriiIconLight（濃色背景用）のジオメトリ。座標系は64×64 スプラッシュ、ログイン、メイン、管理の各ロゴとウィンドウ左上
ツール全体の色 Colors.Light.xaml＋Colors.Dark.xaml 両ファイルのAccentColor／AccentHoverColor／AccentPressedColor／AccentSoftColor／AccentDeepColor＋FocusColor 主ボタン、入力欄のフォーカス枠、選択行、リンク文字、見出しの強調、画面内ロゴの色
.icoの色 scripts/Generate-ToriiIcon.ps1 先頭付近の$ACCENT／$ACCENT_DEEPの2行 再生成したWatashi.ico（＝タスクバー等）
色を変えるときIcons.xamlは触りません。 鳥居の各パーツは色を直書きせず{StaticResource AccentBrush}／AccentDeepBrushを参照しているため、 ライト／ダークのパレットを変えると画面内ロゴの色も追従します。 もう1つのToriiIconLightはTextOnAccentBrush（白）固定の濃色背景用ですが、 現状どの画面からも参照されていません（ToriiLogo／ToriiLogoLightテンプレートも未使用）。 色替えでは無視して構いません。形を変えるときだけ、後で使ったときにズレないよう合わせて直します。

5-2. ツールの色を変える（最短手順）

Colors.Light.xamlの6行を新しい色に置き換える
Colors.Dark.xamlに同じ色相の高コントラスト版を用意する
Generate-ToriiIcon.ps1の$ACCENT／$ACCENT_DEEPを同じ値にする
スクリプトを実行して.icoを再生成する
リビルドして各画面とタスクバーを目視確認する

① Themes/Colors.Light.xaml（瑠璃色に変える例）

<!-- ===== ボーダー ===== -->
<Color x:Key="FocusColor">#1D48C9</Color>          <!-- 旧 #C73E1D / AccentColor と同値にする -->

<!-- ===== アクセント ===== -->
<Color x:Key="AccentColor">#1D48C9</Color>         <!-- 旧 #C73E1D 基本色 -->
<Color x:Key="AccentHoverColor">#163AA7</Color>    <!-- 旧 #A83216 ホバー -->
<Color x:Key="AccentPressedColor">#11308D</Color>  <!-- 旧 #8C2911 押下 -->
<Color x:Key="AccentSoftColor">#E1E7F9</Color>     <!-- 旧 #F9E5E0 選択行・淡い背景 -->
<Color x:Key="AccentDeepColor">#0B1F5B</Color>     <!-- 旧 #5C1A0B 濃色・鳥居の島木 -->

Colors.xamlは共通ブラシとパレット読込だけを持つため変更しません。 続けてColors.Dark.xamlの同じ6キーを同じ色相で調整します。暗背景ではライト側の値を そのままコピーせず、アクセントと文字が十分に判別できる明度にしてください。

② scripts/Generate-ToriiIcon.ps1（Colors.Light.xamlと同じ値に）

# Mirrors Colors.Light.xaml: AccentColor and AccentDeepColor.
$ACCENT      = [System.Drawing.Color]::FromArgb(0xFF, 0x1D, 0x48, 0xC9)   # = #1D48C9
$ACCENT_DEEP = [System.Drawing.Color]::FromArgb(0xFF, 0x0B, 0x1F, 0x5B)   # = #0B1F5B

③ 再生成と④ 確認

# .ico を再生成（src/Watashi.Client/Watashi.ico を上書き）
powershell.exe -NoProfile -File scripts/Generate-ToriiIcon.ps1

# ビルドして起動確認
dotnet build src\Watashi.Client\Watashi.Client.csproj
ライト／ダーク両パレットとGenerate-ToriiIcon.ps1は必ずセットで直します。 片方だけ変えると、画面内のロゴとタスクバーのアイコンで色が食い違います。 .icoを差し替えるだけなら両パレットは変わらず、ボタンなどUIの色は元のままです。

ライトパレット6値の決め方

既定の朱と同じトーンを保つなら、色相（Hue）だけを変えて彩度・明度は下表のまま使います。 AccentDeepColorとAccentColorは.icoの配色にもそのまま使われます。

キーHSL（Hは共通）朱＝既定瑠璃＝Hue 225の例用途
AccentColorS 75% / L 45%#C73E1D#1D48C9主ボタン、強調文字、鳥居の柱
AccentHoverColorS 77% / L 37%#A83216#163AA7主ボタンのホバー

色相を決めれば、6値はこのスニペットで出せます（貼り付けて実行するだけ）。

$hue = 225   # 使いたい色相 (0-359)。5-4 の表の Hue を入れると同梱アイコンと一致します

function Get-BrandHex([double]$h, [double]$s, [double]$l) {
    $c = (1 - [Math]::Abs(2 * $l - 1)) * $s
    $x = $c * (1 - [Math]::Abs((($h / 60) % 2) - 1))
    $m = $l - $c / 2
    switch ([Math]::Floor($h / 60) % 6) {
        0 { $r, $g, $b = $c, $x, 0 }
        1 { $r, $g, $b = $x, $c, 0 }
        2 { $r, $g, $b = 0, $c, $x }
        3 { $r, $g, $b = 0, $x, $c }
        4 { $r, $g, $b = $x, 0, $c }
        5 { $r, $g, $b = $c, 0, $x }
    }
    '#{0:X2}{1:X2}{2:X2}' -f [int][Math]::Round(($r + $m) * 255),
                             [int][Math]::Round(($g + $m) * 255),
                             [int][Math]::Round(($b + $m) * 255)
}

'AccentColor        {0}' -f (Get-BrandHex $hue 0.75 0.45)
'AccentHoverColor   {0}' -f (Get-BrandHex $hue 0.77 0.37)
'AccentPressedColor {0}' -f (Get-BrandHex $hue 0.78 0.31)
'AccentSoftColor    {0}' -f (Get-BrandHex $hue 0.68 0.93)
'AccentDeepColor    {0}' -f (Get-BrandHex $hue 0.79 0.20)
'FocusColor         {0}' -f (Get-BrandHex $hue 0.75 0.45)
既定の朱だけは手調整済みです。 Hue 12を入れると#C93F1Dのように現在値（#C73E1D）と1〜2ずれます。 既存の朱を復元したい場合は式ではなく上表の値をそのまま使ってください。

5-3. アイコンの絵柄を変える

まず、やりたいことがどれかを決めます。ここを取り違えると触るファイルが変わります。

やりたいこと触るもの手順
鳥居のまま色だけ変えたいColors.Light.xaml＋Colors.Dark.xaml＋Generate-ToriiIcon.ps15-2
環境ごとに色を分けたい（絵柄は鳥居）同梱.icoをコピーするだけ5-4
用意した画像／ロゴに差し替えたいWatashi.ico＋Icons.xaml5-3-A
鳥居の形を自分で描き直したいIcons.xaml＋Generate-ToriiIcon.ps1の描画コード5-3-B
アイコンは2つあります。 ①exeに埋め込む.ico（タスクバー・エクスプローラ・インストーラ）と ②アプリが画面に描く画像（各ウィンドウの左上とロゴ）は別のファイルです。 片方だけ変えると、タスクバーは新しいのに画面内は鳥居のまま、といった食い違いになります。

5-3-A. 用意した画像に差し替える

.icoを作ってWatashi.icoを上書き（＝タスクバー側）
PNGをプロジェクトに追加してResource指定（＝画面内側）
Icons.xamlのToriiIconを画像参照に置き換え
リビルドして全画面とタスクバーを確認

① .icoを差し替える

  • 16／24／32／48／64／128／256 px を含むマルチサイズ・背景透過の.icoを用意する（単一サイズだと縮小時にぼやけます）
  • src/Watashi.Client/Watashi.ico を同じ名前で上書きする。名前を変えたい場合はWatashi.Client.csprojとClickOnceProfile.pubxmlの<ApplicationIcon>2箇所も直す

② 画面内用のPNGをプロジェクトに追加する

画像はsrc/Watashi.Client/Assets/logo.pngのように置き（256px程度・透過PNG推奨）、 csprojにResourceとして明示的に追加します。 WPFのSDKが自動で拾うのは.xamlだけで、画像は自動では含まれません。 

<!-- Watashi.Client.csproj -->
<ItemGroup>
  <Resource Include="Assets\logo.png" />
</ItemGroup>

③ Themes/Icons.xamlのToriiIconを置き換える

<DrawingImage x:Key="ToriiIcon">…</DrawingImage>のブロックごと、次の1行に置き換えます。 x:Keyの名前は変えないこと——変えると参照している8ファイル・11箇所すべての修正が必要になります。 名前さえ保てば、参照側（各ウィンドウのIcon属性と<Image>）は1箇所も直さずに全画面へ反映されます。 

<BitmapImage x:Key="ToriiIcon"
             UriSource="pack://application:,,,/Assets/logo.png" />

濃色背景用のToriiIconLightも同じ要領で白抜き版に差し替えられます （現状どの画面からも参照されていないため、急ぐ場合は後回しで構いません）。

別画像にしたら、鳥居用のスクリプトはもう使いません。 Generate-ToriiIcon.ps1を実行するとWatashi.icoが鳥居に戻ります。 assets/icons/の色違い（5-4）も鳥居の絵柄なので使えなくなります。 環境ごとの色分けを続けたい場合は、新しい絵柄でも色違いの.icoを自分で用意してください。

環境ごとの適用手順

  1. deployment.jsonのserverUrlをその環境の中央サーバにする
  2. 選んだ色でWatashi.icoを上書き
    Copy-Item assets\icons\Watashi-blue.ico src\Watashi.Client\Watashi.ico -Force
  3. 画面内の色も揃えるなら5-2の手順でライト／ダーク両パレットを同じ色相に変更（.icoだけならこの手順は不要）
  4. ClickOnceを再発行（マニフェストがハッシュ検証するため再発行は必須）
  5. 発行後に既定へ戻す
    Copy-Item assets\icons\Watashi-shu.ico src\Watashi.Client\Watashi.ico -Force（git restore src/Watashi.Client/Watashi.icoでも可）
# 色を追加したいとき（$variants に名前と Hue を足して実行）
powershell.exe -NoProfile -File scripts/Generate-ToriiIconVariants.ps1
手順2の上書きは発行作業中だけの一時変更です。コミットしないでください。 コミットするとリポジトリの既定アイコンがその色に置き換わります。 分からなくなってもWatashi-shu.icoからのコピー、git restore、 Generate-ToriiIcon.ps1の再実行のどれでも朱色に戻せます。

5-5. 変えたのに反映されないとき

症状確認する場所
ボタンなどUIの色が変わらない表示中テーマに対応するColors.Light.xaml／Colors.Dark.xamlの<Color>行を直したか
ライトだけ／ダークだけ旧色のままもう一方のパレットの変更漏れ。Colors.xaml自体には色値を置かない
画面内ロゴだけ古い色同上。ロゴはAccentBrush／AccentDeepBrush経由
タスクバーのアイコンだけ古い色Generate-ToriiIcon.ps1の再実行漏れ、または.icoのコピー漏れ
フォーカス枠だけ前の色FocusColorの変更漏れ
ビルドしてもexeのアイコンが古いbin／objを消してリビルド。ClickOnce配布分は再発行が必要
画像に差し替えたのに画面内が鳥居のままIcons.xamlのToriiIconを置き換えたか。.icoだけでは画面内は変わらない（5-3-A）
差し替えた画像が表示されない・ビルドエラーcsprojの<Resource Include="…" />の追加漏れ、またはUriSourceのパス誤り
ToriiIconLightだけ古いまま現状どの画面からも参照されていないため実害なし。形を変えたときは合わせて更新
色分けは人のための目印です。 アイコンを変えてもWindowsのアプリIDは変わりません。 Watashi (2)を解消するにはClickOnce IDを分けます。

7-3. deployment.json

接続先と更新先は同じ版で揃えます。A版からB版のマニフェストを参照させてはいけません。

  "serverUrl": "https://server-b.internal",
  "updateManifestUrl":
    "https://host/install/watashi-b/WatashiB.Client.application"
}

7-4. AppUserModelIDの扱い

WindowsはAppUserModelIDでタスクバーのウィンドウをグループ化します。 このプロジェクトはClickOnce配布なので、AppUserModelIDはClickOnceに管理させます。

アプリ側で明示的なAppUserModelIDを設定しないでください。 SetCurrentProcessExplicitAppUserModelIDを追加すると、 ClickOnceが割り当てるIDと競合して予期しない結果になる可能性があります。 A/BのマニフェストIDを分け、ClickOnceから別アプリとしてインストールするのが正しい対応です。

参考: Microsoft Learn: Application User Model IDs / ClickOnce application manifest

7-5. 発行後のマニフェスト確認

最上位の*.applicationと、 Application Files内の*.manifestを比較します。 次のようにassemblyIdentityがA/Bで異なる必要があります。

A版

<assemblyIdentity
  name="WatashiA.Client.application"
  ... />

B版

<assemblyIdentity
  name="WatashiB.Client.application"
  ... />
生成物を直接編集しません。 マニフェストを手作業で改名・編集すると署名とハッシュが壊れます。 元の設定を直して再発行します。

7-6. ローカル状態の分離 (BrandId)

ローカル状態の保存先は、ビルド時プロパティBrandIdで版ごとに分離します。 Services/Brand.csがアセンブリに焼き込まれた値を読み、次の3つを決めます。 既定値はWatashiのため、1種類だけを配布する通常の改名では設定不要です。

対象保存先該当ファイル
設定%LOCALAPPDATA%\{BrandId}\settings.jsonServices/AppSettings.cs
ログ%LOCALAPPDATA%\{BrandId}\logs\Services/AppLog.cs
資格情報{BrandId}/AutoLoginServices/CredentialStore.cs
共通のままだと自動ログインが相互に壊れます。 資格情報ターゲットはWindows資格情報マネージャーの1スロットを奪い合います。 デバイストークンは各中央サーバのDBに個別保存されるため、A版のトークンはB版のサーバでは検証を通りません。 結果、B側の保存でA側のトークンが消え、次にA版を起動すると401を受けて ClearDeviceToken()が走り、B側のトークンまで消えます。 以降A/Bが互いの自動ログインを潰し合い、毎回手動ログインになります。

方法1: 発行プロファイルに書く（Visual Studioから発行する場合はこちら）。 AssemblyNameと同じ.pubxmlに併記します。ブランド固有の値が1ファイルに揃うため、 「URLはBに変えたのにBrandIdを付け忘れた」という取り違えが起きません。 VSの「発行」画面でプロファイルを選ぶだけで反映され、コマンドは不要です。 

<BrandId>Watashi-b</BrandId>

方法2: コマンドラインで渡す。/p:はグローバルプロパティとして最優先で効き、プロファイルの記述も上書きします。

MSBuild.exe src\Watashi.Client\Watashi.Client.csproj /t:Publish `
  /p:Configuration=Release /p:PublishProfile=ClickOnceProfile `
  /p:BrandId=Watashi-b
既存配布のBrandIdは変更しないこと。 現行ツールは未指定（=Watashi）のまま発行し、新ブランド側にだけ新しい値を与えます。 現行側も変えると既存利用者全員が設定と自動ログインを1回失います （再ログインで復旧しますが問い合わせの原因になります）。
配布BrandId保存先
現行（既存利用者）指定しない%LOCALAPPDATA%\Watashi\（現状維持）
新ブランドWatashi-b%LOCALAPPDATA%\Watashi-b\

A/B双方で「このPCを記憶」した後、資格情報が2件に分かれていることを確認します。 

cmdkey /list | findstr /i AutoLogin

7-7. 設定を自動で点検する

発行前の確認はscripts/Check-BrandSetup.ps1で自動化できます。 読み取り専用で、リポジトリを書き換えません。問題があれば終了コード1を返します。 

powershell -NoProfile -File scripts/Check-BrandSetup.ps1
#点検項目
1リポジトリがクラウド同期フォルダ（OneDrive等）配下にないか
2.csprojの重複・競合コピーがないか
3.slnにプロジェクト名の重複がないか
4AssemblyNameが複数ファイルで重複していないか
5ブランド別プロファイルにBrandIdが漏れていないか・重複していないか
6他プロジェクトにAssemblyName／OutputTypeの防御が入っているか

7-8. 症状から確認場所を探す

症状主な確認箇所
VSの発行でだけAmbiguous project nameやCS5001（コマンドラインは通る）他プロジェクトのTreatAsLocalProperty防御が抜けている。当面はコマンドラインから発行すれば回避できる。7-7のスクリプトで検出可能
MSB3030 ... runtimeconfig.json は見つからなかったためコピーできません上と同じOutputType汚染の二次症状。単独では追わないこと
コマンドラインでもAmbiguous project name同じAssemblyNameを宣言したファイルが2つ以上ある。.csprojの重複・競合コピーも疑う
Watashi (2)になるAssemblyName、両マニフェストのassemblyIdentity、旧ピン留め
片方を入れるともう片方が置き換わるClickOnce IDと配布URL
片方がもう片方として更新されるUpdateUrlとupdateManifestUrl
ホバー名だけWatashiのままXAMLのWindow.Titleと古いビルド成果物
自動ログインが解除されるBrandIdの指定漏れ（A/Bが同じ資格情報ターゲットを共有）
設定・ログが混ざるBrandIdの指定漏れ
ビルドは通るのにXDG0008が出るXAMLデザイナー由来。クリーン後にビルドすれば消える。エラー一覧のフィルタを「ビルドのみ」にすると実害の有無が分かる
