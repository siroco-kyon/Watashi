01 / Choose a path

最初に、目的を選びます

「1つのアプリの名前を変える」のか、「A版とB版を同じPCで同時利用する」のかで 必要な変更範囲が違います。

通常の改名

1種類だけ配布する

画面表示名、ClickOnceの製品名、アイコンを変更します。exe名の変更は任意です。

読む章: 2・4・5

A/B共存

2種類を同じPCへ入れる

見た目だけでなく、ClickOnce ID、配布URL、資格情報なども分離します。

読む章: 2〜5に加えて7が必須

変えたいもの主な対象A/B共存
画面・ホバーに出る名前XAMLのWindow.Title別名必須
exeファイル名Watashi.Client.csproj別名推奨
インストール名ClickOnceProfile.pubxml別名必須
タスクバーのグループClickOnceマニフェストID別ID必須
接続先と更新先deployment.json・配布URL完全分離
人が見分けるアイコンWatashi.icoなど色分け推奨

02 / Display name

画面とタスクバーのホバー表示

WPFのWindow.Titleが、各ウィンドウのタイトルとタスクバーのホバー表示に使われます。 A版ならWatashi-a、B版ならWatashi-bへ変更します。

ファイル表示される場所現在値
Views/SplashWindow.xaml起動中Title="Watashi - 起動中"
Views/LoginWindow.xamlログインTitle="Watashi - ログイン"
Views/MainWindow.xamlメイン・通常時のホバーTitle="Watashi"
Views/Admin/AdminWindow.xaml管理画面Title="Watashi - 管理"
Themes/Icons.xaml画面内のロゴ文字Text="Watashi"
App.xaml.csダイアログ"Watashi - …"

一括置換スクリプト

# 変更内容だけ確認
powershell -NoProfile -File scripts/Rename-Brand.ps1 `
  -NewName "Watashi-a" -WhatIf

# 問題なければ適用
powershell -NoProfile -File scripts/Rename-Brand.ps1 `
  -NewName "Watashi-a"
タイトル変更だけではグループは分かれません。 ホバー文字はA/Bになっても、ClickOnceの内部IDが同じなら Watashi (2)のようにまとめられます。A/B共存では7章も実施します。

03 / Executable identity

exe名と製品プロパティ

現在はAssemblyNameが未設定なので、出力名は Watashi.Client.exeです。通常の改名では任意ですが、 A/B共存ではClickOnceのアプリケーションマニフェストIDを分けるため、別名を推奨します。

A版

<AssemblyName>WatashiA.Client</AssemblyName>
<Product>Watashi-a</Product>
<AssemblyTitle>Watashi-a</AssemblyTitle>

B版

<AssemblyName>WatashiB.Client</AssemblyName>
<Product>Watashi-b</Product>
<AssemblyTitle>Watashi-b</AssemblyTitle>
内部IDはASCIIで。 表示名には任意の文字を使えますが、AssemblyNameやURL、マニフェスト名には 全角のｂではなくASCIIのBを使います。

04 / ClickOnce

配布物・インストーラの名前

プロパティ主な効果A/B共存時
ProductNameスタートメニュー、インストーラ、「アプリと機能」別名
PublisherName発行元会社名なら共通でも可
SuiteNameスタートメニューのグループ同じフォルダなら共通でも可
ApplicationIconショートカットとインストーラのアイコン色分け推奨
PublishUrl発行先A/Bで分離
InstallUrl・UpdateUrlインストール・更新先A/Bで分離
ProductNameだけでは別アプリになりません。 A/B共存では、AssemblyName、生成されたassemblyIdentity、 配布・更新URLも別にします。

発行設定の例

A版

<PublishUrl>\\fileserver\share\Watashi-a\</PublishUrl>
<InstallUrl>https://host/install/watashi-a/</InstallUrl>
<UpdateUrl>https://host/install/watashi-a/</UpdateUrl>
<ProductName>Watashi-a</ProductName>

B版

<PublishUrl>\\fileserver\share\Watashi-b\</PublishUrl>
<InstallUrl>https://host/install/watashi-b/</InstallUrl>
<UpdateUrl>https://host/install/watashi-b/</UpdateUrl>
<ProductName>Watashi-b</ProductName>

05 / Icon & color

アイコンとブランドカラー

アイコンは「exe・タスクバー・ClickOnce用の.ico」と 「画面内で描画するXAML」の2系統です。外側だけでなく画面内も揃える場合は両方変更します。

対象変更箇所
exe・タスクバー・インストーラWatashi.icoと両方のApplicationIcon
画面内の鳥居Themes/Icons.xaml
画面内のブランドカラーThemes/Colors.xaml
ico生成色scripts/Generate-ToriiIcon.ps1

同梱している色違い

朱 橙 山吹 若草 常磐 青碧 浅葱 瑠璃 菫 紫 躑躅 
# アイコンを生成
powershell.exe -NoProfile -File scripts/Generate-ToriiIcon.ps1

# 色違い一式を生成
powershell.exe -NoProfile -File scripts/Generate-ToriiIconVariants.ps1
色分けは人のための目印です。 アイコンを変えてもWindowsのアプリIDは変わりません。 Watashi (2)を解消するにはClickOnce IDを分けます。

以下は見た目ではなく運用識別子です。通常の改名では変更不要ですが、 A/Bのローカル状態を完全に独立させる場合はクライアント保存先を分けます。

クライアントログ%LOCALAPPDATA%\{BrandId}\logs\BrandIdで分離（7-6）

07 / Side-by-side deployment

A版・B版を同じPCで共存させる

症状: ショートカット名をWatashi-a／Watashi-bにしても、 タスクバーではWatashi／Watashi (2)になる。 これは見た目の名前ではなく、A/BのClickOnce内部IDが同じ可能性が高い状態です。

設定A版の例B版の例重要度
画面表示名Watashi-aWatashi-b必須
AssemblyNameWatashiA.ClientWatashiB.Client必須
ProductNameWatashi-aWatashi-b必須
発行・更新URL/watashi-a//watashi-b/必須
更新マニフェストWatashiA.Client.applicationWatashiB.Client.application必須
serverUrlA中央サーバB中央サーバ必須
BrandId（発行時/p:）指定しない（既定）Watashi-b必須

資格情報ターゲットWatashi/AutoLoginWatashi-b/AutoLogin↑で自動
アイコン例: 朱例: 瑠璃推奨

7-3. deployment.json

接続先と更新先は同じ版で揃えます。A版からB版のマニフェストを参照させてはいけません。

A版

{
  "serverUrl": "https://server-a.internal",
  "updateManifestUrl":
    "https://host/install/watashi-a/WatashiA.Client.application"
}

B版

{
  "serverUrl": "https://server-b.internal",
  "updateManifestUrl":
    "https://host/install/watashi-b/WatashiB.Client.application"
}

7-4. AppUserModelIDの扱い

WindowsはAppUserModelIDでタスクバーのウィンドウをグループ化します。 このプロジェクトはClickOnce配布なので、AppUserModelIDはClickOnceに管理させます。

アプリ側で明示的なAppUserModelIDを設定しないでください。 SetCurrentProcessExplicitAppUserModelIDを追加すると、 ClickOnceが割り当てるIDと競合して予期しない結果になる可能性があります。 A/BのマニフェストIDを分け、ClickOnceから別アプリとしてインストールするのが正しい対応です。

参考: Microsoft Learn: Application User Model IDs / ClickOnce application manifest

7-5. 発行後のマニフェスト確認

最上位の*.applicationと、 Application Files内の*.manifestを比較します。 次のようにassemblyIdentityがA/Bで異なる必要があります。

A版

<assemblyIdentity
  name="WatashiA.Client.application"
  ... />

B版

<assemblyIdentity
  name="WatashiB.Client.application"
  ... />
生成物を直接編集しません。 マニフェストを手作業で改名・編集すると署名とハッシュが壊れます。 元の設定を直して再発行します。

7-6. ローカル状態の分離 (BrandId)

ローカル状態の保存先は、ビルド時プロパティBrandIdで版ごとに分離します。 Services/Brand.csがアセンブリに焼き込まれた値を読み、次の3つを決めます。 既定値はWatashiのため、1種類だけを配布する通常の改名では設定不要です。

対象保存先該当ファイル
設定%LOCALAPPDATA%\{BrandId}\settings.jsonServices/AppSettings.cs
ログ%LOCALAPPDATA%\{BrandId}\logs\Services/AppLog.cs
資格情報{BrandId}/AutoLoginServices/CredentialStore.cs
共通のままだと自動ログインが相互に壊れます。 資格情報ターゲットはWindows資格情報マネージャーの1スロットを奪い合います。 デバイストークンは各中央サーバのDBに個別保存されるため、A版のトークンはB版のサーバでは検証を通りません。 結果、B側の保存でA側のトークンが消え、次にA版を起動すると401を受けて ClearDeviceToken()が走り、B側のトークンまで消えます。 以降A/Bが互いの自動ログインを潰し合い、毎回手動ログインになります。

発行時にコマンドラインで指定します（グローバルプロパティとして最優先で効きます）。

MSBuild.exe src\Watashi.Client\Watashi.Client.csproj /t:Publish `
  /p:Configuration=Release /p:PublishProfile=ClickOnceProfile `
  /p:BrandId=Watashi-b
既存配布のBrandIdは変更しないこと。 現行ツールは未指定（=Watashi）のまま発行し、新ブランド側にだけ新しい値を与えます。 現行側も変えると既存利用者全員が設定と自動ログインを1回失います （再ログインで復旧しますが問い合わせの原因になります）。
配布BrandId保存先
現行（既存利用者）指定しない%LOCALAPPDATA%\Watashi\（現状維持）
新ブランドWatashi-b%LOCALAPPDATA%\Watashi-b\

A/B双方で「このPCを記憶」した後、資格情報が2件に分かれていることを確認します。 

cmdkey /list | findstr /i AutoLogin

7-7. 症状から確認場所を探す

症状主な確認箇所
Watashi (2)になるAssemblyName、両マニフェストのassemblyIdentity、旧ピン留め
片方を入れるともう片方が置き換わるClickOnce IDと配布URL
片方がもう片方として更新されるUpdateUrlとupdateManifestUrl
ホバー名だけWatashiのままXAMLのWindow.Titleと古いビルド成果物

設定・ログが混ざる発行時の/p:BrandId指定漏れ

08 / Verification

変更後の確認チェックリスト

通常の改名

  • クライアントをリビルドした
  • ログイン・メイン・管理画面の表示名を確認した
  • exeとタスクバーのアイコンを確認した
  • ClickOnceを再発行した
  • スタートメニューと「アプリと機能」の名前を確認した

A/B共存

  • 旧Watashi・試作A/B版をアンインストールした
  • 古いタスクバーのピン留めを外した
  • A/BのassemblyIdentityが異なることを確認した
  • A版をA専用URL、B版をB専用URLからインストールした
  • A/B同時起動時にタスクバーが2グループへ分かれた
  • ホバー表示がWatashi-a／Watashi-bになった
  • 各版が自分の更新URLと中央サーバだけを参照した
  • A/Bの自動ログイン資格情報が互いに上書きされなかった
完了条件: A/Bを同時起動したとき、別々のタスクバーボタン・名前・アイコンで表示され、 更新先・接続先・資格情報が相互干渉しないこと。
