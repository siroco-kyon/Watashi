⛩ Watashi API直接利用ガイド

WPFクライアントをインストールせずに、HTTPS API を直接呼び出して社内ファイルサーバーとファイルをやり取りする方法を説明します。認証・権限チェック・監査ログの記録は、クライアントを使った場合とまったく同じです。

0このガイドについて

本書は、Watashi の WPF クライアントをインストールせずに、curl・PowerShell の Invoke-RestMethod・Postman・自作スクリプトなど任意の HTTPS クライアントから、中央サーバーの API を直接呼び出してファイル操作（一覧・アップロード・ダウンロード・削除・リネーム・フォルダ作成）を行う方法をまとめたものです。

こんな用途に
  • 他システム（バッチ処理・RPA・別サーバーの定期ジョブなど）から Watashi 経由でファイルを受け渡ししたい
  • WPF クライアントを操作せず、スクリプトで定型のアップロード／ダウンロードを自動化したい
  • 動作確認・障害切り分けのために、GUI を介さず API を直接叩いて挙動を見たい
これは抜け道ではありません WPF クライアントは、この文書で説明する API を呼び出しているだけの「1つの実装」にすぎません。別のツールから同じ API を呼んでも、実行されるのは同じユーザー・同じ権限チェック・同じ監査ログ記録です（→第1章・第13章）。ログインに使うユーザー名・パスワードを知っている人だけが、そのユーザーの権限内で操作できます。

1全体像：クライアントもAPIも「同じ入り口」

覚えることは実はひとつだけです。画面の左端にある道具（WPFクライアントか、別のツールか）が変わるだけで、その先（中央サーバー以降）は完全に同じ経路を通ります。

中央サーバー（Watashi.Server）
すべてのリクエストの唯一の入り口。ASP.NET Core 製の HTTP(S) API で、JWT で認証し、ユーザーごとの権限（共有 × パス）を検査してから CIFS（直接接続または Agent 経由）へ中継します。
別のツール
curl、PowerShell の Invoke-RestMethod、Postman、Python の requests など、HTTPS で JSON またはバイナリを送受信できるものであれば何でも構いません。特別な SDK や専用ライブラリは不要です。

2必要なもの

項目説明
Watashi のユーザーアカウント操作したいユーザーのユーザー名・パスワード。実行できる操作は、そのユーザーに割り当てられた権限（共有 × パス × Read/Write/Delete/Rename）の範囲に限られます。
中央サーバーの URL例：本番 https://watashi.internal ／ 開発 http://127.0.0.1:18080（dotnet run 時の既定）
HTTPS が話せるクライアントcurl、PowerShell（Invoke-RestMethod）、Postman、任意のプログラミング言語の HTTP クライアントなど
（本番運用時）サーバー証明書の信頼自己署名証明書の場合はクライアント側で信頼設定が必要（→第15章）
「アプリ専用のAPIキー」のようなものはありません Watashi には API 専用の資格情報という概念はなく、ログイン画面とまったく同じユーザー名・パスワードで認証します。つまり API を直接使う場合も、実質は「そのユーザーとしてログインしている」ことと同じです。誰か別のユーザーになりすますことはできず、そのユーザー自身の資格情報が必要です。

3接続確認（ログイン不要）

本格的に認証する前に、サーバーに到達できるかどうかをログイン不要のエンドポイントで確認できます。

PowerShell
$base = 'https://watashi.internal'   # 開発なら 'http://127.0.0.1:18080'

Invoke-RestMethod "$base/"        # 利用可能なエンドポイント一覧
Invoke-RestMethod "$base/health"  # {"status":"ok","at":"..."}
curl
base=https://watashi.internal

curl "$base/"
curl "$base/health"

GET / は疎通確認用に、主要エンドポイントの一覧も返します。GET /health は監視ツールなどからの死活監視にも使えます。どちらも認証不要です。

4ログインしてトークンを取得する

ファイル操作 API を呼ぶには、まず POST /api/auth/login でログインし、アクセストークン（JWT）を取得します。

ユーザー名は ASCII の大文字・小文字を区別しません。管理者が追加した直後の「初回設定待ち」アカウントは、Watashi クライアントで本人確認と最初のパスワード設定を完了するまで、この API ではログインできません。

PowerShell
$base = 'https://watashi.internal'
$body = @{ username = 'ユーザー名'; password = 'パスワード' } | ConvertTo-Json
$login = Invoke-RestMethod -Method Post -Uri "$base/api/auth/login" `
    -ContentType 'application/json' -Body $body

$accessToken   = $login.accessToken
$refreshToken  = $login.refreshToken
$refreshTokenId= $login.refreshTokenId
$headers = @{ Authorization = "Bearer $accessToken" }
curl
base=https://watashi.internal

login=$(curl -s -X POST "$base/api/auth/login" \
  -H 'Content-Type: application/json' \
  -d '{"username":"ユーザー名","password":"パスワード"}')

access_token=$(echo "$login" | jq -r .accessToken)

レスポンス（LoginResponse）の主なフィールドは次のとおりです。

フィールド内容
accessTokenファイル操作 API に使う JWT。有効期限 15分。
refreshToken / refreshTokenIdaccessToken 更新用。有効期限 30日（→第6章）。
expiresInaccessToken の有効秒数（既定 900 = 15分）。
mustChangePasswordtrue の場合、先に /api/auth/change-password を呼ぶまで他の API は 403 で拒否されます（→第14章）。
passwordExpiresInDays / passwordWarningDaysパスワード有効期限までの日数と警告日数。
ユーザー名・パスワードが違うだけで、あとは全員共通 ログイン API は誰が呼んでも同じ挙動です。「特定のユーザーとして操作したい」場合は、単純にそのユーザーの username / password でログインするだけで、そのユーザー本人としてトークンが発行されます。
ログインには回数制限があります 同一 IP から 1分間に 10回（既定値）を超えてログインを試みると 429 Too Many Requests になります。パスワードを何度も間違えると、別途アカウント自体もロックされます（403）。

5トークンの使い方と有効期限

取得した accessToken は、以降すべてのリクエストの Authorization ヘッダーに載せます。

Authorization: Bearer eyJhbGciOiJIUzI1NiIs...

特別なヘッダーやユーザーエージェントの指定は不要です。標準的な JWT Bearer 認証であり、Watashi クライアント固有の識別情報を送る必要もありません。

署名と有効期限だけでなく、トークン内の資格情報世代をサーバー上の現在状態と毎回照合します。パスワード変更、初回設定への差し戻し、管理者フラグ変更、アカウントロック後は、発行済みのアクセストークンでも直ちに 401 になります。

リフレッシュトークンの使い回しは検知されます 同じ refreshToken を2回使う（＝すでに更新済みの古いトークンを再送する）と、漏えいによる不正利用の疑いとして扱われ、そのトークンの一族（ファミリー）全体が即座に失効します。スクリプトで refreshToken を保存するときは、更新後に必ず新しい値で上書きしてください。

6トークンを更新する

15分経って accessToken が失効したら（またはファイル API が 401 を返したら）、POST /api/auth/refresh で更新します。ユーザー名・パスワードの再送は不要です。

PowerShell
$body = @{ refreshTokenId = $refreshTokenId; refreshToken = $refreshToken } | ConvertTo-Json
$refreshed = Invoke-RestMethod -Method Post -Uri "$base/api/auth/refresh" `
    -ContentType 'application/json' -Body $body

$accessToken    = $refreshed.accessToken
$refreshToken   = $refreshed.refreshToken     # 必ず新しい値に置き換える
$refreshTokenId = $refreshed.refreshTokenId
$headers = @{ Authorization = "Bearer $accessToken" }

更新に失敗すると 401 とともに理由が返ります。

error 値意味対応
password_changedパスワード、初回設定状態、管理者フラグなど資格情報の世代が変更された再ログインが必要
token_reuse_detected失効済みトークンの再利用を検知再ログインが必要（トークン一族が全失効済み）
account_lockedアカウントがロック中管理者にロック解除を依頼
device_revoked信頼デバイスが失効済み再ログインが必要
invalid_tokenトークンが不正・期限切れ再ログインが必要
refreshにも回数制限があります 同一 IP から 1分間に 60回（既定値）まで。login より緩めですが、無限ループで叩き続けないよう注意してください。

7ログアウトする

スクリプトの実行が終わったら、リフレッシュトークンを明示的に失効させておくと安全です。

更新処理とログアウトが並行する可能性がある実装では、先に refresh を完了して最新の accessToken と refreshTokenId を確定し、その組で logout を呼んでください。ローテーション前の ID だけを失効させると、更新後のトークンが残る可能性があります。

PowerShell
$body = @{ refreshTokenId = $refreshTokenId } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri "$base/api/auth/logout" `
    -Headers $headers -ContentType 'application/json' -Body $body

成功すると 204 No Content。自分（ログイン中のユーザー）が所有するリフレッシュトークンのみ失効できます。ログアウトしなくても、放置すれば 30日でリフレッシュトークンは自然に失効します。

8操作できる場所を調べる

ファイルを操作するには hostId と shareId が必要です。どの共有・パスにアクセスできるかはユーザーごとに管理者が割り当てた権限で決まるため、まず自分（ログイン中のユーザー）がアクセスできる範囲を確認します。

PowerShell
$catalog = Invoke-RestMethod -Uri "$base/api/hosts/catalog" -Headers $headers
$catalog.hosts | ForEach-Object {
    $h = $_
    $h.shares | ForEach-Object {
        Write-Host "$($h.name) / $($_.displayName)  hostId=$($h.id) shareId=$($_.id)"
    }
}

GET /api/hosts/catalog は、ユーザーがアクセスできる host / share / 許可パス（location）を1回のリクエストでまとめて返します。個別に GET /api/hosts → GET /api/hosts/{hostId}/shares → .../locations と順に呼ぶより高速です。フィールドの詳細はAPI仕様書を参照してください。

アクセスできる場所が無い場合 hosts が空配列で返ります。管理者にそのユーザーへの権限割り当てを依頼してください。

9ファイル一覧を取得する

PowerShell
Invoke-RestMethod -Uri "$base/api/files?hostId=1&shareId=1&path=/" -Headers $headers

クエリパラメータ:

パラメータ必須説明
hostId / shareId必須/api/hosts/catalog で調べた値
path任意（既定 /）共有内の絶対パス（例 /2026/report）
page任意1以上で200件ずつページング。0以下または省略で全件まとめて返却
sort任意name / name_desc / date / date_desc / size / size_desc（既定はフォルダ優先＋名前昇順）

戻り値の各項目（FileEntry）は name・type（file/directory/parent）・size・modifiedAt などです。詳細はAPI仕様書参照。

10ダウンロードする

PowerShell
Invoke-RestMethod -Uri "$base/api/files/download?hostId=1&shareId=1&path=/report.xlsx" `
    -Headers $headers -OutFile .\report.xlsx
curl
curl -H "Authorization: Bearer $access_token" \
  "$base/api/files/download?hostId=1&shareId=1&path=/report.xlsx" \
  -o report.xlsx

レスポンスはファイルの生バイトです（Content-Type: application/octet-stream、ファイル名は Content-Disposition ヘッダーに UTF-8 で入ります）。サイズが大きくても分割不要で、ストリーミングでそのまま受信できます。

11アップロードする

PowerShell
Invoke-RestMethod -Method Post `
    -Uri "$base/api/files/upload?hostId=1&shareId=1&path=/incoming/data.csv" `
    -Headers $headers -InFile .\data.csv -ContentType 'application/octet-stream'
curl
curl -X POST -H "Authorization: Bearer $access_token" \
  --data-binary @data.csv \
  "$base/api/files/upload?hostId=1&shareId=1&path=/incoming/data.csv"

アップロード先の path は置き先ファイルのフルパスです（既存の同名ファイルは上書きされます）。成功すると 204 No Content。書き込み権限（Write）がそのパスに無いと 403 になります。

本番環境のアップロード上限 サーバー側のアップロード上限は既定 10GB ですが、IIS でホストしている場合は IIS の requestFiltering がさらに手前で効きます。Watashi の web.config では上限を uint の最大値（約 4GB）まで引き上げていますが、それでも実効上限は約4GBです。数十GB級のファイルは分割するか、事前にサーバー管理者へ確認してください。

12削除・リネーム・フォルダ作成

12-1. 削除

PowerShell
Invoke-RestMethod -Method Delete -Uri "$base/api/files?hostId=1&shareId=1&path=/incoming/old.csv" -Headers $headers

Delete 権限が必要。自分に割り当てられた許可パスのルート自体は削除できません（誤操作防止）。

12-2. リネーム（同じフォルダ内のみ）

PowerShell
$body = @{ hostId=1; shareId=1; oldPath='/incoming/old.csv'; newPath='/incoming/new.csv' } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri "$base/api/files/rename" -Headers $headers -ContentType 'application/json' -Body $body

Rename 権限に加えて、変更後のパスへの Write 権限も必要です。oldPath と newPath の親フォルダは同じでなければなりません（フォルダをまたぐ移動は不可）。

12-3. フォルダ作成

PowerShell
$body = @{ hostId=1; shareId=1; path='/incoming/2026-07' } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri "$base/api/files/mkdir" -Headers $headers -ContentType 'application/json' -Body $body

Write 権限が必要。

13すべての操作は監査ログに残る

API を直接叩いても、WPF クライアントを使ったときとまったく同じように、成功・失敗を問わずすべての操作が監査ログに記録されます。

記録される項目内容
日時・ユーザーTimestamp / UserId / Username
操作の種類Operation：LIST DOWNLOAD UPLOAD DELETE RENAME MKDIR
場所HostId / ShareId / Path（リネームは TargetPath も）
結果Result（成功/失敗）、失敗理由 ErrorMessage
接続元ClientIp / ClientHostname / Protocol（HTTPかHTTPSか）
転送量・所要時間BytesTransferred / DurationMs
経路・権限ExecutionNodeId（Direct/Agentどちら経由か）／ UsedPermissionId（どの権限行が適用されたか）

管理者は管理コンソールの「操作ログ」タブ、または CSV エクスポートでこれらを確認できます。CSV には人が読める形の 「ホスト名 / 共有名 :: パス」 も出力されます。API 経由の操作だからといって痕跡が残らない、ということはありません。

むしろ都合がよい点 スクリプトから使う場合、実行元 IP・実行時刻・転送バイト数・所要時間まで自動的に記録されるため、自動化ジョブの実行証跡としてそのまま使えます。

14エラーの見分け方

ステータス典型的な原因対応
400必須パラメータ不足／ホスト・共有が存在しない／リネームで親フォルダが変わっているリクエスト内容を確認
401トークン未指定・期限切れ・不正／パスワード・管理者フラグ・初回設定状態の変更／アカウントロック現在状態を確認して再ログイン。期限切れだけなら refresh
403権限不足／許可ルート自体の削除・リネーム／mustChangePassword 未対応のまま他 API を呼んだ権限を確認、または先に change-password
429ログイン・refresh の回数制限超過間隔を空けてリトライ
502CIFS 側の I/O エラー・権限エラーホスト側の資格情報・共有権限を確認
503実行ノード（Agent）に到達できないAgent の稼働状況を確認

エラーレスポンスは基本的に { "error": "説明メッセージ" } という JSON 形式です。全エンドポイント共通の一覧・詳しいレスポンス例はAPI仕様書の共通エラー一覧を参照してください。

15実運用での注意点

  • 証明書の検証を無効化しない：本番で自己署名証明書を使っている場合は、検証を無効化（curl -k や -SkipCertificateCheck）するのではなく、正しい CA 証明書をクライアント側に信頼させてください。
  • パスワード変更が必須のユーザーは先に change-password：管理者が初期パスワードを発行した場合や期限切れで mustChangePassword=true になったユーザーは、それ以外の API がすべて 403 になります。初回設定待ちのユーザーは通常ログイン自体が 401 になるため、先に Watashi クライアントで初回設定を完了してください。
  • トークンの保管場所に注意：accessToken / refreshToken はそのユーザーの権限をそのまま行使できる鍵です。平文でリポジトリにコミットしたり、ログに残したりしないでください。
  • 大量ファイルの一覧取得はページングを検討：既定では page 省略時に全件返却されるため、数万件規模のフォルダでは page を指定して分割取得すると応答が安定します。
  • この文書がカバーするのはファイル操作 API のみ：ユーザー・権限・ホストの管理を行う管理者向け API は別に存在しますが、本書では扱いません。

16サンプルスクリプト全文

ログインからファイル一覧・ダウンロード・ログアウトまでを通しで行う PowerShell の例です。

PowerShell
$base = 'https://watashi.internal'
$cred = @{ username = 'ユーザー名'; password = 'パスワード' } | ConvertTo-Json

# 1. ログイン
$login = Invoke-RestMethod -Method Post -Uri "$base/api/auth/login" `
    -ContentType 'application/json' -Body $cred
$headers = @{ Authorization = "Bearer $($login.accessToken)" }

# 2. アクセスできる場所を確認
$catalog = Invoke-RestMethod -Uri "$base/api/hosts/catalog" -Headers $headers
$h = $catalog.hosts[0]; $s = $h.shares[0]

# 3. ファイル一覧
$list = Invoke-RestMethod -Uri "$base/api/files?hostId=$($h.id)&shareId=$($s.id)&path=/" -Headers $headers
$list.entries | Format-Table name, type, size

# 4. 先頭のファイルをダウンロード
$file = $list.entries | Where-Object { $_.type -eq 'file' } | Select-Object -First 1
if ($file) {
    Invoke-RestMethod -Uri "$base/api/files/download?hostId=$($h.id)&shareId=$($s.id)&path=/$($file.name)" `
        -Headers $headers -OutFile ".\$($file.name)"
}

# 5. ログアウト
Invoke-RestMethod -Method Post -Uri "$base/api/auth/logout" -Headers $headers `
    -ContentType 'application/json' -Body (@{ refreshTokenId = $login.refreshTokenId } | ConvertTo-Json)
