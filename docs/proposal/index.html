第 1 部

なぜ、この道具が必要なのか

現行ツールをご存じない方も、ここから読めば話が繋がります

1解きたい問題 — ネットワークが分かれていると、ファイルが運べない

社内のネットワークやサーバーは、安全のために「あえて」分けられています。部署ごと、拠点ごと、業務システムごと、外部接続用……。分けることで守れる一方で、その代償として ファイルが行き来できなくなります。

ところが、仕事のほうは分断されていません。見積書、図面、検査データ、システムへの取り込みファイル、受領した資料——「向こう側のサーバーに置きたい」「向こう側から取り出したい」は日常的に発生します。

この状態で起きている3つの困りごと

困りごと具体的には
🚨 危ないUSB メモリ・メール添付・私物クラウドなど、管理の外にある経路を通ってしまう。紛失や誤送信が起きても止められない
🐌 面倒受け渡しのたびに担当者へ依頼、手作業でのコピー、待ち時間。本来の仕事ではない作業に時間が取られる
❓ 分からない誰が・いつ・どのファイルを持ち出したのか記録が残らない。「あのファイル、誰が消した？」に答えられず、監査でも証跡を示せない

2そこで作られた「受け渡し口」 — 元々やりたかった2つのこと

この問題への答えは、抜け道を塞ぐことではなく、「安全な正面玄関」を1つ用意することでした。そのために社内で用意されたのが、現在使われているファイル受け渡しツールです。

やりたかったことは、突き詰めると次の2つだけです。

🔀
① またいで運ぶのを、簡単にする
利用者はネットワークの構造を意識しない。いつもの1つの画面を開けば、向こう側のサーバーのフォルダがそこにあり、マウス操作で置く／取り出せる。
📝
② 運んだ記録を、残す
通り道を1本に絞れば、そこを通ったものは全部記録できる。「いつ・誰が・どのファイルを・どちらへ動かしたか」が後から必ず追える。

※ 本資料では、現在利用中のファイル受け渡しツールを 「現行ツール」 と表記します（社内では固有の呼び名がありますが、その名前を知らなくても読み進められるようにしています）。

うまくいっていること（＝後継ツールでも引き継ぎたい価値）

現行ツールは、上記の「①運ぶ／②記録する」という考え方自体は正しく実現しています。次の3点は、後継ツールでもそのまま引き継ぎます。

🪟
引き継ぐ
分かりやすい2画面
左に自分の PC、右に社内サーバー。マウス操作で上げ下げするだけ。教育コストが低い
🏠
引き継ぐ
社内で完結
外部のクラウドサービスを経由しない。データが社外に出ない
🗄️
引き継ぐ
既存サーバーはそのまま
今のファイルサーバー・共有フォルダを置き換えず、そこへの「安全な入口」を足すだけ

限界（＝今回の改善対象）

一方で、運用を続ける中で 10 個の課題 が挙がっています。単なる「使いにくさ」ではなく、情報漏えいリスクと運用コストに直結するものが含まれます。ここでは、先ほどの「①運ぶ／②記録する」という軸に沿って整理しました。

#現行ツールの課題これが招くリスク・コスト
A「運ぶ」経路そのものが安全でない
1通信が HTTP のみ（暗号化なし・平文）パスワードやファイルの中身が、通信の途中で盗み見られる恐れ。外部監査でも指摘対象になる
3ユーザーごとに触れる範囲を分けられない使える人は全員が同じ範囲にアクセスできてしまう。「必要な人に必要な範囲だけ」という最小権限の原則を満たせない
B「記録」は取れているが、使えない
5ログを見るには データベースを直接参照するしかない「誰が何をしたか」の確認に手間と専門知識が必要。監査や事故調査のときに、すぐ提示できない
C日々の運用が手作業
6ユーザー追加が大変異動・入退社のたびに手作業。管理者の定常負荷になり、対応も遅れがち
7許可するフォルダを 1 つずつ手入力権限付与に時間がかかるうえ、打ち間違い・過剰付与などの設定ミスが起きやすい
8設定変更が大変ちょっとした変更にも作業コストがかかり、担当者以外には触れない（属人化）
Dサーバーの保守が重い
4MySQL の脆弱性対応が大変（Web アプリと同一サーバーに同居）データベースの監視・パッチ当てが恒常的な負担。同居しているため、片方の対応がもう片方にも影響しやすい
10MySQL の立ち上げが大変初期構築・移設に専門作業が必要。Web と DB が 1 台に同居しているため、検証環境を増やす・切り分けるのも大変
9IIS を使う構成でしか構築できないサーバー構成の自由度が低く、移設・冗長化がしにくい
Eその他
2ツール名が 他製品と重複している検索・問い合わせ・社内周知で混乱する。関連情報を探しても別製品の情報しか出てこない
まとめると：「①またいで運ぶ」「②記録を残す」というねらいは今も正しいのに、経路が安全でなく（A）、記録が使えず（B）、維持するのに人手がかかりすぎている（C・D）というのが現状です。だからこそ、ねらいは変えずに中身を作り直すことをご提案します。
第 2 部

これから、どう良くしたいのか

改善の方向性と、後継ツールの全体像

4改善の4つのねらい

目的（またいで運ぶ／記録を残す）はそのままに、次の4点を作り直します。以降の第3部で、それぞれを1章ずつご説明します。

ねらい ①

どのネットワークのサーバーへも、同じ画面から

直接つながらない拠点・閉じたネットワークの先にあるファイルサーバーにも、中継（エージェント）方式で到達できるようにします。利用者から見れば、どのサーバーも同じ一覧に並ぶだけです。

→ 詳細は 第6章

ねらい ②

記録を「すぐ使える」ものにする

記録は取るだけでは意味がありません。管理画面から検索・絞り込み・CSV 出力ができ、聞かれたその場で答えられる状態にします。データベースを直接見る必要はなくなります。

→ 詳細は 第7章

ねらい ③

経路と権限を安全にする

通信を暗号化（HTTPS）し、触れる範囲を人ごと・フォルダごと・操作ごとに限定します。「便利だが危ない道」ではなく「便利で安全な道」にします。

→ 詳細は 第8章

ねらい ④

管理の手間を減らす

ユーザー追加・権限設定・ログ抽出・サーバー保守を、画面操作と自動化に置き換えます。安全にした結果として管理が重くなっては、続きません。

→ 詳細は 第9章

設計の考え方：これらは後から機能を継ぎ足したものではありません。「安全であること・運用が簡単であること・保守が軽いこと」を最初の前提として作り直しています。

Watashi（わたし） は、上記のねらいを実現する後継ツールです。使用感は現行と同じ「2画面でファイルをやり取りする」ままに、中身をまるごと作り直したものです。

第 3 部

具体的に、何が変わるのか

4つのねらいを、1章ずつ

6ねらい① どのネットワークのサーバーへも、同じ画面から

第1章でご説明したとおり、そもそもの問題は「ネットワークが分かれていて届かない」ことでした。Watashi は、行き先ごとに最適な経路を自動で選び、利用者にはその違いを見せません。

利用者から見ると、どうなるか

  • アプリを開くと、自分が許可された場所だけが一覧に並びます。どのネットワークにあるかは意識しません。
  • フォルダをたどって、ドラッグやボタンでアップロード／ダウンロードするだけです。
  • 大きなファイルも扱えます（分割して少しずつ送るため、サイズの上限がありません）。ダウンロードが途中で失敗しても、中途半端なファイルは残りません。
  • 接続先は管理者が配布時に固定します。利用者側では変更できないため、誤った接続先につながる心配がありません。
「経路を増やしても、利用者の学習コストは増えない」のがポイントです。中継が1段でも2段でも、利用者の操作はまったく同じです。

7ねらい② 記録を「すぐ使える」ものにする

現行ツールでも記録自体は取れています。問題は「取り出せない」ことでした。データベースを直接調べる必要があり、専門知識のある担当者しか答えられません。Watashi は、聞かれたその場で答えられる状態を目指します。

観点現行ツールWatashi（後継）
記録の見かた✗データベースを直接参照するしかない✓管理画面から一覧・絞り込み。専門知識は不要
記録の取り出し✗担当者が都度抽出✓CSV 出力。表計算ソフトでそのまま開ける
記録の読みやすさ✗内部の番号で記録されており、人が読んで分からない✓「サーバー名 / 共有名 :: パス」の形で記録。そのまま読める
管理者の操作✗記録対象が限定的✓ユーザー追加・権限変更などもすべて記録
古い記録の扱い✗手作業での整理が必要✓保管期間を設定すれば自動で削除
内部統制・監査の観点：「誰が・いつ・どのファイルに・何をしたか」がすべて残り、管理画面からその場で提示できます。証跡を出すまでのリードタイムが、数日から数分になります。

8ねらい③ 経路と権限を安全にする

受け渡し口を1本にまとめても、その道が危なければ意味がありません。通信の暗号化と触れる範囲の限定の2つが、今回の改善でもっとも効果の大きい部分です。

8-1. 通信の暗号化（HTTPS）

現行ツールの通信は平文（HTTP）です。同じネットワーク上にいる誰かが通信を覗けば、パスワードもファイルの中身もそのまま読めてしまいます。Watashi では通信を暗号化するため、途中で覗かれても意味不明な文字列にしか見えません。

8-2. 触れる範囲を、人ごとに限定する

現行ツールでは、利用できる人は全員が同じ範囲にアクセスできます。Watashi では 「人 × フォルダ × 操作の種類」 の組み合わせで許可します。許可されていないフォルダは、そもそも一覧に表示されません（「見えるけれど開けない」ではありません）。

8-3. そのほかの安全対策

守るものしくみ
ログインパスワード元に戻せない形で保存（管理者でも中身は分かりません）。強度ルール（12 文字以上＋英大文字・小文字・数字・記号）と有効期限を全社で強制
不正なログイン試行連続して失敗するとアカウントを自動ロック。さらに、短時間に何度も試す行為も自動でブロック
サーバーが預かる接続情報ファイルサーバーへの接続情報は暗号化して保管
サーバー間の通信中央サーバーと中継役はお互いに証明書を確認（なりすまし防止）
誤った場所への接続接続先はアプリ配布時に管理者が固定。利用者側では変更できません
退職者・異動者アカウントの無効化と、自動ログイン端末の失効を管理画面からワンクリック
管理機能の露出管理者以外には管理メニュー自体が表示されません
データの社外流出すべて社内で完結。外部のクラウドサービスは経由しません

9ねらい④ 管理の手間を減らす

安全にした結果、管理の手間が増えては続きません。Watashi では、これまで手作業だった作業を画面操作と自動化に置き換えます。

作業これまでWatashi
ユーザーの追加1 人ずつ手作業管理画面で追加。CSV で一括登録できるので、入社・異動シーズンも一気に反映
権限の付与許可するフォルダを 1 つずつ手入力フォルダを一覧から選ぶだけ。「経理部の標準権限」のような権限セットを作っておけば1クリックで一括付与。他の人からまるごとコピーも可能
退職者の処理漏れやすいアカウント削除と自動ログイン端末の失効をワンクリック
「誰が消した？」の調査データベースを調べる必要があり、ほぼ実施できない管理画面で検索 → CSV 出力して提出
設定の変更作業コストが高く属人的パスワード有効期限・自動ログアウト時間・ロック回数なども管理画面から変更
アプリの配布・更新1 台ずつ手作業利用者がアプリを起動するたびに自動で最新版に更新。配り直し不要
データベースの保守MySQL の監視・パッチ当てが恒常的な負担専用のデータベースサーバーが不要。初回起動時に自動生成され、日次でバックアップも自動取得
サーバーの障害対応気づいたら手動で再起動常駐サービスとして動作し、異常終了時は自動で再起動。中継役の異常も自動検知
ログの肥大化手作業で整理保管期間を過ぎた記録は自動削除
管理者の定常負荷が下がります：これまで手作業だった「ユーザー追加・権限設定・ログ抽出・データベース保守」が、画面操作か自動処理に置き換わります。権限を細かくしても、設定の手間はむしろ減ります。

観点現行ツールWatashi（後継）

⑤ ログ確認 ✗データベースを直接見るしかない ✓管理画面で閲覧・絞り込み・CSV 出力。「誰が・いつ・何を」が一目で分かる
⑥ ユーザー追加 ✗1 人ずつ手作業 ✓管理画面で作成。さらに CSV で一括登録（入退社・異動も一気に反映）

⑧ 設定変更 ✗作業が大変・属人的 ✓パスワード有効期限・自動ログアウト時間なども管理画面から変更
⑨ サーバー構成 ✗IIS を使う構成が必須 ✓常駐サービス単体で稼働。IIS は必須ではなく、使いたければ前段に置くことも可能
⑩ 初期構築 ✗MySQL の立ち上げが大変 ✓初回起動でデータベースが自動生成。構築作業ゼロで、検証環境も簡単に増やせる
ポイント：挙げていただいた 10 個の課題は、すべて対応済みです。後付けの対策ではなく、設計の段階から「安全・簡単な運用・軽い保守」を前提に作られています。

URL を開くだけで導入完了。追加ソフトは不要で、更新も自動です

移行がしやすい理由

  • 既存のファイルサーバーはそのまま：置き換えではなく「安全な入口を足す」形なので、既存データの移行作業がありません。
  • サーバーは 1 台から：別のデータベース構築が不要なため、検証環境もすぐ用意できます。
  • 利用者の登録は一括：CSV でまとめて登録でき、権限も「権限セット」で一括付与できます。
  • 操作感が現行とほぼ同じ：2画面のファイル操作なので、現行ツールを使っている方の再教育がほとんど不要です。
  • マニュアル完備：利用者向け・管理者向けの説明書を用意済みです（→ 付録）。
  • 段階的に移行できる：現行ツールを止めずに、部署単位で順次切り替えられます。

ご提案するステップ

  1. 準備：検証用サーバーに Watashi を構築し、対象部署・評価項目を確定します。
  2. 試験導入（PoC）：1 部署・少人数で、実運用に近い形で試します。
  3. 評価：安全性（暗号化・権限分離）、運用性（ユーザー追加・記録の取り出し）、保守性を、現行と比較して確認します。
  4. 本番展開：問題なければ対象部署を拡大し、現行ツールから順次切り替えます。

ご判断のお願い

まずは 試験導入（PoC）の実施 についてご承認いただけますと、現行ツールの課題がどれだけ解消されるかを、実際の画面と数字でご報告できます。

大きな投資判断は、その結果をご覧いただいてからで問題ありません。
