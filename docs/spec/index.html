第 1 部

全体像をつかむ

何をするツールで、何でできていて、なぜその形なのか

1このツールは何をするものか

Watashi は、社員が自分の PC から社内の CIFS/SMB ファイルサーバー (ファイル共有) へアクセスし、アップロード・ダウンロード・削除・リネーム・フォルダ作成を行うための Windows デスクトップツールです。画面は FFFTP に似た 2 ペイン構成で、左が自分の PC、右が社内ファイルサーバーです。

最大の特徴は、クライアントがファイルサーバーへ直接つながらない点です。通信は必ず中央サーバーを通り、中央サーバーが「誰が・どこへ・何をしてよいか」を判断し、実際の SMB アクセスを代行し、結果を記録します。ファイルサーバーの資格情報 (ID/パスワード) はクライアントには一切渡りません。

1.1 解決していること

課題Watashi での解き方
ネットワークが分かれていてファイルが運べない中央サーバーが唯一の通り道になり、直接届かない先へは踏み台 Agent が中継する。利用者はネットワーク構造を意識しない
誰が何を持ち出したか分からない通り道が 1 本なので、通過したものはすべて監査ログに残る。ログイン事象・管理操作・拒否された操作も記録される
共有フォルダの権限が粗いファイルサーバー側の権限とは別に、「利用者 × 共有 × サブパス × 操作種別」で中央が絞り込む
ファイルサーバーの資格情報が広まる資格情報は暗号化して中央 DB にのみ保持。クライアントにも Agent にも永続化されない
接続先を勝手に変えられてしまう接続先は配布パッケージ同梱の deployment.json で固定。クライアントに編集画面を持たせない

1.2 やらないこと (スコープ外)

  • ファイルサーバー側の ACL 管理 — Watashi の権限は「Watashi 経由で何ができるか」を決めるもので、ファイルサーバー自体の権限設定は行いません。Watashi はホストに登録された 1 組の資格情報でファイルサーバーへ接続します。
  • ファイルの中身の検査 — ウイルススキャンや DLP のような内容検査機能はありません。
  • Web ブラウザからの利用 — 利用者向けの UI は WPF デスクトップアプリのみです (API を直接呼ぶことは可能)。
  • Windows 以外のクライアント — クライアントは Windows 専用です。

第 2 部

どう動くのか

1 回の操作がどこを通り、どの経路を選び、どう配布されるのか

41 回のリクエストが処理される流れ

クライアントからの操作は、種類を問わず同じ 5 段階を通ります。「認可 → コンテキスト構築 → 実行 → 監査ログ → エラーマップ」で、これは中央サーバー側の共通ヘルパー ExecuteAsync に実装されています。個々のエンドポイントが独自に認可や記録を書くことはありません。

4.1 共通ヘルパー ExecuteAsync が保証すること

段階内容
① 認可操作種別 (READ / WRITE / DELETE / RENAME …) と対象パスから PermissionService.CanPerformAsync を呼び、許可がなければ 403。判定結果は HttpContext.Items にメモ化され、同一リクエスト内で何度呼んでも DB 参照は 1 回
② コンテキスト構築ホスト・共有・実行ノードを解決し、暗号化されたファイルサーバー資格情報を復号して接続情報を組み立てる
③ 実行NodeRouter が Direct / Agent を振り分け、SMB 操作を実行する
④ 監査ログ成功・失敗・拒否のいずれでも 1 行記録する。所要時間・転送バイト数・接続プロトコル・使用した権限 ID も残す
⑤ エラーマップ内部例外は Results.Problem で汎用メッセージにマスクし、スタックトレースや内部パスをクライアントへ返さない。Agent 側で発生したエラーはステータスコードを保ったまま中央へ伝播する

5ネットワーク構成とポート

通信経路は 区間 A (クライアント ⇄ 中央サーバー) と 区間 B (中央サーバー ⇄ Agent) の 2 つで、それぞれ独立に HTTP / HTTPS を選べます。区間 B は実行ノードごとに選択できます。

5.1 3 つの構成モード

モード区間 A区間 BmTLS想定環境
A: 全 HTTPS + mTLS
推奨		HTTPSHTTPS + クライアント証明書ON本番。踏み台が別のセキュリティゾーンにある場合
B: 混在HTTPSHTTP + 共有秘密OFF中央サーバーと Agent が同一の信頼ゾーンにある場合

本番不可		HTTPHTTPOFF検証・内部ラボ専用
区間 A にはファイルの中身とパスワードが流れるため、本番では区間 A の HTTPS は必須です。区間 B が社内 LAN 内で完結するなら HTTP + 共有秘密でも実用上は成立しますが、個人情報など規制対象を扱う経路は mTLS にしてください。
HTTP 構成でも「この PC を記憶する」(自動ログイン) は利用できますが、デバイストークンが平文で流れます。サーバー側の Auth:AllowHttpForAutoLogin が false なら HTTP の自動ログインは 401 で拒否されます (本番は false 推奨)。

6ノードルーティングと Agent (踏み台)

ホストごとに「どの実行ノードから SMB 接続するか」を管理者が指定します。中央サーバーの NodeRouter がこの指定を見て、自分で SMB を張るか、踏み台へ転送するかを振り分けます。

6.1 中継時の取り決め

  • 資格情報の渡し方 — ファイルサーバーの資格情報は POST の本文、またはヘッダー X-Watashi-Cifs (Base64 の JSON) で渡します。URL のクエリ文字列には載せません (アクセスログへの平文残留を避けるため)。
  • Agent 側では永続化しない — 受け取った資格情報はメモリ上でのみ使い、ディスクには書きません。
  • 到達性の事前判定 — 経路上の Agent (チェーンの場合はゲートウェイ側) が Unhealthy なら、SMB を試みずに即座に 503 を返します。無駄なリトライは行いません。
  • 過負荷制御 — Agent は同時処理数が MaxConcurrency (既定 20) を超えると 503 + Retry-After: 5 を返します。

6.2 Agent の受け口の認証

モード仕組み
mTLS中央サーバーが提示するクライアント証明書のサムプリントを、Agent 側の Auth:CentralCertificateThumbprint と照合する
共有秘密ヘッダー X-Watashi-Secret の値を、Agent 側の Auth:SharedSecret と一致確認する
どちらも未設定すべてのアクセスを 401 で拒否する (設定漏れが「素通し」にならない設計)

6.3 ハートビートと健全性判定

6.4 SMB セッションプール

操作のたびに TCP 接続・SMB ネゴシエーション・ログイン・共有への接続をやり直すと、小さな操作でも待ち時間が積み上がります。そこで (ホスト, ポート, ユーザー, 共有) をキーにしたセッションプールを中央サーバーと Agent の双方で使います。

  • アイドル保持時間の既定は 60 秒 (Cifs:SessionIdleSeconds)、キーあたりの上限は既定 4 (Cifs:MaxSessionsPerKey)
  • バックグラウンドのタイマーが、使われなくなったセッションを自動的に破棄する
  • 同時転送が多い環境では上限を、接続コストが高い環境では保持時間を調整する

7配布と接続先の固定 (deployment.json / ClickOnce)

本章はこのシステムのガバナンスの要です。「クライアント側から接続先を変えられない」ことが設計上の必須要件であり、そのために利用者向けの設定画面をあえて持たせていません。

7.1 deployment.json — 配布時に管理者が固定する設定

接続先サーバーと一部機能の可否は、アプリに同梱する読み取り専用の deployment.json で決まります。管理者が発行前に編集し、利用者は変更できません。

{
  "serverUrl": "https://watashi.internal",
  "updateManifestUrl": "https://watashi.internal/install/Watashi.Client.application",
  "enableDragDrop": true,
  "fileTransferTimeoutMinutes": 30
}
キー既定意味
serverUrl必須接続先の中央サーバー URL。スキーム (https / http) から IsHttps を判定し、画面表示と実際の通信の整合性を保証する
updateManifestUrl必須起動時に確認する ClickOnce 配置マニフェストの URL。exe を直接起動した場合もこの URL で公開版を確認する
enableDragDroptrueドラッグ & ドロップ機能を有効にするか
fileTransferTimeoutMinutes30ファイル転送 1 件あたりのタイムアウト (分)。0 以下を指定した場合は 30 に正規化される

7.2 接続テスト画面 (編集 UI は持たない)

ログイン画面の「接続テスト」は、固定された接続先に対する疎通確認専用です。接続先 URL とドラッグ & ドロップの有効状態を読み取り専用で表示し、/health を呼んで結果を出すだけで、接続先を編集する UI は存在しません。

7.3 ドラッグ & ドロップの配布時ゲート

ドラッグ & ドロップは enableDragDrop でゲートされます。実装は専用のファイル (MainWindow.DragDrop.cs) に隔離されており、無効の場合はイベントハンドラ自体を登録しません。画面上でボタンを隠すだけの制御ではないため、無効配布時に機能が動く余地がありません。

7.4 ClickOnce による配布と更新

  • 配布 URL (例: https://watashi.internal/install/Watashi.Client.application) からインストールする
  • ショートカットからの起動時は ClickOnce が更新を確認する。exe を直接起動した場合も、アプリ自身が updateManifestUrl を確認し、新しい版があれば ClickOnce の更新を起動する
  • 接続先を変更するには再発行 (re-publish) が必要。配布済みファイルの書き換えでは変更できない
  • 配布サーバー (IIS) 側で .application / .manifest / .deploy の MIME 登録が必要

  • HTTP / HTTPS どちらでも利用可能。ただし HTTP は平文のため警告を表示し、サーバー側の Auth:AllowHttpForAutoLogin が false なら拒否する
  • 1 利用者につき 1 台のみ。別の PC でチェックを入れると、以前のデバイストークンは失効する (直列化トランザクションで原子的に切り替え)

  • 管理者は「全デバイス失効」で無効化できる (退職時など)。失効理由 admin_revoked と日時が記録される
  • ログアウト時は資格情報マネージャーからも削除する

9.3 ディレクトリトラバーサルの防御

「../../ を含むパスで許可範囲の外へ抜ける」攻撃には 2 段で対処します。

  1. 利用者が指定したパスを PathHelper.NormalizePath() で正規化し、.. を実際に展開する
  2. 展開後のパスが許可サブパスの配下にあるかを IsPathWithin() で確認する
  3. 範囲外なら 403 を返し、監査ログに denied を記録する

正規化前の文字列に対する検査 (「.. が含まれていたら弾く」といった方式) では、エンコードや区切り文字の揺れで回避されるおそれがあります。展開後の絶対パスで比較するのが要点です。

10.4 中央が止まっているときの記録

Agent は、中央サーバーが一時的に到達不能でも操作を継続できるよう、監査ログをローカルの SQLite にバッファします。

  • 10 秒ごとに中央へ一括送信を試みる
  • 成功すれば一括削除、失敗すれば試行回数を加算する
  • 連続して失敗する場合は間隔を指数的に広げる (最大 5 分)
  • 試行回数が 50 に達した行は送信対象から外れる (滞留を無限に増やさないため)

⑦ 信頼デバイス自動ログインが登録された端末の一覧と、利用者単位の一括失効退職・端末紛失時の対応。失効理由と日時が記録される
⑧ 実行ノードDirect / Agent ノードの登録・削除・状態確認・鍵の再生成ホストで使用中のノードは削除できない。mTLS 構成では証明書のサムプリントで Agent を識別する
⑨ 操作ログ監査ログの検索と CSV 出力利用者名・操作種別・期間で絞り込み、1 ページ 100 件の新しい順 (§10)
⑩ システム設定パスワード期限・警告日数・同時接続上限・アイドル時間・ログ保管日数・ロックまでの失敗回数変更は即時反映され、サーバーの再起動は不要 (§17.4)
設定の置き場所に注意：ログ保管日数やアイドル時間などの運用パラメータは appsettings.json ではなくデータベース上のシステム設定であり、管理画面 (または管理 API) から変更します。一方、接続 URL・証明書・暗号鍵などの基盤設定は appsettings.json 側です。詳細は §17 を参照してください。

18導入手順と本番投入チェックリスト

18.1 構築の流れ

  1. 中央サーバーを構築 — 発行物を配置し、appsettings.json に暗号鍵・証明書・待受ポートを設定して、Windows サービスとして登録する。データベースは初回起動時に自動生成・初期化される
  2. 配布サーバーを用意 — ClickOnce 用に IIS などで発行物を公開する (.application / .manifest / .deploy の MIME 登録が必要)
  3. 踏み台に Agent を配置 — 必要な場合のみ。識別名・中央の URL・認証方式 (mTLS または共有秘密) を設定し、Windows サービスとして登録する
  4. 初期データを登録 — 管理者としてログインし、実行ノード → ホスト → 共有 → (必要なら) テンプレート → 利用者 → 利用者権限 の順に登録する
  5. クライアントを配布 — deployment.json に本番の接続先を書いて発行し、配布 URL を利用者へ案内する
登録の順序には依存関係があります。実行ノードがないとホストを登録できず、ホストがないと共有を登録できず、共有がないと権限を付与できません。新規データベースには Direct (Local) ノードが最初から入っているため、踏み台を使わない構成なら手順 4 はホストの登録から始められます。

対象方針

20.2 設計上の制限

制限理由 / 回避策
中継チェーンは 1 段まで「中央 → ゲートウェイ Agent → 目的の Agent → ファイルサーバー」が最長。これ以上多段にする場合は経路設計自体の見直しが必要
1 ホストにつき資格情報は 1 組ファイルサーバーへの接続は登録された 1 組のアカウントで行う。利用者ごとの権限は Watashi 側で絞り込む方式のため、ファイルサーバー側の ACL による利用者別制御とは併用しにくい
自動ログインは 1 利用者 1 台複数台での自動ログインは非対応。別の PC で登録すると前の登録は失効する
パスワードの履歴チェックなし過去に使ったパスワードの再設定を技術的には防げない。運用ポリシーで補完する前提
クライアントは Windows 専用WPF 実装のため。他 OS からは API を直接呼ぶ形になる
中央サーバーは単一障害点認証・認可・監査を一手に担う構成のため、停止すると全操作が止まる。可用性要件が高い場合は冗長化の設計が別途必要
名前の変更はフォルダをまたげない意図的な制限。フォルダをまたぐ移動を「名前の変更」として行わせないため (§9)
許可フォルダの直下より上へは行けない許可されたルート自体の削除・改名も不可。誤操作による事故を防ぐための制限

メンテナンスの切替と配置（2026-09-05）

管理画面「運用状態」で案内文（最大500文字）と開始・終了予定（端末のローカル日時）を入力し、予定／メンテナンス中／復旧確認中／通常を切り替えます。時刻は案内用で、自動停止・自動解除はありません。

作業中は新しい業務APIを停止し、受付済みHTTP要求は完了させます。認証、状態管理、最小限の運用診断、Agent内部経路は維持します。管理者のファイル操作も停止対象です。解除には復旧確認中・処理中要求0・運用診断の確認が必要です。要求数には独立したAgent処理や後片付けを含まないため、それらも停止前に確認します。

Serverの Maintenance:StateFilePath はDB外の私的ファイルで、既定はProgramDataのWatashi配下のmaintenance-state.jsonです。再起動・DB復元でも停止を保持し、Web公開しません。単一Serverプロセスで運用します。

外部案内を使う場合は Maintenance:PublicStatusFilePath と Maintenance:PublicStatusUrl（HTTPS）を両方設定します。Clientは deployment.json の maintenanceStatusUrl を設定してClickOnce再発行します。外部配信なしでもAPI内の切替は使用できます。公開は書き込みとHTTPS読み戻しを確認し、失敗時は状態を再取得してから再実行します。解除を先行しません。

同梱の Install-StatusAssets.ps1 と Publish-MaintenanceState.ps1、導入・更新・復旧・切り戻し手順を参照してください。独立した静的サイト、IIS・DNS・証明書・ACLは環境に合わせて設定します。API停止時も案内できる停止範囲に分離してください。Serverを先に更新してから2000件対応Clientを配布します。

状態API: GET /api/status（匿名）、GET/PUT /api/admin/maintenance（Admin）。PUTはexpectedRevisionで競合を検出（409）。公開失敗は503。業務停止は503とcode: maintenance、Retry-After: 15。検索APIの上限500件は変更しません。DBスキーマ変更はありません。
