# ユーザー表示名の追加 — 実装・検証計画

## 目的

認証 ID として使っている `Username`（GID）だけでは管理者が利用者を識別しづらいため、
任意の `DisplayName`（画面上の表記は「名前」）をユーザーへ追加する。

`Username` は引き続き認証・Windows 本人確認・一意性・権限判定に使う唯一の識別子とし、
`DisplayName` は管理画面の表示・検索だけに使う。

## 固定する仕様

- `DisplayName` は任意。DB では nullable とし、既存ユーザーは移行後 `NULL` になる。
- 前後の空白を除去し、空文字または空白だけの入力は `NULL` に正規化する。
- 最大長は 100 文字。重複を許可し、一意制約や索引は追加しない。
- 名前ありの表示は `山田 太郎（G012345）`、名前なしは従来どおり `G012345` とする。
- `DisplayName` は JWT、認証処理、Windows 本人確認、ユーザー別キュー、権限判定に含めない。
- 名前の変更だけでは access token、refresh token、信頼デバイスを失効させない。
- 管理 API 以外から名前を公開しない。

## 実装範囲

### 1. データモデルと移行

- `User.DisplayName` を追加する。
- EF Core に最大 100 文字の設定を追加する。
- nullable の `Users.DisplayName` 列を追加するマイグレーションと model snapshot を作成する。
- 既存ユーザーと、それを参照する権限・refresh token・信頼デバイスが移行で保持されることを確認する。

### 2. 管理 API

- `UserDto`、`CreateUserRequest`、`UpdateUserRequest` に `DisplayName` を追加する。
- DTO に統一表示用の `DisplayLabel` を追加する。
- 新規作成時に名前を保存できるようにする。
- PATCH の互換性を次のとおり維持する。
  - `DisplayName` が未指定または `null`: 現在値を変更しない。
  - 空文字または空白だけ: 現在値を消去する。
  - 値あり: trim・長さ検証後に保存する。
- `IsAdmin` だけを送る旧クライアントが名前を消さないことを確認する。

### 3. CSV 入出力

- インポートの任意列として `DisplayName` を追加する。
- 従来の `Username,IsAdmin` と旧 `Password` 列付き CSV を引き続き受け付ける。
- upsert の動作を次のとおりにする。
  - ヘッダーに `DisplayName` がない: 既存名を維持する。
  - セルに値がある: 名前を更新する。
  - セルが明示的に空: 名前を消去する。
  - ヘッダーはあるが当該行のセル自体が欠ける: 既存名を維持する。
- エクスポートでは既存列の位置を変えず、末尾へ `DisplayName` を追加する。
- 名前にも既存の CSV 数式インジェクション対策を適用する。

### 4. 管理クライアント

- ユーザー管理
  - 一覧へ「名前」列を追加し、「ユーザー名」と並べて表示する。
  - 新規作成と選択中ユーザーの編集欄へ、任意の「名前」を追加する。
  - 名前とユーザー名の両方を検索対象にする。
  - 削除・無効化・再有効化・初期 PW 発行・初回設定へ戻す確認を `DisplayLabel` 表示にする。
- ユーザー権限
  - ユーザー一覧、選択見出し、コピー元候補を `DisplayLabel` 表示にする。
  - 名前とユーザー名の両方で絞り込めるようにする。
- 信頼デバイス
  - ユーザー列と失効確認を `DisplayLabel` 表示にする。
  - 名前を検索対象にする。

### 5. 監査ログ

- `AuditLogs.Username` はイベント発生時の不変な証跡として変更しない。
- 管理画面取得時に現在の `Users` を left join し、在籍ユーザーの現在の `DisplayName` を補助表示する。
- 名前でもユーザーフィルターを利用できるようにする。
- 削除済みユーザーは保存済み `Username` だけで表示する。
- 監査 CSV では既存列を維持し、末尾へ現在の `DisplayName` を追加する。
- `AuditLogs` 自体への表示名スナップショット追加、Agent・Outbox の形式変更は行わない。

### 6. ドキュメント

- 機能一覧、仕様書、管理者ガイド、管理者 HTML マニュアルを更新する。
- CSV の新旧互換性と、名前が認証 ID ではないことを明記する。
- 必要な手動検証項目を追加する。

## 検証項目

### 自動テスト

- 表示名の trim、空欄正規化、最大長検証、表示ラベルのフォールバック。
- User → UserDto 射影で表示名が引き継がれる。
- 既存スキーマから最新スキーマへの移行で `DisplayName` 列が追加される。
- 移行前から存在するユーザー、権限、refresh token、信頼デバイスが保持される。
- 旧 PATCH で表示名が消えず、空文字 PATCH では消去できる。
- 旧 CSV、新 CSV、upsert での維持・更新・消去、長すぎる名前の行エラー。
- CSV 出力で式として評価され得る表示名が無害化される。
- 監査ログのユーザー絞り込みが Username、UserId、現在の DisplayName に対応する。
- DTO の表示ラベルが名前あり・なし・削除済み相当の状態を正しく扱う。

### ビルド・手動確認

- ソリューション全体のテストを実行する。
- Server、Client を含むソリューション全体を Release 構成でビルドする。
- 既存 DB のコピーに最新マイグレーションを適用するスモークテストを行う。
- 管理画面のユーザー管理、権限、信頼デバイス、監査ログを目視確認する。
- 名前未設定の既存ユーザーで従来表示が崩れないことを確認する。

## 今回行わないこと

- `Username` の変更・名前によるログイン。
- 一般利用者のメイン画面、ログイン画面、JWT への表示名追加。
- 監査ログ、無効化した管理者名、ごみ箱の削除者名に表示名スナップショットを保存すること。
- 名前変更によるセッション失効。
- PR のマージ。

## リリース順序

1. 稼働 DB をバックアップする。
2. Server を先に更新し、起動時マイグレーションを完了させる。
3. 管理 API と既存クライアントの動作を確認する。
4. Client を更新する。
5. 既存ユーザーの名前を管理画面または CSV で登録する。

## 完了条件

- 上記実装範囲と検証項目をすべて満たす。
- 計画との差異がある場合は、PR 本文に理由と影響を明記する。
- 変更を専用ブランチへコミットし、ドラフト PR を作成する。
- CI 結果を確認する。
- ユーザーの明示指示があるまでマージしない。
