結論

本資料で扱う改善は合計 28 件です。一覧操作の改善により、フォルダー移動・更新・ファイル操作後もキーボードで操作を続けられ、削除が全件成功した際の通知も省略されます。現在のコードで自動テスト（841件）とWPFの描画・連続キー入力を確認しました。

サーバーの更新は完了しています。2026年9月14日（月）から全体展開を開始します。クライアントはツールの起動時に自動更新されます。開始から約2週間を初期流動期間として、利用状況と問い合わせを重点的に確認します（→ 第7章）。

2PoC の進め方

各係から2名ずつに、日常のファイル受け渡し業務でそのまま使ってもらいました。改善の入口は次の2系統です。

  • ① 利用者の声：実際に使って「やりにくい」「前のツールではこうできた」と感じた点を挙げてもらう
  • ② 管理者の気づき：管理者として実環境で運用・確認する中で把握した、本格導入前に潰しておくべき課題

挙がった内容を改修し、「直す → 配布する → 試してもらう」というサイクルで進めました。改修後はレビューと自動テストで確認し、ClickOnce の自動更新により、利用者がツールを起動したタイミングで新しいクライアントへ更新します。

4管理者として把握・改善した点（10 件）

以下は利用者から挙がったものではなく、管理者として実環境で運用・確認する中で把握し、本格導入の前に解消しておくべきと判断して手を入れたものです。利用者からは見えにくいものの、展開後の運用コストと停止リスクに直結する項目です。

管理者の気づき4-1. 利用者を名前で識別できるようにする

権限設定や操作ログの確認を、認証 ID（GID）だけで行うのは実務上つらいと判断しました。任意の表示名（最大100文字・重複可）を追加し、山田 太郎（G012345） の形式でユーザー管理・ユーザー権限・信頼デバイス・操作ログに表示・検索できるようにしました。CSV の一括登録・エクスポートにも対応しています。

表示名はあくまで表示用です。認証、Windows の本人確認、JWT、権限判定、セッション失効の条件には一切使用しません。監査ログに保存済みの記録も書き換えません。

管理者の気づき4-2. 管理画面の表示と監査記録の整合性

管理画面を実際に運用しながら確認する中で、ユーザー一覧・信頼端末一覧の行が正しく表示されない不具合を発見し、修正しました。あわせて監査記録まわりの安全性・整合性についても自己レビューで洗い出し、対応しています。利用者に見える形で表面化する前に解消できています。

管理者の気づき4-3. 既存サーバー環境との互換を確保する

PoC 環境へ載せる過程で、既存の社内サーバー構成と噛み合わなくなっていた設定を2件把握し、復元しました。これは本格導入時に既存環境で必ず踏むもので、事前に潰せた意義は大きいと考えています。

把握した事象対応
IIS の Windows 統合認証の既定値が、既存構成では認証できない側へ変わっていた同梱設定と既定値を既存 IIS 環境と互換な動作へ復元。より厳しい設定は、必要な環境で明示的に選べる形として残した
1つの共有秘密で複数の Agent（踏み台）を運用する従来構成が使えなくなっていた共有秘密での認証時も申告された Agent ID からノードを識別できるよう復元。監査ログもどの Agent 経由かを記録。旧バージョンの Agent も受理し、未登録 ID や申告の不一致は拒否
共有秘密を使う構成では、同じ秘密を持つ Agent はいずれも同じ ID を名乗れます。したがって全 Agent を同一の管理・信頼境界として扱うことを、仕様・管理者向け資料に明記しました。より厳密な分離が必要な場合は、相互 TLS 認証による構成を選択できます。

管理者の気づき4-4. 詰まったときに管理者が自力で回復できる状態にする

運用を想定して確認する中で、接続先の共有が到達不能になると、管理者が何もできなくなる状態が起こり得ることを把握しました。未完了の転送やごみ箱の管理台帳が残っている間は接続先の変更・削除がブロックされる仕様のため、共有そのものが応答しなくなると台帳を片付けられず、共有の付け替えも削除も永久にできない——つまり「壊れた共有を別サーバーへ逃がしたい」という一番使いたい場面で手詰まりになります。次の3点で解消しました。

対応内容
① 見える化管理画面の共有詳細に残存データを表示。「待てば消えるもの」と「待っても消えないもの」を区別して示すため、管理者が待つべきか強制解除すべきかを判断できる
② 強制解除まず正規の後片付けを試み（共有が生きていれば実体ごと回収）、失敗した分だけ台帳を終了させ、回収できなかったパスを監査ログに残す。画面では「進行中の転送が中断される」「回収できない実体がゴミとして残る」ことを確認ダイアログで明示
③ 打ち切り失敗し続ける後片付けを、猶予期間（既定 7 日）を過ぎたら自動的に諦めて終了。詰まった状態そのものが起きにくくなり、警告ログの垂れ流しも止まる

加えて、計画停止を利用者に伝える手段がないという課題に対し、メンテナンスモードを追加しました。管理画面から「予定／作業中／復旧確認／通常」を切り替えると、サーバーは新規の業務要求を止めつつ受付済みの要求は完了させ、利用者側は起動・ログイン・メイン画面で案内を表示します。Serverの受付再開と必須更新の確認後、メンテナンス待機にした転送だけを再開します。API停止中にも案内するには、独立した状態サイトとServer／Client双方の設定が必要です。

管理者の気づき4-5. 問い合わせ対応をしやすくする

「どのバージョンを使っていますか」と尋ねても即答できず、切り分けに時間がかかる——これは展開規模が大きくなるほど効いてきます。バージョン情報を専用画面へ移し、表示中のアプリの実際のバージョンを確認したうえで、アプリ名とバージョンを問い合わせ用にコピーできるようにしました。コピーに失敗した場合は再試行の案内を表示します。あわせて鳥居の「ひとこともらう」で、ごあいさつや転送操作のヒントを表示します（音や自動アニメーションはありません）。

  • サーバーの更新は完了しています。リモート一覧の2000件表示と拡張子順の並べ替えに必要なサーバー側の対応も反映済みです。

  • 9月14日〜9月27日は初期流動期間です。更新状況、一覧の移動・更新・削除、転送の継続を確認し、不具合と問い合わせを集約して対応します。9月28日以降を目安に、課題の対応状況を確認して通常運用へ移行します。
  • 以後の更新はメンテナンスモードで案内できます。計画停止の予定・作業中・復旧確認を管理画面から切り替えると、利用者側に案内が表示され、メンテナンス待機にした転送だけを、受付再開と必須更新の確認後に再開します。独立状態サイトを利用する場合は、導入・運用ガイドに従って設定します。

全体展開の予定

9月14日（月）から全体展開を開始します。最初の約2週間は初期流動として重点的に状況を確認し、利用者の問い合わせや課題に対応します。

通常運用への移行は9月28日（月）以降を目安とし、初期流動での確認結果に応じて調整します。
